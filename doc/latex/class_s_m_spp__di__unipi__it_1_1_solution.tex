\subsection{Detailed Description}
a solution of a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} 

The \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} class represents a solution of a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}. A solution of a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} can be composed, for example, by the values of the static and dynamic \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} and dual variables of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} of a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}. This \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} be used to store and retrieve those values. A \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} must implement the method

void read( Block $\ast$ const block )

which takes a (pointer to a) \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, reads the values of the current solution of this \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} and stores them. Once the values of a solution of a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} have been stored, they can be retrieved by the method

void \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_a6ba3f1b8f44f35e6a56fc0795587f68a}{write( Block $\ast$ const block )}}

which takes a (pointer to a) \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} and writes the value of the solution currently stored in this \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} into the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}.

A \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} is normally constructed by the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} whose solution must be stored. When it is constructed, a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} object can be \char`\"{}configured\char`\"{} to take only a specific part of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} solution status (see the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_configuration}{Configuration}} parameter in \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block_a1db67c2f65111af4314e79dfc81ba597}{Block\+::get\+\_\+\+Solution()}}); say, only the primal or the dual values, only the values of a specific set of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}, ... This configuration is \char`\"{}permanent\char`\"{}\+: once a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} is object created, it will only store that particular set of information. Trying to read a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} from a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} that does not have the required information (say, because dual information is required which is stored in some \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}, but these have not been constructed yet) is an error ans should result in an exception being thrown.

Of course, it is a fortiori an error (resulting in an exception being thrown) to read or write a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} out of the wrong \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}. This does not only mean \char`\"{}the wrong type of Block\char`\"{}, but basically \char`\"{}the very same Block
that has created the solution object\char`\"{}, or at least one that is \char`\"{}identical\char`\"{} to it (say, a copy \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} constructed as an R3 \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}), or at the very very least that is \char`\"{}compatible\char`\"{} (meaning it has the same size in the relevant sets of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} / \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}). \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} are not meant to be exchanged between different \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, even of the same type.

\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} also provides support for producing weighted sum of solutions of a given \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, which in particular allows to produce convex combinations of them (convexity being an all-\/important property, and convex relaxations being at the heart of countless many optimization techniques). This is somehow delicate because some \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}}, in particular discrete ones, may not \char`\"{}be happy\char`\"{} with being arbitrarily scaled and/or summed, and thus requires some care, see the comments to \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_abf1a2d1763f128a72b2677d4b9ff4d3b}{scale()}} and \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_adc2450947fd142657637bf79d91505a9}{sum()}}.

{\footnotesize\ttfamily virtual \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}}$\ast$ scale (\begin{DoxyParamCaption}\item[{double}]{factor }\end{DoxyParamCaption}) const\hspace{0.3cm}{\ttfamily [pure virtual]}}



returns a scaled version of this \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} 

This method constructs and returns a scaled version of this \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}}, where each of the solution information is scaled by the given double value. A \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} object can be \char`\"{}configured\char`\"{} to take only a specific part of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} solution status\+: the scaled version of a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} object obviously \char`\"{}shares the same configuration\char`\"{} as the original object.

Scaling by a double is a \char`\"{}somewhat dangerous\char`\"{} operation\+: it is quite natural if all solution information is \char`\"{}double\char`\"{}, which is what is most likely to happen most of the time, but not in all cases. For instance, some \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} may correspond to combinatorial problems whose solutions are essentially combinatorial objects (paths/cuts on a graph ...), for which \char`\"{}scaling\char`\"{} makes little sense. Yet, these problems are typically also represented in terms of subspaces of $^\wedge$n, and therefore one might expect scaling to be possible. However, it is clear that scaling may destroy some of the properties that solutions have\+: for instance, a path in a graph can be represented by means of a predecessor function, but a scaled path can not -- in the sense that it needs at least another information, the scaling factor, or to be transformed into a different format, such as the amount of \char`\"{}flow\char`\"{} going on each arc of the graph.

This implies that there might be different \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} objects relative to a given \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}; say, the \char`\"{}original ones\char`\"{} corresponding to combinatorial solutions (a path, represented by a predecessor function) and the "scaled ones) produced by scaling and/or summing (see \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_adc2450947fd142657637bf79d91505a9}{sum()}}) below (say, a double for each arc of the graph). Thus, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_abf1a2d1763f128a72b2677d4b9ff4d3b}{scale()}} might return a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} object that, while being appropriate for the original \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, may in fact be \char`\"{}of
a different type\char`\"{} than the originating one\char`\"{}. The requirement is that the

This method adds a scaled version of the given \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} (see \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_abf1a2d1763f128a72b2677d4b9ff4d3b}{scale()}}) to this \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}}. A \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} object can be \char`\"{}configured\char`\"{} to take only a specific part of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} solution status\+: this means that even of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} object pointed by solution has \char`\"{}more information\char`\"{} than the current one, only the relevant part will be extracted and summed to that of the current one, so that \char`\"{}the original configuration is preserved\char`\"{} even after this operation. It is an error if solution does not have the required part (and, a fortiori, if it is not the right \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}}), resulting in an exception being thrown.

As discussed in \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_abf1a2d1763f128a72b2677d4b9ff4d3b}{scale()}}, scaling by a double is a \char`\"{}somewhat dangerous\char`\"{} operation that may not necessarily make sense for all kinds of solution information, in particular discrete ones. The same potentially holds for sums (many combinatorial structures are closed under sum but not all are), and a fortiori for \char`\"{}sum with a scaled object\char`\"{}. Thus, some \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} may not be able to properly implement this operation without fundamentally alter their own internal representation, which is not supposed to happen. Thus,

IT IS N\+OT N\+E\+C\+E\+S\+S\+A\+R\+I\+LY S\+A\+FE TO C\+A\+LL \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_adc2450947fd142657637bf79d91505a9}{sum()}} ON A \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} J\+U\+ST P\+R\+O\+D\+U\+C\+ED BY \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block_a1db67c2f65111af4314e79dfc81ba597}{Block\+::get\+\_\+\+Solution()}}

although in general it should always be possible to \char`\"{}configure the
\+Solution\char`\"{}, by using the corresponding \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_configuration}{Configuration}} object to instruct the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} to produce the kind of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} object for which it is safe. Furthermore,

IT IS S\+A\+FE TO C\+A\+LL \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_adc2450947fd142657637bf79d91505a9}{sum()}} ON A S\+O\+L\+U\+T\+I\+ON C\+O\+N\+S\+T\+R\+U\+C\+T\+ED BY \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_abf1a2d1763f128a72b2677d4b9ff4d3b}{scale()}}

That is, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_abf1a2d1763f128a72b2677d4b9ff4d3b}{scale()}} has to report a \char`\"{}general\char`\"{} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}}, one for which it makes sense {\itshape both} scale it and sum it with other \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} objects. Note that the idea is that is must be always possible to use \char`\"{}less
general\char`\"{} solution objects as the solution parameter in \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_adc2450947fd142657637bf79d91505a9}{sum()}}\+: the recipient (current) \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} object must be \char`\"{}general\char`\"{} for \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_adc2450947fd142657637bf79d91505a9}{sum()}} to be possible, but the summed one need not be. Of course, all this must be entirely handled by the (different variants of) \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}}.

It should be remarked that there could be \char`\"{}intermediate\char`\"{} types of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} objects between the \char`\"{}less general\char`\"{} and the \char`\"{}more general\char`\"{} ones. For instance, some discrete structures are closed under sum, or even scaled sum where the scalar has appropriate properties (say, it\textquotesingle{}s an integer). Thus, it may not be efficient to require \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_abf1a2d1763f128a72b2677d4b9ff4d3b}{scale()}} to return the \char`\"{}more general\char`\"{} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}}. Yet, handling these special cases should always be possible by requiring the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} to produce \char`\"{}the right kind of Solution
object\char`\"{} by means of its \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_configuration}{Configuration}}.
