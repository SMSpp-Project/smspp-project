\item conversely, multiple linearizations may be produced at some x. For instance, even if u$^\wedge$$\ast$ is unique, any -\/optimal solution u\textquotesingle{} of P(x) produces a linearization ( g\textquotesingle{}, \textquotesingle{} ) = L( u\textquotesingle{} ) which is an -\/subgradient of f, i.\+e., \textquotesingle{}  f(x) -\/  (by the very definition of -\/optimal solution) and f(y) $>$= \textquotesingle{} + g\textquotesingle{} ( y -\/ x ) for all y.
\end{DoxyItemize}

Thus, one linearization may in fact \char`\"{}refer to multiple points\char`\"{}, and, conversely, \char`\"{}a single point may provide multiple linearizations\char`\"{}. This class has to cater for all these mechanics, which is done via two distinct \char`\"{}pools\char`\"{} of linearizations, the \char`\"{}local\char`\"{} and the \char`\"{}global\char`\"{} one.

The local pool is directly tied to the last point x where \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function_a504d4e3e174c7a518cc66156a8a45ce5}{compute()}} has been called, and it is automatically cleared as soon as \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function_a504d4e3e174c7a518cc66156a8a45ce5}{compute()}} is called again (on a different x). The idea is therefore that the local pool is to be populated with linearizations \char`\"{}significant at x\char`\"{}. The specific concept is left intentionally vague, but examples are\+:


\begin{DoxyItemize}
\item for a convex function, the -\/subdifferential, i.\+e., the set of -\/subgradients at x (see above);
\item for a concave function, the set of -\/supergradients \mbox{[}the same thing with properly inverted signs\mbox{]};
\item for a reasonably regular function (say, continuous and differentiable almost everywhere), either the Goldstein or the Clarke -\/subdifferential, which are something like the closed convex hull of the set of vectors obtained as limits of  f(x\+\_\+i) as x\+\_\+i goes to x, or to any point in a ball of radius  around x.
\end{DoxyItemize}

Note that whenever useful, as in this case, with a little abuse of notation we refer to only the g part of the linearization as \char`\"{}the
linearization\char`\"{}. This, for instance, allows to say that, if the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} is differentiable at x and  = 0, all the three examples collapse to  f(x) as the only possible linearization.

We purposely refrain from giving a more formal definition as the above examples are only meant to convey the general idea that there is a set of \char`\"{}linearizations relevant up to a number \textbackslash{}eps\char`\"{}, which is what the interface supports. Specific algorithms will have specific requirements on the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} (say, convex) which will typically imply requirements on the set in question (say, is the -\/subdifferential), but since there are several possible variants this is left for further specifications\+: the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_c05_function}{C05\+Function}} aims at capturing all these cases.

Note that all the sets mentioned in the examples are {\itshape convex}. Accordingly, the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_c05_function}{C05\+Function}} interface explicitly supports the notion that convex combinations of linearizations are important. It should be apparent why this is necessary\+: proving (approximate) optimality/stationariety of a point x$^\wedge$$\ast$ (even in the simple case where there are no constraints or other components in the objective function) amounts at proving that 0  $^\wedge$n belongs to the corresponding set of linearizations (-\/subdifferential). In general, even if called at such a x$^\wedge$$\ast$ the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_c05_function}{C05\+Function}} cannot be expected to produce the 0 linearization; this is why proving (approximate) optimality/stationariety of x$^\wedge$$\ast$ typically boils down to producing a set of linearizations g\+\_\+i at points x\+\_\+i \char`\"{}close\char`\"{} to x$^\wedge$$\ast$ and then proving that 0  conv( \{ g\+\_\+i \} ). Thus, the interface has to cater for\+:


\begin{DoxyItemize}
\item collecting and storing in a \char`\"{}long-\/term memory\char`\"{} (the global pool, as opposed to the short-\/term memory of the local pool) linearizations that have been produced at different points x\+\_\+i;
\item making convex combinations of linearizations of the global pool.
\end{DoxyItemize}

In particular, there is usually \char`\"{}one important convex combination\char`\"{} that is very relevant for algorithmic purposes. This can be clearly seen in the Lagrangian function example\+: for a point x$^\wedge$$\ast$ to be -\/optimal for the mininization of f (the Lagrangian Dual), one must collect a set of -\/subgradients g\+\_\+i such that 0  conv( \{ g\+\_\+i \} ). It is immediate to realize that this corresponds to a set of -\/optimal solutions u\+\_\+i to P(x$^\wedge$$\ast$) such that u$^\wedge$$\ast$ =  u\+\_\+i , for appropriate convex multipliers , is such that A u$^\wedge$$\ast$ = b. If U in (P) is a convex set then such an u$^\wedge$$\ast$ is an optimal solution to (P), otherwise u$^\wedge$$\ast$ is the optimal solution of the relaxation of (P) substituting U with conv( U ). In all cases, u$^\wedge$$\ast$ can be a relevant object to construct. For instance, u$^\wedge$$\ast$ can be used to to separation of constraints (in case the A u = b ones are very many, so that an active-\/set strategy is necessary), or to guide heuristics or branching operations (if the set U included integrality constraints, so that the Lagrangian Dual of (P) is only a relaxation).

More in general, proving optimality/stationariety of some x$^\wedge$$\ast$ involves constructing one convex combination of linearizations with appropriate properties. It may be very useful to be able to store away this object in case the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} (or other parts of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}) changes, in order to provide effective reoptimization. For instances, the changes may be such that x$^\wedge$$\ast$ may nonetheless remain an optimal solution, and the availability of the \char`\"{}important linearization\char`\"{} may allow to prove this with very little computational effort. This is why the interface has specific provisions for producing and storing in the global pool this kind of objects.

A further important detail is that there can be two types of linearizations\+: \char`\"{}diagonal\char`\"{} and \char`\"{}vertical\char`\"{}. Diagonal linearizations are the previously illustrated ones; the names comes from picturing the ( x , v ) space $^\wedge$\{n+1\} as having the x component on the horizontal axis and the v component as the vertical one (the typical arrangement for the graphical space of a function). Then, a linearization ( g ,  ) typically corresponds to a line approximating f in the neighbourhood of some x. If, say, f is convex, this corresponds to a linear constraint \begin{DoxyVerb}  ( 1 , - g ) ( v , x ) >= \alpha       (*)
\end{DoxyVerb}


which is globally correct for the graph of f (actually, the epigraph). The corresponding line in the ( x , v ) space either intersects the x axis \char`\"{}diagonally\char`\"{} or is parallel to it (if g = 0), but it can never be hortogonal to it. Thus, there is an entirely different form of lines in the graphical space, those corresponding of linear constraints of the form \begin{DoxyVerb}  ( 0 , - g ) ( v , x ) >= \alpha       (**)
\end{DoxyVerb}


These may still be valid for the (epi)graph of f. This is in particular the case for convex functions evaluated outside of their domain, i.\+e., at points y s.\+t. f(y) = +. In some cases, it is possible for the function to compute a \char`\"{}vertical\char`\"{} linearization ($\ast$$\ast$) which is valid for all ( x , v ) in the (epi)graph of f but that \char`\"{}cuts off\char`\"{} y, i.\+e., such that 0 $<$ g y + alpha. This is true for instance in the Lagrangian case P(x) where U is an unbounded set, say a convex one\+: then, P(x) is unbounded below if there is some v in the recession cone of U such that ( c + x A ) v $>$ 0. This immediately implies that f(y) = + for all y with the same property, i.\+e., that the constraint c v + x ( A v ) $<$= 0 is valid for the (epi)graph of f. Since v is typically constructed by whatever algorithm is used to solve P(x) in order to prove that it is unbounded above, the corresponding vertical linearization of the form ($\ast$$\ast$) can be returned by the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_c05_function}{C05\+Function}}. Note that, customarily, a solution algorithm would also compute a feasible solution u  U together with v, and therefore can return both a diagonal and a vertical linearization, which the interface allows. In the parlance of Benders\textquotesingle{} decomposition, diagonal linearizations are \char`\"{}optimality cuts\char`\"{} and vertical linearizations are \char`\"{}feasibility cuts\char`\"{}. However, the concept is possibly general.

There is usually \char`\"{}one important convex combination\char`\"{} that is very relevant for algorithmic purposes. This can be clearly seen in the Lagrangian function example\+: for a point x$^\wedge$$\ast$ to be -\/optimal for the mininization of f (the Lagrangian Dual), one must collect a set of -\/subgradients g\+\_\+i such that 0  conv( \{ g\+\_\+i \} ). More in general, proving optimality/stationariety of some x$^\wedge$$\ast$ involves constructing one convex combination of linearizations with appropriate properties. stores a convex combination of the given linearizations 

This method creates a convex combination of a given set of linearizations, with given coefficients, and stores it (or information allowing to compute it) into the global pool of linearizations with the given name.

The linearizations whose convex combination the new one must be created from, together with the corresponding coefficients, are indicated by vector of pairs. Each pair has the name of a linearization (that must be currently stored in the global pool of linearizations) and the coefficient this linearization must have in the convex combination. Once this convex combination is created, it is stored into the global pool with the name passed as argument. If the new linearization is stored under the name of a previously stored linearization, the latter is replaced with the former.

The rationale for this method is that most approximate sub-\/differentials are convex sets. Thus, proving (approximate) optimality/stationariety of a point x$^\wedge$$\ast$ (even in the simple case where there are no constraints or other components in the objective function) amounts at proving that 0  $^\wedge$n belongs to the corresponding set of linearizations (-\/subdifferential). In general, even if called at such a x$^\wedge$$\ast$ the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_c05_function}{C05\+Function}} cannot be expected to produce the 0 linearization; this is why proving (approximate) optimality/stationariety of x$^\wedge$$\ast$ typically boils down to producing a set of linearizations g\+\_\+i at points x\+\_\+i \char`\"{}close\char`\"{} to x$^\wedge$$\ast$ and then proving that 0  conv( \{ g\+\_\+i \} ). Such a \char`\"{}convexified
linearization\char`\"{} is often a valid linearization as any one directly produced by the function, and therefore can be saved in the global pool as they are. This may allow, for instance, to reduce the maximum size of the global pool by replacing many linearizarizations by just one \char`\"{}representing them all\char`\"{} (think conjugate subgradients).

Note that the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_c05_function}{C05\+Function}} may freely decide to either store the convexified linearization itself, or information allowing to compute it, or both. For instance, in the Lagrangian case, any linearization g\+\_\+i corresponds to a point u\+\_\+i in U. Hence, the convexified linearization corresponds to a point in conv( U ); if U is convex then that point is still in U, otherwise it is a point in its convex hull which can still have numerous algoroithmic uses.

The method has a default empty implementation as some \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} may ignore this information because it can perform the other required actions \mbox{[}see \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_c05_function_a6fa70047dc8b3d43a3ed44f1859a7239}{get\+\_\+linearization\+\_\+coefficients()}}\mbox{]} by other means. In particular, a linear function always have the same linearization everywhere, and therefore any convex combination of these always returns the same vector. \mbox{\Hypertarget{class_s_m_spp__di__unipi__it_1_1_c05_function_ac477d0c3276fa28127d5aff69f31c367}\label{class_s_m_spp__di__unipi__it_1_1_c05_function_ac477d0c3276fa28127d5aff69f31c367}}

store a linearization in the global pool 

The last linearization that was computed by calling \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_c05_function_a9a77f2430dcf732f6d6d9fd50d923baf}{compute\+\_\+new\+\_\+linearization()}} (which returned true) can be permanently stored in the global pool of linearizations by calling this method. Linearizations in the global pool are identified by their names, which must be integers between 0 and int\+G\+P\+Max\+Sz -\/ 1 (this allows to implement the global pool as a simple vector-\/like structure containing either the linearizations or the information allowing to compute them). The name must be provided when storing a linearization, so that this specific linearization can be later retrieved by using its name. If a linearization is stored under the name of a previously stored linearization, the latter is replaced with the former in the global pool. A linearization is kept in the global pool until it is explicitly deleted \mbox{[}see \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_c05_function_a538bfc1740cb18a36b0edf8b35085e2c}{delete\+\_\+linearization()}}\mbox{]} or replaced with another linearization by a call of this method. A linearization with \char`\"{}large\char`\"{} name is also deleted if the global pool of linearizations is shrank by changing int\+G\+P\+Max\+Sz.

The method has a default empty implementation as some \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} may ignore this information because it can perform the other required actions \mbox{[}see \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_c05_function_a6fa70047dc8b3d43a3ed44f1859a7239}{get\+\_\+linearization\+\_\+coefficients()}}\mbox{]} by other means. In particular, a linear function always have the same linearization everywhere, and therefore there is arguably no need to store it many times over.
