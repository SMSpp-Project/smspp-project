\subsection{Detailed Description}
base class of all possible real-\/valued functions 

The class \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} is the base class intended to represent \char`\"{}all possible\char`\"{} real-\/valued functions.

This base class is meant to provide only the \char`\"{}most basic\char`\"{} interface of a function, i.\+e., only access to function {\itshape values}; things like derivatives and/or specific algebraic forms of the function are demanded to derived classes. As such, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} only supports a few fundamental facts\+:


\begin{DoxyItemize}
\item a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} \char`\"{}reports to\char`\"{} one \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_observer}{Observer}} \mbox{[}see \mbox{\hyperlink{_observer_8h}{Observer.\+h}}\mbox{]}, i.\+e., sends it all its \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}};
\item a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} is influenced by a set of \char`\"{}active\char`\"{} Variables, i.\+e., those which contribute to it setting its (real) value\+: hence, the class implements the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_var_dep_interface}{Thin\+Var\+Dep\+Interface}} paradigm (i.\+e., derives from \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_var_dep_interface}{Thin\+Var\+Dep\+Interface}}) that class makes no provisions about how this set is stored in order to leave more freedom to derived classes to implement it in specialized ways;
\item a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} must be computed, and this can be costly (think multiple integrals or min-\/max functions requiring the solution of a hard optimization problem), which is why the class implements the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface}{Thin\+Compute\+Interface}} paradigm (i.\+e., derives from \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface}{Thin\+Compute\+Interface}}).
\item a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} can be approximately evaluated, which means that one can be content with only lower and/or upper estimates of the function values, provided they are \char`\"{}exact enough\char`\"{} (see details in the interface).
\end{DoxyItemize}

However, \begin{DoxyVerb}    Function OBJECTS ARE NOT SUPPOSED TO DO THAT
\end{DoxyVerb}


The rationale is that \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} objects may either be a part of some other object (\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}}, ... ) or, possibly, be \char`\"{}free-\/floating\char`\"{} ones; when it is constructed, a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} has no way of knowing which of the two cases it is in. Hence, to be on a safe side the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} must not register itself with its \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}. Rather \begin{DoxyVerb}    IF THE Function IS SET AN Observer THAT ALSO IS A
    ThinVarDepInterface, THEN THAT Observer WILL BE REGISTERED
    AS "ACTIVE" IN THE Variable OF THE Function
\end{DoxyVerb}


Thus, if the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} is used inside a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}}, ... then it will be the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}}, ... that is registered. Hence, each each time a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} is added to/removed from the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}}, the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} will have to register/unregister its \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_observer}{Observer}} (rather than itself) to the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}. \begin{DoxyVerb}    FREE-FLOATING Function, USED SOMEHOW AND SOMEWHERE IN A Block
    BUT *NOT* INSIDE A ThinVarDepInterface, WILL *NOT* REGISTER
    THEMSELVES OR ANYTHING ELSE IN THEIR "ACTIVE" Variable
\end{DoxyVerb}


Since the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} is not (directly) used to implement a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}}, ... the fact that it depends on those \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} is not \char`\"{}made
known\char`\"{} to the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} themselves. This may (but hopefully won\textquotesingle{}t) cause issues, and it would make it difficult to have multi-\/level \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} (sum of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}}, composition of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}}, ...). If any of this becomes enough of a nuisance this mechanism will have to be revised, but for now it appears to be reasonable.

The base \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} class also supports providing the user with some very basic information about properties of the function that only depend on function values, such as\+:


\begin{DoxyItemize}
\item \mbox{[}upper and/or lower semi-\/\mbox{]}continuity;
\item convexity and/or concavity;
\item existence of a (finite) Lipschitz constant.
\end{DoxyItemize}

A fundamental design decision in S\+M\+S++ is that T\+HE \char`\"{}\+N\+A\+M\+E\char`\"{} OF A \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} IS I\+TS M\+E\+M\+O\+RY A\+D\+D\+R\+E\+SS. This means that M\+O\+V\+I\+NG A \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} IS N\+OT P\+O\+S\+S\+I\+B\+LE\+: copying a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} to a different memory location makes a distinct \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}}.
