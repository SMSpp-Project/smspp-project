\subsection{Detailed Description}
abstract base class for any solution algorithm for any \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} 

The {\itshape abstract} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} class is meant to represent the basic interface between a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} \mbox{[}see \mbox{\hyperlink{_block_8h}{Block.\+h}}\mbox{]}, representing (possibly together with its recursively nested sub-\/\+Blocks) a (block-\/structured mathematical) model, and any algorithm capable of \char`\"{}solving\char`\"{} it. This means (trying to) produce feasible solutions, i.\+e., values for all the Variables \mbox{[}see \mbox{\hyperlink{_variable_8h}{Variable.\+h}}\mbox{]} of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} that satisfy all its Constraints \mbox{[}see \mbox{\hyperlink{_constraint_8h}{Constraint.\+h}}\mbox{]}, or proving that there is none.

It is important to clearly state the {\itshape ownership} of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} and \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} \mbox{[}see \mbox{\hyperlink{_block_8h}{Block.\+h}}\mbox{]}, which is that they are directly defined either in the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, or in any of its inner Blocks (recursively). This has important consequences, related to the fact that a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} defined in a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} may contain Variables that the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} does not own. Conversely, some \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} can be active in a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} that is not owned by the block. The intended semantic of these cases are\+:


\begin{DoxyItemize}
\item If a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} defined in a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} contains \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} that the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} does not own, when the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} is asked to solve the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} these Variables have to be treated as {\itshape constants}, with the value that they currently have. Note that this is a specific case where the data of the corresponding mathematical problem changes, but there is no \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} that signals this to any \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} attached to the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}. This means that the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} needing to know about this will have to \char`\"{}manually\char`\"{} check whether or not a change occurred.
\item A \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} not owned by the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} is irrelevant to the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} even if it contains \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} owned by the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}; any \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} has to thoroughly ignore it. Paradoxically, such a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} may contain {\itshape only} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} owned by the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, and therefore logically belonging to it, but still it has to be ignored.
\item The \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} may change all, and only, the Variables owned by the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} when solving it, and has to take into account all, and only, the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} owned by the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} when defining what a feasible solution is.
\end{DoxyItemize}

The \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} class is thought primarily (although not exclusively) for mathematical models in the form of an optimization problem; hence, the solutions should be either generically \char`\"{}good\char`\"{} ones, or, better, provably (approximately) optimal ones. This is provided an optimal solution exists at all\+: if the mathematical model is unbounded (below for a minimization problem, above for a maximization one), then the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} should be able to detect it and, hopefully, \char`\"{}prove\char`\"{} it.

The base \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} class is very generic, and therefore it only supports a number of very general notions\+:


\begin{DoxyItemize}
\item a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} is attached to a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, from which it picks all the data characterizing the model and that it uses to output any solution it finds (in the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}});
\item a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} can (in fact, must) be specialized to work on a specific class of models, represented by one (or more) specific class(es) derived from \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}};
\item a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} can (in fact, must) react to changes in the data of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, of which it is made aware by appropriate \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}};
\item a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} can (attempt at) solve the model, i.\+e., obtain at least one feasible solution (to within the required tolerance for each \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, see \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block_a4204ffb542117f4ea97eeceeda4da079}{Block\+::is\+\_\+feasible()}}) that is also provably optimal to within the required accuracy, see Set\+Par() below; upon termination it will provide a full account about how the solution attempt went \mbox{[}see sol\+\_\+type below\mbox{]};
\item a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} may be able to provide multiple solutions to the problem for each call of solve() \mbox{[}see \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver_af109b504a566c90a4ea45c1574c128fe}{new\+\_\+var\+\_\+solution()}} and \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver_a91d7cd0dc4fa453406ef30db2bfa37a5}{get\+\_\+var\+\_\+solution()}} below\mbox{]}, be them feasible or unfeasible ones, in an appropriate order (from the \char`\"{}more interesting\char`\"{} to the \char`\"{}less interesting\char`\"{});
\item a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} compute solutions, and this can only be expected to be costly (up to extremely costly), which is why the class implements the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface}{Thin\+Compute\+Interface}} paradigm (i.\+e., derives from \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface}{Thin\+Compute\+Interface}}).
\end{DoxyItemize}

Despite tying to be quite general, the class is clearly somewhat bent towards {\itshape single-\/objective, real-\/valued} optimization problems, as shown by extensive support towards the concept of \char`\"{}objective function value\char`\"{} and (upper and lower) bounds upon that. Hence, although not strictly necessary, it is somewhat intended that the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}} of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} actually is a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_real_objective}{Real\+Objective}}. Hence, one would expect that the O\+F\+Value type \mbox{[}see below\mbox{]} is the same as that defined in \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_real_objective}{Real\+Objective}}. Steps are taken so that problems without an objective function should not find this choice \char`\"{}too
intrusive\char`\"{}; basically, every method having to do with the (real) objective function value is given here a safe default implementation so that it can be basically ignored by classes not having that concept (say, because they have no objective function) at all. For \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} with more complex, non-\/real-\/valued objective functions, appropriate derived classes will have to be defined that extend the \char`\"{}simple\char`\"{} treatment of real-\/valued objectives to the necessarily more complex concepts.

(try to) solve the model encoded in the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} 

Starts or the solution process of the problem, or restarts a previously interrupted solution process, and returns the status of the solver at termination.

If everything runs smoothly then the function is expected to return k\+OK which means that the optimization process was finished successfully, i.\+e., a solution was found that can be {\itshape proven} feasible and optimal w.\+r.\+t. the prescribed accuracy levels. However, the return codes k\+Infeasible and k\+Unbounded, corresponding respectively to the case that the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} {\itshape proves} the problem to be infeasible and unbounded, are also \char`\"{}k\+O\+K-\/type\char`\"{} return codes. Different \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} may be able to provide some further information about certificates of optimality, unboundendness or infeasibility, and more functionalities can be expected to exist in the derived classes about this.

If \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver_a504d4e3e174c7a518cc66156a8a45ce5}{compute()}} returned k\+Stop\+Time or k\+Stop\+Iter, then calling it again resets the time counter, allowing the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} to proceed further in the optimization process. An {\itshape exact} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} will always eventually return k\+OK given enough time (although \char`\"{}enough\char`\"{} can be longer than the thermal death of the universe), unless an error occurs (see k\+Error). However, not all Solvers are exact, which is what the return status k\+Low\+Precision is for\+: to indicate that, limits to computational resources notwithstanding, the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} has exhausted all its means to try to look for a (better) solution, so calling again \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver_a504d4e3e174c7a518cc66156a8a45ce5}{compute()}} will not help.

In case \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver_a504d4e3e174c7a518cc66156a8a45ce5}{compute()}} returns anything $>$= k\+Error, then this means that the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} was forced to stop due to some error, e.\+g. of numerical nature or because of lack of some crucial resource (say, memory). This may mean that no solution at all may have been produced, but some may instead be available, cf. k\+Low\+Precision; in fact, even the {\itshape optimal} solution could be available, but {\itshape with no certificate of optimality}. However, what a return code surely means is that there is little or no hope that calling \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver_a504d4e3e174c7a518cc66156a8a45ce5}{compute()}} again may rectify the problem.

In general, calling \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver_a504d4e3e174c7a518cc66156a8a45ce5}{compute()}} again after that it has reported k\+OK, k\+Infeasible, k\+Unbounded, k\+Low\+Precision, or k\+Error is possible, but it should not be expected to obtain a different result unless\+:


\begin{DoxyItemize}
\item some \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} has occurred in the meantime to the data of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, i.\+e., \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver_ae71b15277f34912175559c36e04f98fd}{add\+\_\+\+Modification()}} has been called at least once;
\item some of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} that the problem depends onto (if any), i.\+e., \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} not belonging to the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} but still present in some of its Constraint/\+Objective, have changed.
\end{DoxyItemize}

While the first occurrence is easy for the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} to verify, the second is not unless the previous value of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} is stored and checked; this is not required to happen, see the extensive comments to \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver_a504d4e3e174c7a518cc66156a8a45ce5}{compute()}} in the base \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface}{Thin\+Compute\+Interface}} class.

As a partial exception to this rule, if a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} has been asked to provide \char`\"{}all\char`\"{} its stored solutions \mbox{[}see k\+Max\+Sol, k\+R\+Acc\+Sol, k\+A\+Acc\+Sol and k\+F\+Acc\+Sol above and \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver_af109b504a566c90a4ea45c1574c128fe}{new\+\_\+var\+\_\+solution()}} below\mbox{]}, be them feasible or not, a new call to \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver_a504d4e3e174c7a518cc66156a8a45ce5}{compute()}} after a return value of k\+OK is interpreted as \char`\"{}please do provide more solutions\char`\"{}. The return value of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver_a504d4e3e174c7a518cc66156a8a45ce5}{compute()}} should be the same (unless, for instance, a k\+Error occurs), but the list of available solutions might be replenished.

Because directions are in the same space of solutions, the method assumes that the direction can be suitably represented with the same \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} that are used for solutions. Apart from that, the base \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} class makes no assumption about how the direction is stored, this being dependent on what the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} actually are. Note that the previous value in the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} is lost for good, irrespectively of the fact that it contained a solution or a direction, and the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} class does not provide any mechanism to retrieve it at a later time (except saving them beforehand in a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} object, see \mbox{\hyperlink{_solution_8h}{Solution.\+h}}).

One possible use for such a direction is to construct a solution with \char`\"{}arbitrarily good\char`\"{} (small for a minimization problem, large for a maximization one) value of the objective function. However, this typically requires first constructing a feasible solution, and then modifying it by means of the direction.
