\subsection{Detailed Description}
base class of all objects depending on a set of \char`\"{}active\char`\"{} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} 

Several objects in S\+M\+S++ explicitly depend on a set of \char`\"{}active\char`\"{} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}; these are \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}} and \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} (\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} may \char`\"{}indirectly\char`\"{} depend on a set of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}, but these are not defined through this interface).

The {\itshape abstract} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_var_dep_interface}{Thin\+Var\+Dep\+Interface}} class is meant to factor out many of the methods required to deal with this aspect. Factoring them is primarily meant to avoid un-\/necessary code duplication and to ensure consistency between similar parts of the interface of different objects; in particular, all \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_var_dep_interface}{Thin\+Var\+Dep\+Interface}} have to behave as standard S\+TL containers (with underlying type \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}), with iterator and \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_var_dep_interface_1_1const__iterator}{const\+\_\+iterator}} defined to allow sifting through the set of \char`\"{}active\char`\"{} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}. This is done by defining \char`\"{}virtual\char`\"{} iterators that can be specialized by derived classes (using inheritance, not templates) and a iterators redirecting from those. Furthermore, this allows \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} to deal with all these objects in an unified way.

Another reason for introducing the class at this point of the design cycle is that S\+M\+S++ may evolve by allowing \char`\"{}more structured\char`\"{} access to the set of \char`\"{}active\char`\"{} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}; say, explicitly distinguishing between static and dynaic ones and/or allowing to partition them in groups, like having as input multiple whole vector/list/multi-\/arrays of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}. However, how this is to be accomplished (if ever) is not decided yet. By factoring all aspects of the \char`\"{}active\char`\"{} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} interface into a single class, the effort to later refactor the interfaces to allow for this might be decreased.
