\subsection{Detailed Description}
a solution of a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_m_c_f_block}{M\+C\+F\+Block}} 

The \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_m_c_f_solution}{M\+C\+F\+Solution}} class, derived from \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}}, represents a solution of a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_m_c_f_block}{M\+C\+F\+Block}}, i.\+e.\+:


\begin{DoxyItemize}
\item an m-\/vector of F\+Number for the arc flow values;
\item an n-\/vector of C\+Number for the node potentials;
\end{DoxyItemize}

where m is the number of arcs and n is the number of nodes in the graph. This means that \begin{DoxyVerb}  THE REDUCED COSTS ARE NOT EXPLICITLY SAVED
\end{DoxyVerb}


This is OK for feasible dual solutions, as the dual variables of the bound constraints (a.\+k.\+a. Reduced Costs) can be cheapily computed out of the potentials. This may not be appropriate in all cases, as one may want to deal with unfeasible dual solutions; if this will ever be the case, the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_m_c_f_solution}{M\+C\+F\+Solution}} class will have to be changed accordingly.

It is useful to remark that some special cases of M\+CF would actually have \char`\"{}special\char`\"{} solutions (\char`\"{}less general\char`\"{} ones in the parlance of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}}). In particular\+:


\begin{DoxyItemize}
\item if all capacities are Inf$<$\+F\+Number$>$() and there is only one source or sink node, then the M\+CF problem is in fact a Shortest Path (sub-\/)Tree one, and its solutions can be represented by means of a predecessor function;
\item if all (finite) capacities and node deficits are integer, then there always exist optimal flow solutions of M\+CF that are integer;
\item if all arc costs are integer, then there always exist optimal potential solutions of M\+CF that are integer.
\end{DoxyItemize}

Thus, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_m_c_f_block}{M\+C\+F\+Block}} would have scope for different kinds of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} objects. The currently implemented one is the \char`\"{}most general\char`\"{} one, so that the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_abf1a2d1763f128a72b2677d4b9ff4d3b}{Solution\+::scale()}} and \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution_adc2450947fd142657637bf79d91505a9}{Solution\+::sum()}} operations are always possible; specialized \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} for the specific cases are left for future development.

returns a scaled version of this \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} 

This method constructs and returns a scaled version of this \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}}, where each of the solution information is scaled by the given double value. A \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} object can be \char`\"{}configured\char`\"{} to take only a specific part of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} solution status\+: the scaled version of a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} object obviously \char`\"{}shares the same configuration\char`\"{} as the original object.

Scaling by a double is a \char`\"{}somewhat dangerous\char`\"{} operation\+: it is quite natural if all solution information is \char`\"{}double\char`\"{}, which is what is most likely to happen most of the time, but not in all cases. For instance, some \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} may correspond to combinatorial problems whose solutions are essentially combinatorial objects (paths/cuts on a graph ...), for which \char`\"{}scaling\char`\"{} makes little sense. Yet, these problems are typically also represented in terms of subspaces of $^\wedge$n, and therefore one might expect scaling to be possible. However, it is clear that scaling may destroy some of the properties that solutions have\+: for instance, a path in a graph can be represented by means of a predecessor function, but a scaled path can not -- in the sense that it needs at least another information, the scaling factor, or to be transformed into a different format, such as the amount of \char`\"{}flow\char`\"{} going on each arc of the graph.

This implies that there might be different \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} objects relative to a given \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}; say, the \char`\"{}original ones\char`\"{} corresponding to combinatorial solutions (a path, represented by a predecessor function) and the "scaled ones) produced by scaling and/or summing (see \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_m_c_f_solution_ac91491316467fa9925f2c8e8fc08f4c1}{sum()}}) below (say, a double for each arc of the graph). Thus, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_m_c_f_solution_a2c818cbb6d8b22f839a7f7336f6b382b}{scale()}} might return a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} object that, while being appropriate for the original \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, may in fact be \char`\"{}of
a different type\char`\"{} than the originating one\char`\"{}. The requirement is that the
newly created Solution must be a \char`\"{}general" one, in the sense that it makes sense (obviously) to scale it, and also to {\itshape sum} it with other \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solution}{Solution}} objects, see \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_m_c_f_solution_ac91491316467fa9925f2c8e8fc08f4c1}{sum()}}.
