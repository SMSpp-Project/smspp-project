\subsection{Detailed Description}
base class for any possible modification that can happen to a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} 

The class \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} is the top of the hierarchy of (small) objects describing the differenc changes that can occur to the various pieces of a S\+M\+S++ model, in the classes \mbox{[}derived from\mbox{]} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}}.

\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} objects primarily serve to ensure any \char`\"{}interested\char`\"{} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} is made aware of the changes and can efficiently react to them. In fact, \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} objects are passed \char`\"{}up\char`\"{} in the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} hierarchy, i.\+e., from each \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} to its ancestors, to ensure that all \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} attached to any \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} that can be affected by the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} get the information. Since the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} has to reach an unknown number of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}}, smart pointers to the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} will be passed, so that each solver can individually (implicitly) delete the smart pointer, so that the \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} object will ultimately be deleted when the last \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} is done with that. Thus, a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} would {\itshape in principle} not be needed if there are no \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} attached to any of the relevant Blocks; this is why \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} provides the method anyone\+\_\+there() to check if any \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} is \char`\"{}listening\char`\"{} to the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}}, and potentially avoid to even generate it if none is.

However, the fact that no \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} is \char`\"{}listening\char`\"{} does not necessarily imply that a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} must not be issued; the reason is that there are, conceptually, {\itshape two} different kinds of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}}.

The first kind directly acts on the \char`\"{}physical representation\char`\"{} (PR) of a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}. Such a \char`\"{}physical Modification\char`\"{} (P\+Mod) is typically issued when a method of the specialized interface of a specific derived class from \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} is called. The P\+Mod indicates how the PR changes, and this is all that a {\itshape specialized} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} for that {\itshape specific kind of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}} has to know to update itself. However, any non-\/specialized solver, which rater relies on the \char`\"{}abstract representation\char`\"{} (AR) of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, has no way of properly reacting to such a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}}. Yet, when the PR is modified, the AR must change accordingly; this means that, besides the P\+Mod, one or more \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} pertaining to the AR (which we will therefore denote by A\+Mod) will also be issued. For instance, consider an hypothetical Knapsack\+Block that represents a knapsack problem and has an array that stores the weights of the items. In the AR, these weights may appear as coefficients of a linear function in a constraint (or in different ways, if for instance a dynamic programming formulation is used). When the user changes the weight of an item in the Knapsack\+Block, this produces a specific P\+Mod. To keep the AR and the PR synchronized, the Knapsack\+Block would have to update (say) that linear constraint where this weight appears as a coefficient, which would then produce an A\+Mod. This is, of course, if the AR has already been generated, otherwise there is simply nothing to modify.

All this means that there can be more than one \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} \char`\"{}in flight\char`\"{} at any point in time that is actually related to a single change in a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}. This requires that any \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} be capable of understanding if a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} is a \char`\"{}copy\char`\"{} of some other \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} that has already been handled, and either discard it outright, or at least be sure that the handling does not leave the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} in an inconsistent state (say, the same \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} is removed twice ...) and, hopefully, that no excessive cost is incurred for re-\/handling what is basically the same \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}}. This should not be a problem because, basically, a specialized \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} will use the PR, and therefore only consider P\+Mod, while a general-\/purpose \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} will use the AR, and therefore only consider A\+Mod.

A relevant consequence of this, however, is that if a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} receives a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} that it does not \char`\"{}understand\char`\"{}, it may be allowed to ignore it. This is in particular true for a general-\/purpose \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} using the AR, which can assume that any \char`\"{}unknown\char`\"{} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} is a P\+Mod, and that one or more A\+Mod is still in (or has already been extracted from) the queue that describe the same changes.

However, a general-\/purpose \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} using the AR may want to directly modify the AR of a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}. When the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} receives an A\+Mod (associated with the AR), it must update its PR; hence, it also has to issue one (or more) P\+Mod representing the same change. In the previous example of the Knapsack\+Block, a general-\/purpose \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} may change the coefficient in the linear constraint; the Knapsack\+Block should then modify its PR accordingly, and issue the corresponding P\+Mod.

As a consequence, in general an A\+Mod must be constructed and passed to the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} whenever the AR changes, even if there is no \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} \char`\"{}listening\char`\"{} to it (either directly or to any ancestor), because the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} has anyway to update its PR; of course, if there is no \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} listening then no P\+Mod will be issued (but the PR will be changed), and the original A\+Mod will not be passed up.

However, this gives rise to an issue. Assume a \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, say our fictional Knapsack\+Block, has a method in its specific interface to change the weight of an item. This method must modify both the PR and the AR of the \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} (if the latter is constructed), which means that both a P\+Mod and an A\+Mod will be issued. However, when the A\+Mod will reaches the \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, the latter should in principle change its PR accordingly; this is wasted work, as the PR is already in synch with the AR, and may give rise to issues in cases when multiple A\+Mod/\+P\+Mod are issued as a consequence of a single change. This is why \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} has the method \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification_a22fe0cccfc755cfd89b240587d1f1cad}{concerns\+\_\+\+Block()}}. This method is intended to return true if the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} \char`\"{}has not been seen by the
\+Block already\char`\"{}, i.\+e., it has not been issued by the \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} itself while modifying its PR. When a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} is issued by \char`\"{}someone other than the
\+:\+Block\char`\"{} (say, a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}}), and therefore the \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} is not already aware of the corresponding changes, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification_a22fe0cccfc755cfd89b240587d1f1cad}{concerns\+\_\+\+Block()}} should return true. If, instead, a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} is issued by the \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, then \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification_a22fe0cccfc755cfd89b240587d1f1cad}{concerns\+\_\+\+Block()}} should return false. Of course, the object actually issuing the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} (\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}}, ...) may not be aware of which of the two cases is, which is why all methods that result in changes that issue an A\+Mod must have a parameter that controls that return value. Note that the base \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} class always returns false\+: this is typically the right behavior for P\+Mod, which are directly issued by the \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} and that therefore can be of no interest for it. The derived class \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_a_modification}{A\+Modification}} is defined which just allows to set the value returned by the method\+: typically, A\+Mods should derive from \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_a_modification}{A\+Modification}}.

Note that a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} may be unwilling to accept some A\+Mod, e.\+g. because the corresponding P\+Mod may be too complex to handle. All \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} should clearly define the set of A\+Mod that they handle, and the user should be careful to avoid any change that results in an unsupported A\+Mod, for that would typically result in an exception being thrown.

Complex cases may occur in which a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} uses partly the AR and partly the PR of a block; in this case, the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} will have to handle both A\+Mod and P\+Mod. However, such a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} will by necessity be specific for a given \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, and therefore it will know exactly how the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} reacts to changes; this should make it possible to handle both types of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} avoiding problems with \char`\"{}duplicates\char`\"{}. This could actually happen frequently enough, because some kinds of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} may be seen as being both a A\+Mod and a P\+Mod. These are in particular those concerning a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}, since the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} are a necessary part of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}, and hence in some sense belonging both to the AR and to the PR.

All this having been said, a number of general remarks on how \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} should be organized, issued and reacted to are in order\+:


\begin{DoxyEnumerate}
\item A \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} typically says {\itshape what} has changed but not (necessarily) {\itshape how}. For instance, a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} changing, say, the R\+HS of a \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}, would in general indicate \char`\"{}the R\+H\+S has changed\char`\"{} but {\itshape not} report the new value of the R\+HS. When a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} (and/or a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} managing this A\+Mod to keep its PR in synch) handles this \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}}, it will have to access the \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} to retrieve the {\itshape current} value of the R\+HS from there. Note that likely the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} / \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} is keeping some information \char`\"{}equivalent\char`\"{} to the value that the (say) R\+HS had before the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} happened, and can therefore \char`\"{}see the difference\char`\"{} (e.\+g., check if the R\+HS has in fact been set to exactly the same value that is had before, so that the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} is actually \char`\"{}void\char`\"{}).
\item As a consequence of the previous point,

W\+H\+EN T\+HE M\+O\+D\+I\+F\+I\+C\+A\+T\+I\+ON IS I\+S\+S\+U\+ED, T\+HE C\+H\+A\+N\+GE M\+U\+ST BE D\+O\+NE A\+L\+R\+E\+A\+DY

In fact, at the moment in which add\+\_\+\+Modification() is called, control is passed to the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_observer}{Observer}} / \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} (and ultimately, possibly, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}}) that receives it. This object may {\itshape immediately} access the changed object to retrieve its new state, and therefore the state at the moment in which the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} is \char`\"{}physically issued\char`\"{} (i.\+e., add\+\_\+\+Modification() is called) should be \char`\"{}ready\char`\"{}.
\item However, \begin{DoxyVerb}MODIFICATION ARE "ASYNCHRONOUS" OBJECTS
\end{DoxyVerb}


Indeed, the rationale of Modificaton is that they be processed in a \char`\"{}lazy\char`\"{} way, possibly \char`\"{}a long time after they have been issued\char`\"{}. The result is that \begin{DoxyVerb}THE STATE OF THE Block WHEN THE Modification IS PROCESSED CAN
BE VERY DIFFERENT FROM THAT WHEN THE Modification WAS ISSUED
\end{DoxyVerb}


In the same example as before, it may well happen that the R\+HS of the same \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} is changed several time before a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} is asked to solve the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} again. This means that in the list of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} there might be several \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}}; yet, at the moment in which the {\itshape first} one is processed, the R\+HS is set to the {\itshape current} value, i.\+e., that which in fact correspond to the {\itshape last} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}}. The net result is that all the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} apart from the first \char`\"{}do
   nothing\char`\"{}. It is the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}}\textquotesingle{}s responsibility to ensure that this does not create problems, and hopefully to recognise this and basically \char`\"{}ignoring\char`\"{} all the \char`\"{}void\char`\"{} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} with low computational cost.
\item Ensuring that a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}} issued when the state of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} was different can still be meaningfully processed by using its current state can be delicate. This is in particular true when dealing with {\itshape dynamic} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} / \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} of a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}.
