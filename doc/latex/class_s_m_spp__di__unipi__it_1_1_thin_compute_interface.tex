\subsection{Detailed Description}
abstract base class for any S\+M\+S++ object with a computational part 

Several objects in S\+M\+S++ can (but do not necessarily) have a significant computational component, i.\+e., some operations are computationally demanding and therefore require being dealt with care\+:


\begin{DoxyItemize}
\item the operations have parameters (possibly, many and complex) determining how exactly they are performed;
\item the operations may not necessarily suceed, especially if only allowed a limited the amount of computational resources (which may be done by setting some of the above parameters);
\item the computation may depend on the value of some set of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}, and a (simple) mechanism is provided for knowing whether the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} have or not changed their value since the last call without having to check this explicitly;
\item the operations may be performed asyncronously on a different thread (although this aspect is not treated yet, and left for a future revision of the class).
\end{DoxyItemize}

Objects with this behaviour are (obviously) \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} \mbox{[}see \mbox{\hyperlink{_solver_8h}{Solver.\+h}}\mbox{]}, but also possibly \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} \mbox{[}see \mbox{\hyperlink{_function_8h}{Function.\+h}}\mbox{]}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} \mbox{[}see \mbox{\hyperlink{_constraint_8h}{Constraint.\+h}}\mbox{]} and \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}} \mbox{[}see \mbox{\hyperlink{_objective_8h}{Objective.\+h}}\mbox{]}. The link between these is obvious enough\+: \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} and \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}} may well be implemented in terms of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}}, and evaluating a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} may well be a computationally demanding task, up to requiring a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}}. Yet, not all \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} (and hence, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} and \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}}) are computationally heavy enough to warrant such a complex interface, and although likely most \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} are, there might be \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} that have low enough complexity to allow foregoing it.

The {\itshape abstract} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface}{Thin\+Compute\+Interface}} class is meant to factor out many of the methods required to deal with these aspects. Factoring them is primarily meant to avoid un-\/necessary code duplication and to ensure consistency between similar parts of the interface of different objects, although there is (currently) no planned direct use of the fact that the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} and \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}} classes then have a common ancestor.

The interface is \char`\"{}thin\char`\"{} in the sense that {\itshape almost} all the methods are either pure virtual, or are given a thin default implementation suiting the case where the computational cost of the object is low. The idea is that the actual implementation of the methods is deferred until towards the end of the derivatiobn chain, so that classes that do not have a computational cost warranting the complex interface (say, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_linear_function}{Linear\+Function}}) do not have to pay any implementation cost for features that are not justified. The exception to this rule is the definition of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_compute_config}{Compute\+Config}} class and the methods for reading and writing a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_compute_config}{Compute\+Config}}; these can be implemented using the abstract part of the interface, and therefore potentially need to be implemented only once.

A reason for introducing the class at this point of the design cycle is that S\+M\+S++ will eventually have to cater for asyncronous calls, which is going to be expecially important for the computationally-\/heavy objects that \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface}{Thin\+Compute\+Interface}} targets. However, how this is to be accomplished is not decided yet. By factoring all aspects of the computational interface into a single class, the effort to later refactor the interfaces to allow for asyncronous calls should be decreased.

\subsubsection{\texorpdfstring{compute()}{compute()}}
{\footnotesize\ttfamily virtual int compute (\begin{DoxyParamCaption}\item[{bool}]{changedvars = {\ttfamily true} }\end{DoxyParamCaption})\hspace{0.3cm}{\ttfamily [pure virtual]}}



(try to) compute whatever the object is supposed to 

Starts or the computation process, or restarts a previously interrupted computation process, and returns the status of the solver at termination.

The return code indicates the status of the computation; it is expected to follow the rules set by compute\+\_\+type \mbox{[}see above\mbox{]}, but it is a generic int so that derived classes can add their own specific return codes.

The computation can be expected to be (although it is not necessarily) costly, i.\+e., it can take \char`\"{}a lot of time\char`\"{}. It is therefore necessary to clarify what \char`\"{}can happen while the computation in underway\char`\"{}, in particular considering the multi-\/threaded scenario. In principle, the object doing the computation may undergo changes, which however can be of two different types\+:


\begin{DoxyItemize}
\item \char`\"{}\+Normal\char`\"{} changes which happen in the object (\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}}, ...) and/or in the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} it is attached to (\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}}), which the object either \char`\"{}knows directly\char`\"{} (as they happen at it) or is properly notified (by an appropriate \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}}).
\item In addition, for all objects that share the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface}{Thin\+Compute\+Interface}} interface the computation depends, among other things, from a set of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}. For \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}} and \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}} these are the \char`\"{}active\char`\"{} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}, while for \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}}, these are the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} in the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}} of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} it is attached to which do not belong to the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} itself, and therefore have to be treated as constrants when the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} is solved. These may change their value, but there is no mechanism that signals any abject if such a change has occurred.
\end{DoxyItemize}

During the execution of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface_a00fd6363d98ea46bcc273842b327d050}{compute()}}, any of these may in principle occur\+: either because of another thread working on the same objects, or because the computation itself triggers some complex chain of events resulting in a change. However, the changes may affect the result of the computation, which could therefore be no longer correct for the state of the object at the beginning of the call, but only for that at the end (and note that there may be no bound on the number of changes which may occurr in the meantime). The point is whether this is allowed to happen, and the general answer is \char`\"{}no\char`\"{}. That is, the rule is that

during a call to \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface_a00fd6363d98ea46bcc273842b327d050}{compute()}}, no changes must occur to the object (say, the whole \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} to which the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}} is attached to) which change the answer that \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface_a00fd6363d98ea46bcc273842b327d050}{compute()}} is supposed to compute

The rule leaves scope for some changes occurring, although these must ensure that the answer is not affected. Changes of this type include generation of valid inequalities/lazy constraints/dynamic variables in a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}} (being solved by a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_solver}{Solver}}), as these are supposed not to change the optimal solution of the underlying problem. Note that, however, \begin{DoxyVerb}          IT IS UNIQUELY THE CALLER'S RESPONSIBILITY
            TO ENSURE THAT THE RULE IS RESPECTED
\end{DoxyVerb}


This should always be possible, if necessary by making copies of the objects (e.\+g., via an R3 \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_block}{Block}}). The object doing \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface_a00fd6363d98ea46bcc273842b327d050}{compute()}} is {\itshape not} required to check for violation of the rules, as this might be complex and/or computational costly. This is for instance true for the abrupt change of the value of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}, which would require keeping a copy of the initial value and periodic checks. Other changes may be easier to detect, e.\+g. because they are conveyed by a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}}. It is therefore possible (and, potentially, advised) for an object to check for such an occurrence and react by immediately terminating computation returning a k\+Error status (or any more specific status $>$ k\+Error), but this is not required and left to each specific object to decide.

The parameter changedvars is meant to cater for a similar occurrence happening not inside a single call to \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface_a00fd6363d98ea46bcc273842b327d050}{compute()}}, but between two consecutive ones. The point is that when \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface_a00fd6363d98ea46bcc273842b327d050}{compute()}} is called, it may be for restarting a previously started computation process that has been temporarily interrupted. If no changes occurred in the object, this should be \char`\"{}very easy\char`\"{}\+: just \char`\"{}jump in the main loop where you exited it,
and continue as if nothing had happened\char`\"{} (this is provided the state of the solution process is properly preserved, which is usually the case). Otherwise, the computation may have to be significantly reshaped\+: in the best case reoptimization techniques can be used to warm-\/start the new one using results from the old one, but in some cases there could be no other resort than restarting everything from scratch.

Hence, each time \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface_a00fd6363d98ea46bcc273842b327d050}{compute()}} is called and a previous state is available, the object will have to decide how to make best use of it. This depends on whether or not there were changes in the object. As previously mentioned, there are two types of changes\+: those that are surely \char`\"{}known\char`\"{} to the object (either because they occurred in a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_constraint}{Constraint}}, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_objective}{Objective}} or \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_function}{Function}}, or because are properly signalled by an appropriate \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_modification}{Modification}}), and the changes of the value of the relevant \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}}. The only way to know whether the latter has happened would be to read the value (whatever that is) and to compare it with the previous one, which in turn would imply having kept a copy of the latter, which is typically not done (see the general rule above).

The changedvars parameters is here to solve this issue. If it is true, then the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface_a00fd6363d98ea46bcc273842b327d050}{compute()}} method is allowed to assume that the value of the relevant \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} (if any) has not changed since the last call. This therefore allows the object to \char`\"{}resume the computation where it started\char`\"{}, provided of course that no other changes of different type occurred. Note that this is actually providing the object with the {\itshape guarantee} that the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} have not changed\+: thus, \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface_a00fd6363d98ea46bcc273842b327d050}{compute()}} can read the current value of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_variable}{Variable}} and be guaranteed that it is the same as it was previously, directly extending the general rule valid within one call to \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface_a00fd6363d98ea46bcc273842b327d050}{compute()}} to possibly arbitrarily long sequences of calls. As for the general rule, it is uniquely the caller\textquotesingle{}s responsibility to ensure that the property holds, as the object will typically not have the means for checking it (and anyway are not required to).

If changedvars == false instead, the object has to assume that the relevant variables have changed. If it is important for the object to detect which ones have changed and which ones have not, it will have to implement this check internally. This implies keeping a copy of the previous values, which is what the global rule avoids being required to do, but that clearly the global rule does not forbid doing.

set the whole set of parameters in one blow 

This method sets the whole set of parameters in one blow using a \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_compute_config}{Compute\+Config}} object.

Although the class is thin, this method is given a working configuration using the class interface; hence, derived classes correctly implementing \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface_a73669f587bb938b587c54ad7e73ec297}{set\+\_\+par()}} (all the required versions), get\+\_\+num\+\_\+$\ast$\+\_\+par(), get\+\_\+dflt\+\_\+$\ast$\+\_\+par() and $\ast$\+\_\+par\+\_\+str2idx() can in principle avoid to re-\/implement it.

Note that the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_compute_config}{Compute\+Config}} in principle only contains a subset of the possible parameters. The way in which the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_compute_config}{Compute\+Config}} must be \char`\"{}interpreted\char`\"{} depends on the f\+\_\+diff field in there\+: if f\+\_\+diff == true then all the other parameters are left unchanged, while if f\+\_\+diff == false then all the parameters that are {\itshape not} specified in the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_compute_config}{Compute\+Config}} are rather reset to their default value. Note that for a \char`\"{}fresh\char`\"{} (just constructed) object, the two values of f\+\_\+diff are equivalent. Since calling set\+\_\+\+Compute\+Config( nullptr ) would not make sense if the \char`\"{}empty\char`\"{} \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_compute_config}{Compute\+Config}} were intended in the differential sense (it would do nothing), when scfg == nullptr the field f\+\_\+diff should be interpreted as false, which \char`\"{}resets the object to its factory defaults\char`\"{} (hence calling set\+\_\+\+Compute\+Config( nullptr ) on a \char`\"{}fresh\char`\"{} object makes little sense). Note that in the base \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface}{Thin\+Compute\+Interface}} class implementation this is obtained by just calling \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface_a73669f587bb938b587c54ad7e73ec297}{set\+\_\+par()}} for all parameters, resetting them to default values, and then calling it again on the parameters specified in the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_compute_config}{Compute\+Config}} (if any); if this has negative performance impacts on a given \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface}{Thin\+Compute\+Interface}}, it will have to re-\/implement its version of the method.

The above is already reason enough for the method to be virtual, but not the only one. For instance, derived classes may need to do something to react to changes of the parameters which is different from what is done when they are individually changed. A particularly simple case is when the \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface}{Thin\+Compute\+Interface}} formally has some parameters but in fact it \char`\"{}listens to no-\/one\char`\"{}, in which case the implementation does not need to do anything. Conversely, the implementation in the base class does not use the f\+\_\+extra\+\_\+\+Configuration field of the \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_compute_config}{Compute\+Config}}, so any \+:\mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_thin_compute_interface}{Thin\+Compute\+Interface}} which needs it will have to derive its own version of the method (but, not necessarily of \mbox{\hyperlink{class_s_m_spp__di__unipi__it_1_1_compute_config}{Compute\+Config}}).
