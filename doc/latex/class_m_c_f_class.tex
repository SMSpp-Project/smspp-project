\subsection*{Public Types}
\begin{Indent}\textbf{ Public types}\par
{\em The \mbox{\hyperlink{class_m_c_f_class}{M\+C\+F\+Class}} defines four main public types\+:


\begin{DoxyItemize}
\item Index, the type of arc and node indices;
\item F\+Number, the type of flow variables, arc capacities, and node deficits;
\item C\+Number, the type of flow costs, node potentials, and arc reduced costs;
\item F\+O\+Number, the type of objective function value.
\end{DoxyItemize}

By re-\/defining the types in this section, most M\+C\+F\+Solver should be made to work with any reasonable choice of data type (= one that is capable of properly representing the data of the instances to be solved). This may be relevant due to an important property of M\+CF problems\+: {\itshape if all arc capacities and node deficits are integer, then there exists an integral optimal primal solution}, and {\itshape if all arc costs are integer, then there exists an integral optimal dual solution}. Even more importantly, {\itshape many solution algorithms will in fact produce an integral primal/dual solution for free}, because {\itshape every primal/dual solution they generate during the solution process is naturally integral}. Therefore, one can use integer data types to represent everything connected with flows and/or costs if the corresponding data is integer in all instances one needs to solve. This directly translates in significant memory savings and/or speed improvements.

It is the user\textquotesingle{}s responsibility to ensure that these types are set to reasonable values$\ast$. So, the experienced user may want to experiment with setting this data properly if memory footprint and/or speed is a primary concern. Note, however, that {\itshape not all solution algorithms will happily accept integer data}; one example are Interior-\/\+Point approaches, which require both flow and cost variables to be continuous (float). So, the viability of setting integer data (as well as its impact on performances) is strictly related to the specific kind of algorithm used. Since these types are common to all derived classes, they have to be set taking into account the needs of all the solvers that are going to be used, and adapting to the \char`\"{}worst case\char`\"{}; of course, F\+Number == C\+Number == double is going to always be an acceptable \char`\"{}worst case\char`\"{} setting. \mbox{\hyperlink{class_m_c_f_class}{M\+C\+F\+Class}} may in a future be defined as a template class, with these as template parameters, but this is currently deemed overkill and avoided.

Finally, note that the above integrality property only holds for {\itshape linear} M\+CF problems. If any arc has a nonzero quadratic cost coefficient, optimal flows and potentials may be fractional even if all the data of the problem (comprised quadratic cost coefficients) is integer. Hence, for {\itshape quadratic} M\+CF solvers, a setting like F\+Number == C\+Number == double is actually mandatory$\ast$, for any reasonable algorithm will typically misbehave otherwise. }\begin{DoxyCompactItemize}

\subsection{Detailed Description}
This abstract base class defines a standard interface for (linear or convex quadartic separable) Min Cost Flow (M\+CF) problem solvers.

The data of the problem consist of a (directed) graph G = ( N , A ) with n = $\vert$\+N$\vert$ nodes and m = $\vert$\+A$\vert$ (directed) arcs. Each node `i' has a deficit b\mbox{[} i \mbox{]}, i.\+e., the amount of flow that is produced/consumed by the node\+: source nodes (which produce flow) have negative deficits and sink nodes (which consume flow) have positive deficits. Each arc `(i, j)' has an upper capacity U\mbox{[} i , j \mbox{]}, a linear cost coefficient C\mbox{[} i , j \mbox{]} and a (non negative) quadratic cost coefficient Q\mbox{[} i , j \mbox{]}. Flow variables X\mbox{[} i , j \mbox{]} represents the amount of flow to be sent on arc (i, j). Parallel arcs, i.\+e., multiple copies of the same arc `(i, j)' (with possibily different costs and/or capacities) are in general allowed. The formulation of the problem is therefore\+: \[ \min \sum_{ (i, j) \in A } C[ i , j ] X[ i, j ] + Q[ i , j ] X[ i, j ]^2 / 2 \] \[ (1) \sum_{ (j, i) \in A } X[ j , i ] - \sum_{ (i, j) \in A } X[ i , j ] = b[ i ] \hspace{1cm} i \in N \] \[ (2) 0 \leq X[ i , j ] \leq U[ i , j ] \hspace{1cm} (i, j) \in A \] The n equations (1) are the flow conservation constraints and the 2m inequalities (2) are the flow nonnegativity and capacity constraints. At least one of the flow conservation constraints is redundant, as the demands must be balanced ( $\sum_{ i \in N } b[ i ] = 0$); indeed, exactly n -\/ Connected\+Components( G ) flow conservation constraints are redundant, as demands must be balanced in each connected component of G. Let us denote by QA and LA the disjoint subsets of A containing, respectively, \char`\"{}quadratic\char`\"{} arcs (with Q\mbox{[} i , j \mbox{]} $>$ 0) and \char`\"{}linear\char`\"{} arcs (with Q\mbox{[} i , j \mbox{]} = 0); the (M\+CF) problem is linear if QA is empty, and nonlinear (convex quadratic) if QA is nonempty.

The dual of the problem is\+: \[ \max \sum_{ i \in N } Pi[ i ] b[ i ] - \sum_{ (i, j) \in A } W[ i , j ] U[ i , j ] - \sum_{ (i, j) \in AQ } V[ i , j ]^2 / ( 2 * Q[ i , j ] ) \] \[ (3.a) C[ i , j ] - Pi[ j ] + Pi[ i ] + W[ i , j ] - Z[ i , j ] = 0 \hspace{1cm} (i, j) \in AL \] \[ (3.b) C[ i , j ] - Pi[ j ] + Pi[ i ] + W[ i , j ] - Z[ i , j ] = V[ i , j ] \hspace{1cm} (i, j) \in AQ \] \[ (4.a) W[ i , j ] \geq 0 \hspace{1cm} (i, j) \in A \] \[ (4.b) Z[ i , j ] \geq 0 \hspace{1cm} (i, j) \in A \]

Pi\mbox{[}\mbox{]} is said the vector of node potentials for the problem, W\mbox{[}\mbox{]} are bound variables and Z\mbox{[}\mbox{]} are slack variables. Given Pi\mbox{[}\mbox{]}, the quantities \[ RC[ i , j ] = C[ i , j ] + Q[ i , j ] * X[ i , j ] - Pi[ j ] + Pi[ i ] \] are said the \char`\"{}reduced costs\char`\"{} of arcs.

A primal and dual feasible solution pair is optimal if and only if the complementary slackness conditions \[ RC[ i , j ] > 0 \Rightarrow X[ i , j ] = 0 \] \[ RC[ i , j ] < 0 \Rightarrow X[ i , j ] = U[ i , j ] \] are satisfied for all arcs (i, j) of A.

The \mbox{\hyperlink{class_m_c_f_class}{M\+C\+F\+Class}} class provides an interface with methods for managing and solving problems of this kind. Actually, the class can also be used as an interface for more general Non\+Linear M\+CF problems, where the cost function either nonseparable ( C( X ) ) or arc-\/separable ( $\sum_{ (i, j) \in A } C_{i,j}( X[ i, j ] )$ ). However, solvers for Non\+Linear M\+CF problems are typically objective-\/function-\/specific, and there is no standard way for inputting a nonlinear function different from a separable convex quadratic one, so only the simplest form is dealt with in the interface, leaving more complex Non\+Linear parts to the interface of derived classes.

Constructor of the class.

nmx and mmx, if provided, are taken to be respectively the maximum number of nodes and arcs in the network. If nonzero values are passed, memory allocation can be anticipated in the constructor, which is sometimes desirable. The maximum values are stored in the protected fields nmax and mmax, and can be changed with \mbox{\hyperlink{class_m_c_f_class_a8d82d26f7845eb69081c860e14c3dc4c}{Load\+Net()}} \mbox{[}see below\mbox{]}; however, changing them typically requires memory allocation/deallocation, which is sometimes undesirable outside the constructor.

After that an object has been constructed, no problem is loaded; this has to be done with \mbox{\hyperlink{class_m_c_f_class_a8d82d26f7845eb69081c860e14c3dc4c}{Load\+Net()}} \mbox{[}see below\mbox{]}. Thus, it is an error to invoke any method which requires the presence of a problem (typicall all except those in the initializations part). The base class provides two protected fields n and m for the current number of nodes and arcs, respectively, that are set to 0 in the constructor precisely to indicate that no instance is currently loaded. \mbox{\Hypertarget{class_m_c_f_class_a93c0882740d38b9f8eb05994a01f76b7}\label{class_m_c_f_class_a93c0882740d38b9f8eb05994a01f76b7}}

\subsubsection{\texorpdfstring{Load\+D\+M\+X()}{LoadDMX()}}
{\footnotesize\ttfamily void Load\+D\+MX (\begin{DoxyParamCaption}\item[{istream \&}]{D\+M\+Xs,  }\item[{bool}]{Is\+Quad = {\ttfamily false} }\end{DoxyParamCaption})\hspace{0.3cm}{\ttfamily [inline]}, {\ttfamily [virtual]}}

Read a M\+CF instance in D\+I\+M\+A\+CS standard format from the istream. The format is the following. The first line must be

p min $<$number of=\char`\"{}\char`\"{} nodes$>$=\char`\"{}\char`\"{}$>$ $<$number of=\char`\"{}\char`\"{} arcs$>$=\char`\"{}\char`\"{}$>$

Then the node definition lines must be found, in the form

n $<$node number$>$=\char`\"{}\char`\"{}$>$ $<$node supply$>$=\char`\"{}\char`\"{}$>$

Not all nodes need have a node definition line; these are given zero supply, i.\+e., they are transhipment nodes (supplies are the inverse of deficits, i.\+e., a node with positive supply is a source node). Finally, the arc definition lines must be found, in the form

a $<$start node$>$=\char`\"{}\char`\"{}$>$ $<$end node$>$=\char`\"{}\char`\"{}$>$ $<$lower bound$>$=\char`\"{}\char`\"{}$>$ $<$upper bound$>$=\char`\"{}\char`\"{}$>$ $<$flow cost$>$=\char`\"{}\char`\"{}$>$

There must be exactly $<$number of=\char`\"{}\char`\"{} arcs$>$=\char`\"{}\char`\"{}$>$ arc definition lines in the file.

This method is {\itshape not} pure virtual because an implementation is provided by the base class, using the \mbox{\hyperlink{class_m_c_f_class_a8d82d26f7845eb69081c860e14c3dc4c}{Load\+Net()}} method (which {\itshape is} pure virtual). However, the method {\itshape is} virtual to allow derived classes to implement more efficient versions, should they have any reason to do so.

\begin{DoxyNote}{Note}
Actually, the file format accepted by Load\+D\+MX (at least in the base class implementation) is more general than the D\+I\+M\+A\+CS standard format, in that it is allowed to mix node and arc definitions in any order, while the D\+I\+M\+A\+CS file requires all node information to appear before all arc information.

Other than for the above, this method is assumed to allow for quadratic$\ast$ Dimacs files, encoding for convex quadratic separable Min Cost Flow instances. This is a simple extension where each arc descriptor has a sixth field, $<$quadratic cost$>$=\char`\"{}\char`\"{}$>$. The provided istream is assumed to be quadratic Dimacs file if Is\+Quad is true, and a regular linear Dimacs file otherwise. 
\end{DoxyNote}

Inputs a new network.

The parameters nmx and mmx are the new max number of nodes and arcs, possibly overriding those set in the constructor \mbox{[}see above\mbox{]}, altough at the likely cost of memory allocation and deallocation. Passing nmx == mmx == 0 is intended as a signal to the solver to deallocate everything and wait for new orders; in this case, all the other parameters are ignored.

Otherwise, in principle all the other parameters have to be provided. Actually, some of them may not be needed for special classes of M\+CF problems (e.\+g., costs in a Max\+Flow problem, or start/end nodes in a problem defined over a graph with fixed topology, such as a complete graph). Also, passing 0 is allowed to set default values.

The meaning of the parameters is the following\+:


\begin{DoxyItemize}
\item pn is the current number of nodes of the network ($<$= nmax).
\item pm is the number of arcs of the network ($<$= mmax).
\item pU is the m-\/vector of the arc upper capacities; capacities must be nonnegative, but can in principle be infinite (== F\+\_\+\+I\+NF); passing pU == 0 means that all capacities are infinite;
\item pC is the m-\/vector of the arc costs; costs must be finite ($<$ C\+\_\+\+I\+NF); passing pC == 0 means that all costs must be 0.
\item p\+Dfct is the n-\/vector of the node deficits; source nodes have negative deficits and sink nodes have positive deficits; passing p\+Dfct == 0 means that all deficits must be 0 (a circulation problem);
\item p\+Sn is the m-\/vector of the arc starting nodes; p\+Sn == 0 is in principle not allowed, unless the topology of the graph is fixed;
\item p\+En is the m-\/vector of the arc ending nodes; same comments as for p\+Sn.
\end{DoxyItemize}

Note that node \char`\"{}names\char`\"{} in the arrays p\+Sn and p\+En must go from 1 to pn if the macro U\+S\+A\+N\+A\+M\+E0 \mbox{[}see above\mbox{]} is set to 0, while they must go from 0 to pn -\/ 1 if U\+S\+A\+N\+A\+M\+E0 is set to 1. In both cases, however, the deficit of the first node is read from the first (0-\/th) position of p\+Dfct, that is if U\+S\+A\+N\+A\+M\+E0 == 0 then the deficit of the node with name `i' is read from p\+Dfct\mbox{[} i -\/ 1 \mbox{]}.

The data passed to \mbox{\hyperlink{class_m_c_f_class_a8d82d26f7845eb69081c860e14c3dc4c}{Load\+Net()}} can be used to specify that the arc `i' must not \char`\"{}exist\char`\"{} in the problem. This is done by passing pC\mbox{[} i \mbox{]} == C\+\_\+\+I\+NF; solvers which don\textquotesingle{}t read costs are forced to read them in order to check this, unless they provide alternative solver-\/specific ways to accomplish the same tasks. These arcs are \char`\"{}closed\char`\"{}, as for the effect of \mbox{\hyperlink{class_m_c_f_class_ae1c33ba491b57343fbc157123fff5b11}{Close\+Arc()}} \mbox{[}see below\mbox{]}. \char`\"{}invalid\char`\"{} costs (== C\+\_\+\+I\+NF) are set to 0 in order to being subsequently capable of \char`\"{}opening\char`\"{} them back with \mbox{\hyperlink{class_m_c_f_class_ab902a23d1c9520a22b79de5d451c3348}{Open\+Arc()}} \mbox{[}see below\mbox{]}. The way in which these non-\/existent arcs are phisically dealt with is solver-\/specific; in some solvers, for instance, this could be obtained by simply putting their capacity to zero. Details about these issues should be found in the interface of derived classes.

Note that the quadratic part of the objective function, if any, is not dealt with in \mbox{\hyperlink{class_m_c_f_class_a8d82d26f7845eb69081c860e14c3dc4c}{Load\+Net()}}; it can only be separately provided with \mbox{\hyperlink{class_m_c_f_class_a4aa1d49c3edafbf4783d579d175070fd}{Chg\+Q\+Coef()}} \mbox{[}see below\mbox{]}. By default, the problem is linear, i.\+e., all coefficients of the second-\/order terms in the objective function are assumed to be zero.

{\footnotesize\ttfamily virtual void M\+C\+F\+Put\+State (\begin{DoxyParamCaption}\item[{\mbox{\hyperlink{class_m_c_f_class_ab547218814e3b90d15f219f5aaf8b937}{M\+C\+F\+State\+Ptr}}}]{S }\end{DoxyParamCaption})\hspace{0.3cm}{\ttfamily [inline]}, {\ttfamily [virtual]}}

Restore the solver to the state in which it was when the state `S' was created with \mbox{\hyperlink{class_m_c_f_class_a995a05ecaa6ece4be3afbddbb36b2c4e}{M\+C\+F\+Get\+State()}} \mbox{[}see above\mbox{]}.

The typical use of this method is the following\+: a M\+CF problem is solved and the \char`\"{}optimal state\char`\"{} is set aside. Then the problem changes and it is re-\/solved. Then, the problem has to be changed again to a form that is close to the original one but rather different from the second one (think of a long backtracking in a Branch \& Bound) to which the current \char`\"{}state\char`\"{} referes. Then, the old optimal state can be expected to provide a better starting point for reoptimization \mbox{[}see Re\+Optimize() below\mbox{]}.

Note, however, that the state is only relative to the optimization process, i.\+e., this operation is meaningless if the data of the problem has changed in the meantime. So, if a state has to be used for speeding up reoptimization, the following has to be done\+:


\begin{DoxyItemize}
\item first, the data of the solver is brought back to {\itshape exactly} the same as it was at the moment where the state `S' was created (prior than this operation a Re\+Optimize( false ) call is probably advisable);
\item then, \mbox{\hyperlink{class_m_c_f_class_ac14589cd80aed231b6fc7da247f50601}{M\+C\+F\+Put\+State()}} is called (and Re\+Optimize( true ) is called);
\item only afterwards the data of the problem is changed to the final state and the problem is solved.
\end{DoxyItemize}

A \char`\"{}put state\char`\"{} operation does not \char`\"{}deplete\char`\"{} the state, which can therefore be used more than once. Indeed, a state is constructed inside the solver for each call to \mbox{\hyperlink{class_m_c_f_class_a995a05ecaa6ece4be3afbddbb36b2c4e}{M\+C\+F\+Get\+State()}}, but the solver never deletes statuses; this has to be done on the outside when they are no longer needed (the solver must be \char`\"{}resistent\char`\"{} to deletion of the state at any moment).

Since not all the M\+CF solvers reoptimize (efficiently enough to make these operations worth), an \char`\"{}empty\char`\"{} implementation that does nothing is provided by the base class. \mbox{\Hypertarget{class_m_c_f_class_acd08873d1e15db41bf42648226f8feb1}\label{class_m_c_f_class_acd08873d1e15db41bf42648226f8feb1}}

Extract a smaller/easier equivalent M\+CF problem. The data of the instance is changed and the easier one is solved instead of the original one. In the M\+CF case, preprocessing may involve reducing bounds, identifying disconnected components of the graph etc. However, proprocessing is solver-\/specific.

This method can be implemented by derived classes in their solver-\/specific way. Preprocessing may reveal unboundedness or unfeasibility of the problem; if that happens, \mbox{\hyperlink{class_m_c_f_class_a0554708d9abb0e079a8d6f073def9bab}{Pre\+Process()}} should properly set the `status' field, that can then be read with \mbox{\hyperlink{class_m_c_f_class_a333e27ad7a73779b096cb70829cbe8be}{M\+C\+F\+Get\+Status()}} \mbox{[}see below\mbox{]}.

Note that preprocessing may destroy all the solution information. Also, it may be allowed to change the data of the problem, such as costs/capacities of the arcs.

A valid preprocessing is doing nothing, and that\textquotesingle{}s what the default implementation of this method (that is {\itshape not} pure virtual) does. \mbox{\Hypertarget{class_m_c_f_class_a5441232979a0ac98410d765b04830eeb}\label{class_m_c_f_class_a5441232979a0ac98410d765b04830eeb}}

Write the current M\+CF problem to an ostream. This may be useful e.\+g. for debugging purposes.

The base \mbox{\hyperlink{class_m_c_f_class}{M\+C\+F\+Class}} class provides output in two different formats, depending on the value of the parameter frmt\+:


\begin{DoxyItemize}
\item k\+Dimacs the problem is written in D\+I\+M\+A\+CS standard format, read by most M\+CF codes available;
\item k\+M\+PS the problem is written in the \char`\"{}modern version\char`\"{} (tab-\/separated) of the M\+PS format, read by most L\+P/\+M\+IP solvers;
\begin{DoxyItemize}
\item k\+F\+W\+M\+PS the problem is written in the \char`\"{}old version\char`\"{} (fixed width fields) of the M\+PS format; this is read by most L\+P/\+M\+IP solvers, but some codes still require the old format.
\end{DoxyItemize}
\end{DoxyItemize}

The implementation of \mbox{\hyperlink{class_m_c_f_class_acd008d9548bf3e1aef1291864171bb2d}{Write\+M\+C\+F()}} in the base class uses all the above methods for reading the data; as such it will work for any derived class that properly implements this part of the interface, but it may not be very efficient. Thus, the method is virtual to allow the derived classes to either re-\/implement \mbox{\hyperlink{class_m_c_f_class_acd008d9548bf3e1aef1291864171bb2d}{Write\+M\+C\+F()}} for the above two formats in a more efficient way, and/or to extend it to support other solver-\/specific formats.

\begin{DoxyNote}{Note}
None of the above two formats supports quadratic M\+C\+Fs, so if nonzero quadratic coefficients are present, they are just ignored. 
\end{DoxyNote}
