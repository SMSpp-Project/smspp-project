\section{Introduction}

This document describes the format of input files for the \SMSpp components of the \textsc{plan4res} project. These are the components tasked with performing the actual solution of the different optimization problems involved in the process. The production of these files possibly requires:
%
\begin{itemize}
 \item a sophisticated data extraction and preparation phase;
 %
 \item a tuning phase aimed at finding appropriate parameters for the different modelling and algorithmic options of the solution process.
\end{itemize}
%
The description of both phases is outside of the scope of this document, which only deals with the required final form of the input.

\medskip
\noindent
Insomuch as the set of types of optimization problems (\Block in \SMSpp parlance) to be solved within the project, and the set of available solution methods for doing it (\Solver in \SMSpp parlance) may be expanding over time, this document is intended as dynamic: as new components will added, the document will grow to cover the corresponding input formats. Non-backward-compatible modification of existing input formats will be kept to a minimum, and always agreed upon with the involved partners before being put into production. Appropriate versioning of both the software and this document will ensure consistency between the data preparation and data consumption processes.

\medskip
\noindent
The self-documenting nature of \netCDF, together with its portable readability and the schema definition of the various \Block, will make it possible to re-use all or some blocks of one \SMSpp-generated model in other contexts.

\section{General \code{netCDF} file structure}

\netCDF (network Common Data Form) \cite{netCDF} is a set of interfaces for array-oriented data access and a freely distributed collection of data access libraries for \code{C}, \code{Fortran}, \code{C++}, \code{Java}, and other languages. The \netCDF libraries support a machine-independent format for representing scientific data. Together, the interfaces, libraries, and format support the creation, access, and sharing of scientific data.

\medskip
\noindent
\netCDF data is:
%
\begin{itemize}
 \item Self-Describing. A \netCDF file includes information about the data it contains.
 %
 \item Portable. A \netCDF file can be accessed by computers with different ways of storing integers, characters, and floating-point numbers.
 %
 \item Scalable. A small subset of a large dataset may be accessed efficiently.
 %
 \item Appendable. Data may be appended to a properly structured \netCDF file without copying the dataset or redefining its structure.
 %
 \item Sharable. One writer and multiple readers may simultaneously access the same \netCDF file.
 %
 \item Archivable. Access to all earlier forms of \netCDF data will be supported by current and future versions of the software.
\end{itemize}
%
For the purpose of this document, only a relatively small set of \netCDF concepts need be discussed.
%
\begin{itemize}
 \item \netCDF \textit{file}: is the basic container of \netCDF, e.g.~corresponding to a standard file in the filesystem of the host machine. In the \code{C++} interface used by \SMSpp it corresponds to an object of type \code{netCDF::NcFile}. A typical constructor of the object requires the pathname of the file (a standard \code{char *}) and the mode, which can be e.g.~\code{netCDF::NcFile::read} or \code{netCDF::NcFile::replace} for reading and writing, respectively.
 %
 \item \netCDF \group: a \netCDF file is organised into several \groups, which can be nested inside each other to an arbitrary degree. In the \code{C++} interface used by \SMSpp, each group corresponds to an object of type \code{netCDF::NcGroup}; note that \code{netCDF::NcFile} derives from \code{netCDF::NcGroup}, and therefore all capabilities of the group are shared by the file (but not vice-versa). Each \group has a unique string name by which it can retrieved; \code{netCDF::NcGroup} (and, therefore, \code{netCDF::NcFile}) has a method \code{getGroup()} taking as input a \code{std::string} with the group name and returning an \code{netCDF::NcGroup} object containing the \emph{child group} with the given name (if any) of that group.
 %
 \item \netCDF \attribute: is a simple data point specific of a netCDF group, having a unique string name by which it can retrieved and a simple value (\code{int}, \code{double}, \code{std::string}, \ldots). In the \code{C++} interface used by \SMSpp, it is represented by a \code{netCDF::NcGroupAtt} object, which can be obtained by its enclosing \code{netCDF::NcGroup} via the method \code{getAtt()} taking in input its name. Then, the method(s) \code{getValue()} (available with different signatures corresponding to the different supported basic data types) allows to retrieve its value.
 %
 \item \netCDF \dimension: it basically represent the different indices over which the actual data is indexed, each of which is given a name. In the \code{C++} interface used by \SMSpp, it is represented by a \code{netCDF::NcDim} object, which can be obtained by its enclosing \code{netCDF::NcGroup} via the method \code{getDim()} taking in input its name. The \dimension (a \code{size\_t} value) is returned by the method \code{getSize()}.
 %
 \item \netCDF \variable: this is the container for the ``complex'' data of a \groups. It has a name (\code{std::string}), a basic data type (\code{int}, \code{double}, \code{std::string}, \ldots) and in principle any number of \dimensions.  In the \code{C++} interface used by \SMSpp, it is represented by a \code{netCDF::NcVar} object, which can be obtained by its enclosing \code{netCDF::NcGroup} via the method \code{getVar()} taking in input its name. Once the \code{netCDF::NcVar} object is obtained, individual values of the \variable can be read by its method(s) \code{getVar()} (available with different signatures corresponding to the different supported basic data types), taking a \code{std::vector<size\_t>} as long as the the number of \dimensions of the \variable (obtainable e.g.~with its method \code{NgetDimCount()}).
\end{itemize}
%
The above components allow to read and write structured data files with basically any nested format, which makes \netCDF ideal for representing the data characterizing \SMSpp, as discussed below.

\section{General \SMSpp file structure}

In \SMSpp, files can describe two different kinds of objects:
%
\begin{enumerate}
 \item \Block objects, representing the data characterizing a specific instance of a (structured) optimization problem to be solved;
 \item \Configuration objects, representing parameters of the solution process, either pertaining to a \Block (say, which of the different available formulations of the optimization problem should be used), or to a \Solver used to actually perform the optimizaton process.
\end{enumerate}
%
Both objects have \code{serialize()} and \code{deserialize()} methods allowing to save the current state to a given \netCDF \textit{file}/\group, as well as \emph{factories} allowing to create a new object from scratch out of a given \netCDF \textit{file}/\group.

\medskip
\noindent
The issue of \SMSpp is that an optimization problem is represented by a \Block, which can have any number of sub-\Block (recursively) representing parts of the problem with a specific structure. Yet, ``specific structure'' here may mean that the enclosing \Block can make some assumptions on what kind of sub-\Block it contains, but it may not know exactly their type. In \code{C++} parlance, \Block is an abstract base class, and specific optimization problems are represented by specific derived classes (\dBlock). A given \dBlock can make assumption on the type of its sub-\Block, but there can be many different variants of it, represented by different derived classes from the same base one. Thus, clearly the data-reading must be organized in such a way that each \dBlock is responsible for retrieving that which is necessary to it without making assumptions about the global organization of the file. This does not only apply to the data of the instance, but also to \emph{configuration} options that a \dBlock may have. In fact, several aspect of the \dBlock representing a given problem (which formulation is used, if and how variables and constraint of the formulation are dynamically generated, which parts of the primal/dual solution are saved, \ldots) can be implemented in different ways. Note that these decisions are in principle independent from the specific instance, and therefore are conceptually to be stored in, and retrieved from, a separate container than that holding the data of the \Block; this is why the \Configuration class is provided. Since \Block is a tree-shaped nested data structure, \Configuration also have to be such. Clearly, \netCDF perfectly suit this kind of requirement; in particular, the standing assumption for both classes is that
%
\begin{center}
 \emph{the data of one object} (\Block/\Configuration) \emph{is all to be found in the same \netCDF group; \\ the data of its ``sub-objects'' (sub-\Block/sub-\Configuration) is to be found in child groups of the group}.
\end{center}

\medskip
\noindent
Hence, the format of a \SMSpp \netCDF file depends on wether it holds \Block information, \Configuration information, or both. For the latter, there are actually two separate kind of \Configuration information that can be attached to a \dBlock. The first describes the above-mentioned options that are inherent to the \dBlock itself, which are described by the specific derived class \BlockConfig of \Configuration. However, a \dBlock need be solved, which is done by \Solver objects; each \Block can have an arbitrary number of \Solver ``registered'' with it. A \Solver can be an arbitrarily complex solution process; in particular, the structure of \Block immediately implies that one can register \Solver with any sub-\Block, which is actually useful e.g.~to decomposition algorithms. Hence, not only each \dSolver can have an arbitrarily large set of algorithmic configuration options; an arbitrarily large set of \Solver can be attached to a \Block and to all of its sub-\Block, recursively. Thus, the different derived class \BlockSolverConfig of \Configuration is provided to describe all this information. Note, again, that this is conceptually separate from both the specific instance encoded in the \dBlock and the choice of the \Block-specific options encoded in the \BlockConfig, which justifies why a separate container is used.

\medskip
\noindent
To allow holding all this different information, a \SMSpp \netCDF file has the following general structure. It must contain (in the \code{netCDF::NcFile} object, which is also a \code{netCDF::NcGroup}) an \attribute \cstr{SMS++\_file\_type} of \code{int} type which specifies which of three different kinds of file it is. The values are encoded in the \code{enum} \code{smspp\_netCDF\_file\_type} defined in \code{SMSTypedefs.h}, as follows:
%
\begin{itemize}
  \item \code{eProbFile = 0}: the \textit{file} (which is also a \group) has any number of child \groups with names \cstr{Prob\_0}, \cstr{Prob\_1}, \ldots In turn, each child \group has \emph{exactly three} child \groups with names \cstr{Block}, \cstr{BlockConfig} and \cstr{BlockSolver}, respectively. The first is intended to contain the serialization of a \dBlock, the second the serialization of a \dBlockConfig of the same \dBlock, and the third the serialization of a \dBlockSolverConfig of the same \dBlock, although any of the three can in principle be empty. If any of the child is not empty, it \emph{must} necessarily contain all the information necessary to reconstruct the specific instance.
  %
  \item \code{eBlockFile = 1}: the \textit{file} (which is also a \group) has any number of child \groups with names \cstr{Block\_0}, \cstr{Block\_1}, \ldots Each child \group contains the serialization of a \dBlock.
  %
  \item \code{eConfigFile = 2}: the \textit{file} (which is also a \group) has any number of child \groups with names \cstr{Config\_0}, \cstr{Config\_1}, ... Each child \group contains the serialization of a \dConfiguration. Note that no distinction is required between a \dBlockConfig and a \dBlockSolverConfig, since they are both derived from \Configuration.
\end{itemize}
%
Note that (some variants of) the \code{deserialize()} methods of \Block / \Configuration allow to directly specify which of the different objects stored in the file to read via its index $i$ in the ``name''.

\medskip
\noindent
To completely describe the file formats we now have to describe the format of the \netCDF \group as far as the base \Block and \Configuration (for the latter, actually both sub-classes \BlockConfig and \BlockSolverConfig) are concerned, i.e., the (possibly, small) part of the contents that do not depend on the specific derived class.

%- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
\subsection{\Block description}

The only content that any \netCDF \group describing a \dBlock must necessarily have is a string \attribute with name \cstr{type} containing the classname of the object. This must be exact, e.g., as returned by the protected virtual method \code{name()}, since it is used in the \emph{factory} when deserializing the object. Note that template classes derived from \Block are allowed, with the standard notation \cstr{class\_name<template\_paramaters>}.

%- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
\subsection{\Configuration description}

The only content that any \netCDF \group describing a \dConfiguration must necessarily have is a string \attribute with name \cstr{type} containing the classname of the object. This must be exact, e.g., as returned by the protected virtual method \code{name()}, since it is used in the \emph{factory} when deserializing the object. Note that template classes derived from \Configuration are allowed, with the standard notation \cstr{class\_name<template\_paramaters>}; see for instance the template \code{SimpleConfiguration<>} class.

%- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
\subsubsection{\BlockConfig description}\label{ssec:BlockConfig}

Besides the mandatory \cstr{type} attribute of any \dConfiguration, a \SMSpp \netCDF \group for a \BlockConfig can contain the following:
%
\begin{itemize}
 \item the \attribute \cstr{name} of string type containing the ``name'' of the \Block (this is not a classname, but rather a string describing something about the \Block that is supposedly useful when printing/debugging);
 %
 \item the \group \cstr{static\_constraints} containing a \Configuration object for the static constraints of the \Block;
 %
 \item the \group \cstr{dynamic\_constraints } containing a \Configuration object for the dynamic constraints of the \Block;
 %
 \item the \group \cstr{static\_variables} containing a \Configuration object for the static variables of the \Block;
 %
 \item the \group \cstr{dynamic\_variables} containing a \Configuration object for the dynamic variables of the \Block;
 %
 \item the \group \cstr{objective} containing a \Configuration object for the objective of the \Block;
 %
 \item the \group \cstr{is\_feasible} containing a \Configuration object for the \code{is\_feasible()} method of the \Block;
 %
 \item the \group \cstr{is\_optimal} containing a \Configuration object for the \code{is\_optimal()} method of the \Block;
 %
 \item the \group \cstr{solution} containing a \Configuration object for the methods of the \Block dealing with solutions (\code{get\_Solution()} and \code{map\_[back/forward]\_solution()});
 %
 \item the \group \cstr{extra} containing a \Configuration object, which has no direct use in the base \Block class, but is added so that derived classes can put there any configuration information without having to define further derived classes form \BlockConfig (which, however, they can still do if they want);
 %
 \item the \dimension \cstr{n\_sub\_Block} containing the number of \BlockConfig descriptions for the sub-\Block of the current \dBlock;
 %
 \item with $n$ being the size of \code{n\_sub\_Block}, $n$ \groups, with name \cstr{sub-BlockConfig\_$i$} for all $i = 0, \ldots, n - 1$, containing each the description of a \BlockConfig for one of the sub-\Block of the current \dBlock.
\end{itemize}
%
Of all these, only the \cstr{name} \attribute and the \cstr{n\_sub\_Block} \dimension are mandatory (they must exist, although they may be empty/zero). All other groups may not exist, in which case the corresponding field of the class is filled with a \code{nullptr}, indicating that the ``default'' configuration (whatever that may mean for the \dBlock in question) have to be used. Note that that the matching between the sub-\BlockConfig and the sub-\Block is positional: the \BlockConfig found in the group ``{\tt sub-BlockConfig\_}$i$'' is that for the $i$-th sub-\Block. Note that the vector of sub-\BlockConfig is allowed to be of different size than the number of sub-\Block; if it is larger any extra \BlockConfig is simply ignored, if it is shorter then all missing sub-\BlockConfig are treated as \code{nullptr} (default configuration).

%- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
\subsubsection{\BlockSolverConfig description}

Besides the mandatory \cstr{type} attribute of any \dConfiguration, a \SMSpp \netCDF \group for a \BlockSolverConfig can contain the following:
%
\begin{itemize}
 \item the \dimension \cstr{n\_SolverConfig} containing the number of \Solver that are to be attached to this \Block, and therefore the (expected) number of their \dConfiguration objects;
 %
 \item the \variable \cstr{SolverNames}, of type string and indexed over the \dimension \cstr{n\_SolverConfig}; the $i$-th entry of the variable is assumed to contain the classname of a \dSolver object to be attached to the \Block (this must be exact, e.g., as returned by the protected virtual method \code{name()}, since it is used in the \emph{factory} when creating the object);
 %
 \item with $n$ being the size of \code{n\_SolverConfig}, $n$ \groups, with name \cstr{SolverConfig\_$i$} for all $i = 0, \ldots, n - 1$, containing each the description of a \dConfiguration object for the $i$-th \dSolver;
 %
 \item the \dimension \cstr{n\_BlockSolverConfig} containing containing the number of \BlockSolverConfig descriptions for the sub-\Block of the current \dBlock;
 %
 \item with $m$ being the size of \code{n\_BlockSolverConfig}, $m$ \groups, with name \cstr{BlockSolverConfig\_$i$} for all $i = 0, \ldots, m - 1$, containing each the description of a \BlockSolverConfig for one of the sub-\Block of the current \dBlock.
\end{itemize}
%
Of all these, only the \cstr{n\_SolverConfig} and \cstr{n\_BlockSolverConfig} \dimensions and the \cstr{SolverNames} \variable are mandatory; the individual \groups may not exist if the corresponding \dimension is $0$. Note that that the matching between the sub-\BlockSolverConfig and the sub-\Block is positional: the \BlockSolverConfig found in the group ``{\tt BlockSolverConfig\_}$i$'' is that for the $i$-th sub-\Block. Note that the vector of sub-\BlockSolverConfig is allowed to be of different size than the number of sub-\Block; if it is larger any extra \BlockSolverConfig is simply ignored, if it is shorter then all missing sub-\BlockConfig are treated as \code{nullptr} (default configuration).

\medskip
\noindent
Note that the \dConfiguration objects to be found in the \groups \cstr{SolverConfig\_$i$} are not ``any'' \dConfiguration; rather, they are assumed to be of the specific type \ComputeConfig, whose format is described in the next subsection.

\subsubsection{\ComputeConfig description}\label{ssec:ComputeConfig}

\ComputeConfig (defined in \code{ThinComputeInterface.h}) is a class of \dConfiguration objects specifically tailored for representing sets of algorithmic parameters of solution algorithms, like the ones presumably required by a \dSolver.
Besides the mandatory \cstr{type} attribute of any \dConfiguration, a \SMSpp \netCDF \group for a \ComputeConfig can contain the following:
%
\begin{itemize}
 \item the \attribute \cstr{diff} of \code{int} type containing the value for the \code{f\_diff} field of the \ComputeConfig (basically, a bool telling if the information in it has to be taken as ``the configuration to be set'' or as ``the changes to be made from the current configuration'');
 %
 \item the \dimension \cstr{num\_int\_par} containing the number of \code{int} parameters;
 %
 \item the \variable \cstr{int\_par\_names}, of type string and indexed over the \dimension \cstr{num\_int\_par}; the $i$-th entry of the variable is assumed to contain the string name of an \code{int} parameter;
 %
 \item the \variable \cstr{int\_par\_vals}, of type \code{int} and indexed over the \dimension \cstr{num\_int\_par}; the $i$-th entry of the variable is assumed to contain the value of the \code{int} parameter whose string name is to be found in the $i$-th entry of \cstr{int\_par\_names};
 %
 \item the \dimension \cstr{num\_dbl\_par} containing the number of \code{double} parameters;
 %
 \item the \variable \cstr{dbl\_par\_names}, of type string and indexed over the \dimension \cstr{num\_dbl\_par}; the $i$-th entry of the variable is assumed to contain the string name of a \code{double} parameter;
 %
 \item the \variable \cstr{dbl\_par\_vals}, of type \code{double} and indexed over the \dimension \cstr{num\_dbl\_par}; the $i$-th entry of the variable is assumed to contain the value of the \code{double} parameter whose string name is to be found in the $i$-th entry of \cstr{dbl\_par\_names};
 %
 \item the \dimension \cstr{num\_str\_par} containing the number of string parameters;
 %
 \item the \variable \cstr{str\_par\_names}, of type string and indexed over the \dimension \cstr{num\_str\_par}; the $i$-th entry of the variable is assumed to contain the string name of a string parameter;
 %
 \item the \variable \cstr{str\_par\_vals}, of type string and indexed over the \dimension \cstr{num\_str\_par}; the $i$-th entry of the variable is assumed to contain the value of the string parameter whose string name is to be found in the $i$-th entry of \cstr{str\_par\_names};
 %
 \item the \group \cstr{extra} containing a \Configuration object, which has no direct use in the base \ComputeConfig class, but is added so that derived classes can put there any configuration information without having to define further derived classes form \ComputeConfig (which, however, they can still do if they want).
\end{itemize}
%
The three \dimensions \cstr{num\_*\_par} are mandatory. If any of these is zero, the corresponding variables \cstr{*\_par\_names} and \cstr{*\_par\_vals} may not be defined. The \cstr{extra} \group may not exist, in which case the corresponding \Configuration object is set to a \code{nullptr}.

\section{File formats of existing \dBlock}

This Section collects the description of the \netCDF file formats for all the implemented \dBlock developed for \textsc{plan4res}. As such, the section will be continuously updated over the course of the project as new \dBlock will be added, although as usual non-backward-compatible changes to existing input formats will be kept to a minimum, and always agreed upon with the involved partners before being put into production. 

%- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
\subsection{\code{SimpleMILPBlock}}

\code{SimpleMILPBlock} is a simple class, only having the ``abstract representation'', for describing Mixed-Integer Linear Programs of the generic form
\[
 \min \{ \, \bar{c} + cx \,:\, \underline{b} \leq Ax \leq \bar{b} \;\;,\;\;
                               l \leq x \leq u \, \}
\]
where $c$, $l$, $u \in \mathbb{R}^n$, $\underline{b}$, $\bar{b} \in \mathbb{R}^m$, $A \in \mathbb{R}^{m \times n}$, and $c^0 \in \mathbb{R}$. Actually, entries of $\underline{b}$ and $l$ can be $-\infty$, and entries of $\bar{b}$ and $u$ can be $+\infty$. The coefficient matrix $A$ is usually very sparse, which justifies the choice of a standard sparse (row-wise) format to represent it.

\medskip
\noindent
Besides the mandatory \cstr{type} \attribute of any \dBlock, the group will contain the following:
%
\begin{itemize}
 \item the \attribute \cstr{infinity} containing the number that is used to specify that one of the bounds (entries of $\underline{b}$, $\bar{b}$, $l$ or $u$) is $\pm \infty$;
 %
 \item the \dimension \cstr{num\_vars} containing the number $n$ of \code{Variable} (columns in the matrix $A$) of the \code{SimpleMILPBlock};
 %
 \item the \dimension \cstr{num\_constraints} containing the number $m$ of \code{Constraint} (rows in the matrix $A$) of the \code{SimpleMILPBlock};
 %
 \item the \dimension \cstr{nzcount} containing the total number of nonzero coefficients in the \code{Constraint} of the \code{SimpleMILPBlock};
 %
 \item the \variable \cstr{rmatval}, of type \code{double} and indexed over the \dimension \cstr{nzcount}, that contains the nonzeros in the coefficient matrix $A$ of the MILP, arranged row-wise (see \code{rmatbeg});
 %
 \item the \variable \cstr{rmatind}, of type \code{UInt64} and indexed over the \dimension \cstr{nzcount}, that contains the column indices of the nonzeros in the coefficient matrix $A$ of the MILP, arranged row-wise; that is, the $i$-th entry of \code{rmatind} indicates to which variable (column) the (allegedly, nonzero) coefficient to be found in the $i$-th entry of \code{rmatval} refers;
 %
 \item the \variable \cstr{rmatbeg}, of type \code{UInt64} and indexed over the \dimension \cstr{num\_constraints}, that contains the indices into the \code{rmatval}/\code{rmatind} vectors where each constraint (row of the coefficient matrix $A$ of the MILP) begins: all the nonzeros corresponding to constraint $h = 0, \ldots, \code{num\_constraints} - 1$ are to be found in \code{rmatval[ rmatbeg[ $h$ ] ]}, \ldots, \code{rmatval[ rmatbeg[ $h + 1$ ] $- 1$ ]}, with their column (variable) indices to be found in the corresponding entries of \code{rmatind[]};
 %
 \item the \variable \cstr{x\_lb}, of type \code{double} and indexed over the \dimension \cstr{num\_vars}, whose $i$-th entry is the (possibly, $-\infty$) lower bound on the feasible value of the $i$-th variable (the vector $l$);
 %
 \item the \variable \cstr{x\_ub}, of type \code{double} and indexed over the \dimension \cstr{num\_vars}, whose $i$-th entry is the (possibly, $+\infty$) upper bound on the feasible value of the $i$-th variable (the vector $u$);
 %
 \item the \variable \cstr{row\_lb}, of type \code{double} and indexed over the \dimension \cstr{num\_constraints}, whose $i$-th entry is the (possibly, $-\infty$) lower bound on the feasible value that the linear expression of the $i$-th constraint (as specified by the coefficients in \code{rmatval}, \code{rmatind}, and \code{rmatbeg}) can take (the vector $\underline{b}$);
 %
 \item the \variable \cstr{row\_ub}, of type double and indexed over the \dimension \cstr{num\_constraints}, whose $i$-th entry is the (possibly, $+\infty$) upper bound on the feasible value that the linear expression of the $i$-th constraint (as specified by the coefficients in \code{rmatval}, \code{rmatind}, and \code{rmatbeg}) can take (the vector $\bar{b}$);
 %
 \item the \variable \cstr{obj}, of type \code{double} and indexed over the \dimension \cstr{num\_vars}, whose $i$-th entry is the coefficient of the $i$-th variable in the linear objective function of the MILP (the vector $c$);
 %
 \item the scalar \variable \cstr{obj\_offset}, of type \code{double} (and, since it is a scalar, not indexed over any \dimension) giving the fixed offset in the linear objective function of the MILP (the constant $\bar{c}$).
\end{itemize}
%
All these are mandatory.

\subsection{\code{StructuredMILPBlock}}

While \code{SimpleMILPBlock} is a ``leaf'' \Block just representing a generic MILP, \code{StructuredMILPBlock} derives from \code{SimpleMILPBlock} and extends it to represent ``structured'' MILP of the format
%
\begin{align*}
 \min \; & \textstyle
           \bar{c} + c^0 x^0 + \sum_{h = 1}^k c^k x^k \\[0.1cm]
 %
 & x^h \in X^h & h = 1, \ldots, k \\[0.1cm]
 %
 & \underline{b}^0 \leq A^0 x^0 \leq \bar{b}^0 \;\;,\;\;
   l^0 \leq x^0 \leq u^0 \\[0.1cm]
 %
 & \textstyle
   \underline{r} \leq B^0 x^0 + \sum_{h = 1}^k B^k x^k \leq \bar{r}
\end{align*}
%
where $X^h$ denotes the feasible region of the $h$-th sub-\Block of the \code{StructuredMILPBlock}, which must be a \code{SimpleMILPBlock}, $x^h$ its \code{Variable}, and $c^h$ the coefficients of its objective. Thus, a \code{StructuredMILPBlock} has its own MILP constraints on its own variable $x^0$, represented exactly as in \code{SimpleMILPBlock} (indeed, a \code{StructuredMILPBlock} is a \code{SimpleMILPBlock}), plus the constraints of an arbitrary numbers of \code{SimpleMILPBlock}, plus constraints ``linking'' the variable $x^0$ of the ``father'' with those of the ``sons''. Note that the ``sons'' of a \code{StructuredMILPBlock} are \code{SimpleMILPBlock}, which means they can actually be other \code{StructuredMILPBlock}. Thus, \code{StructuredMILPBlock} allows to represent any block-structured MILP \emph{provided that the linking constraints only link variables of the father to variables of its immediate sons, and not to variables of further descendants}.

\medskip
\noindent
 Besides the mandatory \cstr{type} attribute of any \dBlock, and whatever has to be found in the \code{netCDF::NcGroup} of a \code{SimpleMILPBlock} (since a \code{StructuredMILPBlock} is a \code{SimpleMILPBlock}), the group should contain the following:
%
\begin{itemize}
 \item the \dimension \cstr{linking\_num\_constraints} containing the number of ``linking'' \code{Constraint} (rows of the matrices $B^h$) of the \code{StructuredMILPBlock};
 %
 \item the \dimension \cstr{linking\_nzcount} containing the total number of nonzero coefficients in the ``linking'' \code{Constraint} (the matrices $B^h$) of the \code{StructuredMILPBlock};
 %
 \item the \variable \cstr{linking\_rmatval}, of type \code{double} and indexed over the \dimension \cstr{linking\_nzcount}, that contains the nonzeros in the coefficient matrix of the ``linking'' \code{Constraint} (the matrices $B^h$), arranged row-wise (see \code{linking\_rmatbeg});
 %
 \item the \variable \cstr{linking\_rmatind}, of type \code{UInt64} and indexed over the \dimension \cstr{linking\_nzcount}, that contains the column indices of the nonzeros in the coefficient matrix of the ``linking'' \code{Constraint} (the matrices $B^h$), arranged row-wise; this has to be used together with \code{linking\_rmatblk}, see below;
 %
 \item the \variable \cstr{linking\_rmatblk}, of type \code{UInt64} and indexed over the \dimension \cstr{linking\_nzcount}, that contains the block indices of the variables corresponding to nonzeros in the coefficient matrix of the ``linking'' \code{Constraint} (the matrices $B^h$); that is, the $i$-th entry of \code{linking\_rmatblk} indicates the index $h$ of the \Block to which the \code{Variable} belongs, with $h = 0$ used for the ``father'' \code{StructuredMILPBlock} and $h = 1, 2, \ldots$ used for the \code{Variable} of the 1st, 2nd, \ldots of its \code{SimpleMILPBlock} sons, while the $i$-th entry of \code{linking\_rmatind} is the index of the \code{Variable} in the $h$-th \Block;
 %
 \item the \variable \cstr{linking\_rmatbeg}, of type \code{UInt64} and indexed over the \dimension \cstr{linking\_num\_constraints}, that contains the indices into the \code{linking\_rmatval}/\code{linking\_rmatind} vectors where each ``linking''  \code{Constraint} (row of the matrices $B^h$) begins: all the nonzeros corresponding to constraint $h = 0, ..., \code{linking\_num\_constraints} - 1$ are to be found in \code{linking\_rmatval[ linking\_rmatbeg[ $h$ ] ]}, \ldots, \code{linking\_rmatval[ linking\_rmatbeg[ $h + 1$ ] $- 1$ ]}, with their column (variable) and \Block indices to be found in the corresponding entries of \code{linking\_rmatind} and \code{linking\_rmatblk}, respectively;
 %
 \item the \variable \cstr{linking\_row\_lb}, of type double and indexed over the \dimension \cstr{linking\_num\_constraints}, whose $i$-th entry is the (possibly, $-\infty$) lower bound on the feasible value that the linear expression of the $i$-th ``linking'' \code{Constraint} (as specified by the coefficients in \code{linking\_rmatval}, \code{linking\_rmatind}, \code{linking\_rmatbeg}, and \code{linking\_rmatblk}) can take;
 %
 \item the \variable \cstr{linking\_row\_ub}, of type double and indexed over the \dimension \cstr{linking\_num\_constraints}, whose $i$-th entry is the (possibly, $+\infty$) upper bound on the feasible value that the linear expression of the $i$-th ``linking'' \code{Constraint} (as specified by the coefficients in \code{linking\_rmatval}, \code{linking\_rmatind}, \code{linking\_rmatbeg}, and \code{linking\_rmatblk}) can take.
\end{itemize}
%
All these are mandatory.

\subsection {\code{MCFBlock}}

The \code{MCFBlock} class implements the \Block concept for the (linear) Min-Cost Flow (MCF) problem.

\smallskip
\noindent
The data of the problem consist of a (directed) graph $G = ( N , A )$ with $n = |N|$ nodes and $m = |A|$ (directed) arcs. Each node $i$ has a deficit $b[ i ]$, i.e., the amount of flow that is produced/consumed by the node: source nodes (which produce flow) have negative deficits and sink nodes (which consume flow) have positive deficits. Each arc $(i, j)$ has an upper capacity $U[ i , j ]$ and a linear cost coefficient $C[ i , j ]$. Flow variables $X[ i , j ]$ represents the amount of flow to be sent on arc $(i, j)$. Parallel arcs, i.e., multiple copies of the same arc $(i, j)$ are in general allowed; it is expected that they have different costs (for otherwise they can be merged into a unique arc), but this is not strictly enforced. Multiple copies of some arc $(i, j)$ can be seen as ``total'' flow cost on that arc being a piecewise-linear convex function. The formulation of the problem is:
%
\begin{align*}
 \min \; & \textstyle \sum_{ (i, j) \in A } C[ i , j ] X[ i, j ] \\[0.1cm]
 %
 & \textstyle
   \sum_{ (j, i) \in A } X[ j , i ] -
   \sum_{ (i, j) \in A } X[ i , j ] = b[ i ] & i \in N \\[0.1cm]
 %
 & 0 \leq X[ i , j ] \leq U[ i , j ] & (i, j) \in A
\end{align*}
%
The $n$ equations are the flow conservation constraints and the $2m$ inequalities are the flow nonnegativity and capacity constraints. At least one of the flow conservation constraints is redundant, as the demands must be balanced ($\sum_{ i \in N } b[ i ] = 0$); indeed, exactly $n$ - ConnectedComponents( $G$ ) flow conservation constraints are redundant, as demands must be balanced in each connected component of $G$.

\smallskip
\noindent
The graph $G$ is allowed to be ``partly dynamic''. The set of nodes and arcs that are input at the beginning are assumed not to be changed (save for changing costs, capacities, and deficits, and for arcs to be closed or opened). Then, new arcs and nodes, up to a set maximum, can be dynamically added or deleted. This means that the graph can be fully static (if the maximum number of dynamic arcs and nodes is set to zero) as well as fully dynamic (if the initial graph is empty).

\smallskip
\noindent
Besides the mandatory \cstr{type} attribute of any \dBlock, the \group representing the \code{MCFBlock} should contain the following:
%
\begin{itemize}
 \item the \dimension \cstr{NNodes} containing the number of nodes in the graph ($n$);
 %
 \item the \dimension \cstr{NArcs} containing the number of arcs in the graph ($m$);
 %
 \item the \variable \cstr{C}, of type \code{double} and indexed over the \dimension \cstr{NArcs}; the $i$-th entry of the variable is assumed to contain the upper capacity of the $i$-th arc in the graph, that whose starting node and ending node are specified by the \variable \cstr{SN} and \cstr{EN} (below);
 %
 \item the \variable \cstr{U}, of type \code{double} and indexed over the \dimension \cstr{NArcs}; the $i$-th entry of the variable is assumed to contain the cost of the $i$-th arc in the graph (the lower capacity being fixed to 0), that whose starting node and ending node are specified by the \variable \cstr{SN} and \cstr{EN} (below);
 %
 \item the \variable \cstr{B}, of type \code{double} and indexed over the \dimension \cstr{NNodes}; the $i$-th entry of the variable is assumed to contain the deficit of the i-th node in the graph (note that node names here go from $0$ to $n - 1$);
 %
 \item the \variable \cstr{SN}, of type \code{int} and indexed over the \dimension \cstr{NArcs}; the $i$-th entry of the variable is assumed to contain the starting node of the $i$-th arc in the graph (note that node names here go from $1$ to $n$, they are shifted by $1$ w.r.t.~to the indices used in the \cstr{B} variable);
 %
 \item the \variable \cstr{EN}, of type \code{int} and indexed over the \dimension \cstr{NArcs}; the $i$-th entry of the variable is assumed to contain the ending node of the $i$-th arc in the graph (note that node names here go from $1$ to $n$, they are shifted by $1$ w.r.t.~to the indices used in the \cstr{B} variable);
 %
 \item the \dimension \cstr{DynNNodes} containing the current number of dynamic nodes: all the nodes between $0$ and \cstr{NNodes} $-$ \cstr{DynNNodes} $- 1$ are static, i.e., they cannot be deleted (and re-created), whereas all those from \cstr{NNodes} + \cstr{DynNNode} to \cstr{NNodes} $- 1$ are dynamic, i.e., they can deleted and later on re-created;
 %
 \item the \dimension \cstr{DynNArcs} containing the current number of dynamic arcs: all the arcs between 0 and \cstr{NArcs} - \cstr{DynNArcs} $- 1$ are static, i.e., they cannot be deleted (and re-created), whereas all those from \cstr{NArcs} $+$ \cstr{DynNArcs} to \cstr{NArcs} $- 1$ are dynamic, i.e., they can deleted and later on re-created;
 %
 \item the \dimension \cstr{MaxDynNNodes} containing the maximum number of dynamic nodes in the graph (the maximum value that $n$ can take); data in the \code{MCFBlock} is allocated to accommodate for the fact that further \cstr{MaxDynNNodes} $-$ \cstr{DynNNodes} nodes can later on be dynamically created (and deleted); if \cstr{MaxDynNNodes} $<$ \cstr{DynNNodes} the \dimension is ignored and \cstr{NNodes} is taken as the maximum overall number of nodes;
 %
 \item the \dimension \cstr{MaxDynNArcs} containing the maximum number of dynamic arcs in the graph (the maximum value that $m$ can take): data in the \code{MCFBlock} is allocated to accommodate for the fact that further \cstr{MaxDynNArcs} $-$ \cstr{DynNArcs} arcs can later on be dynamically created (and deleted); if \cstr{MaxDynNArcs} $<$ \cstr{DynNArcs} the \dimension is ignored and \cstr{NArcs} is taken as the maximum overall number of arcs.
\end{itemize}

\smallskip
\noindent
The two \dimensions \cstr{NNodes} and \cstr{NArcs} are mandatory, such as are the two \variables \cstr{SN} and \cstr{EN}. The three other \variables are optional. If \cstr{C} is missing, all arc costs are assumed to be $0$. If \cstr{U} is missing, all arc capacities are assumed to be infinite. If \cstr{B} is missing, all node deficits are assumed to be $0$. Finally, all the \dimensions \cstr{DynNNodes}, \cstr{DynNArcs}, \cstr{MaxDynNNodes} and \cstr{MaxDynNArcs} are optional: if they are missing they are treated as being $0$ (this happening for all four means that the graph is "fully static" and cannot be changed).

\subsection {\code{UCBlock}}

The class \code{UCBlock}, implements the \Block concept [see Block.h] for the Unit Commitment (UC) problem in electrical power production. This is typically a short-term (across for instance one week or one day time horizon) *deterministic* problem regarding finding an optimal schedule of the production of electrical generators satisfying a (large) set of technical constraints.
\smallskip
The model is quite flexible due to the fact that different types of units and network constraints can be used by means of the fact that the class manages son \Block of type \code{UnitBlock} and \code{NetworkBlock}. Also \code{UCBlock} handles a reasonably large variety of constraints, regarding not only active power but also primary and secondary reserve and inertia. Admittedly, some choices in \code{UCBlock} (like \code{HeatBlock}, pollution constraints, ...) are quite specific of the UC of the plan4res project; however, all the \cstr{nonstandard} aspects of UC can be switched away from the model (by simply not providing the data describing them). The main elements that \code{UCBlock} handles are:
%
\begin{itemize}
 \item The time horizon of the problem, i.e., a discrete set of (typically, equally-spaced) time instants at which decisions are made (like, the $24$ hours in a day);
 %
 \item A set of electricity generating units, represented by derived classes of the base class \code{UnitBlock};
 %
 \item A set of \code{NetworkBlock}, one for each time instant in the time horizon, which represent the constraints on the electricity demand satisfaction and the technical constraints on the transmission network. These can be basically \cstr{empty} if the capacity of the transmission network is such as to never really impact generation decisions (a \cstr{bus});
 %
 \item An optional set of \code{HeatBlock}, each representing the satisfaction of some specific \cstr{type of heat} on a close geographical area by heat-generating units possibly coupled with a heat storage. The link with the rest of the UC model lies in the fact that some of the heat-generating units in a \code{HeatBlock} may also be electricity generating ones (i.e., a \code{UnitBlock}); actually, the same \code{UnitBlock} can generate heat of \cstr{different types}, and therefore appear as a heat-generating units in more than one \code{HeatBlock}.
\end{itemize}

\smallskip
\noindent
Besides the mandatory \cstr{type} attribute of any \dBlock, the \group should contain the following:
%
\begin{itemize}
 \item the \dimension \cstr{TimeHorizon} containing the number of time steps in the problem;
 %
 \item the \dimension \cstr{NumberUnits} containing the number of units (\code{UnitBlock}) in the problem;
 %
 \item the \groups \cstr{UnitBlock\_0}, \cstr{UnitBlock\_1}, ... , \cstr{UnitBlock\_n} with \code{n == NumberUnits - 1}, containing each one \code{UnitBlock} corresponding to one or more electricity generating unit (electrical generator). It is an error if the corresponding groups are not there. Each \code{UnitBlock} can have more than one electrical generator (cf. \code{UnitBlock::get\_number\_generators()}), a value that is useful in the following (cf. \cstr{GeneratorNode}) is the total number of those, which we will refer to as \cstr{NumberElectricalGenerators}. This is computed by just calling \code{get\_number\_generators()} on each of the \code{UnitBlock} and summing all the results. Clearly, \code{NumberElectricalGenerators >= NumberUnits} and indeed, most of the \code{UnitBlock} can be expected to have just one electrical generator. If this happens for all the units then the \code{NumberElectricalGenerators ==  NumberUnits}. If, instead, some UnitBlock (like cascades of hydro generators or combined cycle plants) actually has more than one electrical generator, then \code{NumberElectricalGenerators > NumberUnits} (each UnitBlock must have at least one). This is because some \code{UnitBlock} (like cascades of hydro generators or combined cycle plants) can actually have more than one electrical generator in it (but each \code{UnitBlock} must have at least one). It is then useful (cf. \cstr{GeneratorNode}) to be able to assign a unique index \code{g = 0, 1, \dots, NumberElectricalGenerators - 1} to each of the electrical generators in the \code{UCBlock}. When \code{NumberElectricalGenerators == NumberUnits}, the index is the same as \code{i = 0, 1, \dots, NumberUnits - 1}(there is a one-to-one correspondence between \code{UnitBlock} and electrical generators). When, instead, \code{NumberElectricalGenerators > NumberUnits}, a mapping must be defined. The mapping is the obvious one: \code{UnitBlock} have an ordering \code{i = 0, 1, \dots, NumberUnits - 1} (cf. the groups \cstr{UnitBlock\_0}, \cstr{UnitBlock\_1}, ... above), and the electrical generators into each \code{UnitBlock} also have some natural ordering (corresponding to the columns of the matrices of variables, cf. e.g. \code{UnitBlock::get\_commitment()}). Thus, in general the mapping is:
 \begin{itemize}
 \item electrical generator \code{0 =} first generator of \code{UnitBlock\_0}
 \item electrical generator \code{1 =} second generator of \code{UnitBlock\_0}
 \item \code{\dots}
  \item electrical generator \code{k = k-th} generator of \code{UnitBlock\_0} (\code{k = UnitBlock\_0 -> get\_number\_generators()}
 \item electrical generator \code{k + 1 =} first generator of \code{UnitBlock\_1}
 \item electrical generator \code{k + 2 =} second generator of \code{UnitBlock\_1}
 \item \code{\dots}
 \end{itemize}
 \smallskip
 \noindent
 which of course boils down to \cstr{g = i} when each UnitBlock has exactly one electrical generator;
 %
 \item the \dimension \cstr{NumberHeatBlocks} containing the number of heat blocks in the problem. The \dimension is optional: if it is not provided then it is taken to be $0$, which means that there is no heat block in the problem;
 %
 \item the \groups \cstr{HeatBlock\_0}, \cstr{HeatBlock\_1}, ... , \cstr{HeatBlock\_n} with \code{n == NumberHeatBlocks - 1}, containing each one a \code{HeatBlock}. When \code{NumberHeatBlocks == 0}, these groups need not be there since they are not read. If, instead, \code{NumberHeatBlocks > 0}, it is an error if the corresponding groups are not there. Since each HeatBlock can have more than one heat generator (cf. \code{HeatBlock::get\_number\_heat\_generators()}), a value that is useful in the following (cf. \cstr{HeatSet}) is the total number of those. We will refer to such number as \cstr{NumberHeatGenerators}, which is computed by just calling \code{get\_number\_heat\_generators()} on each of the \code{HeatBlock} and summing all the results. Clearly, \code{NumberHeatGenerators >= NumberHeatBlock}. Some of the \code{HeatBlock} may have just one heat generator; if this happens for all the heat blocks (but this is not likely), then \code{NumberHeatGenerators ==  NumberHeatBlocks}. It is then useful (cf. \cstr{HeatNode}) to be able to assign a unique index \code{h = 0, 1, \dots, NumberHeatGenerators - 1} to each of the heat generators in the \code{UCBlock}. When \code{NumberHeatGenerators == NumberHeatBlocks} the index is the same as \code{b = 0, 1, \dots, NumberHeatBlock - 1} (there is a one-to-one correspondence between \code{HeatBlock} and heat generators, but this is not likely to happen). When, instead, \code{NumberHeatGenerators > HeatBlock}, a mapping must be defined. The mapping is the obvious one: \code{HeatBlock} have an ordering \code{b = 0, 1, ..., NumberHeatBlocks - 1} (cf. the groups \cstr{HeatBlock\_0}, \cstr{HeatBlock\_1}, ... above), and the heat generators into each \code{HeatBlock} also have some natural ordering (corresponding to the columns of the matrices of variables, cf. e.g. \code{HeatBlock::get\_heat()}. Thus, in general the mapping is:
 \begin{itemize}
  \item heat generator \code{0 =} first generator of \code{HeatBlock\_0}
  \item heat generator \code{1 =} second generator of \code{HeatBlock\_0}
  \item \code{\dots}
  \item heat generator \code{k = k-th} generator of \code{HeatBlock\_0} (\code{k = HeatBlock\_0 -> get\_number\_heat\_units()}
  \item heat generator \code{k + 1 =} first generator of \code{HeatBlock\_1}
  \item heat generator \code{k + 2 =} second generator of \code{HeatBlock\_1}
  \item \code{\dots}
 \end{itemize}
 \smallskip
 \noindent
 which of course boils down to \cstr{h = b} when each HeatBlock has exactly one heat generator (but this is not assumed to happen);
 %
 \item optionally, the \dimensions and variables necessary to deserialize a \code{NetworkData} object that describes the transmission network; see \ref{NetworkData} for details. If that is not provided (basically, \cstr{NumberNodes} is not provided or it is \code{== 1}), then the transmission network is taken to have only one node (a bus). If the data of a \code{NetworkData} is specified, the \code{NetworkData} is passed to each of the \code{NetworkBlock} (see below) of the \code{UCBlock}, if any. However, if a \code{NetworkBlock} also has a \code{NetworkData} specified in its own group, then the \code{NetworkData} inside the \code{NetworkBlock} overrules that inside the \code{UCBlock}, which is ignored by that \code{NetworkBlock};
 %
 \item The \variable \cstr{ActivePowerDemand}, of type double, and indexed both over the dimensions \cstr{NumberNodes} and \cstr{TimeHorizon}. This variable is optional if
 \begin{itemize}
  \item = a \code{NetworkBlock} is defined for each time instant (see below), and
  \item = each of the defined \code{NetworkBlock} has the \cstr{ActiveDemand} variable specified in the corresponding group.
 \end{itemize}
 Otherwise it is mandatory. When it is defined, the entry \code{ActivePowerDemand[ n , t ]} is  assumed to contain the active power demand of node $n$ of the transmission network at the given time instant $t$, where the first dimension \cstr{NumberNodes} can be read via \code{NetworkBlock::NetworkData::get\_number\_nodes()} from either the \code{NetworkData} object in \code{UCBlock}, or these in the \code{NetworkBlock}. When \cstr{ActivePowerDemand} is defined, and also the \cstr{ActiveDemand} variable is defined in the group of some \code{NetworkBlock}, then \cstr{ActiveDemand} overrules the value in the corresponding row of \cstr{ActivePowerDemand}, which is ignored.
 %
 \item the \groups \cstr{NetworkBlock\_0}, \cstr{NetworkBlock\_1}, ... , \cstr{NetworkBlock\_t} with \code{t = TimeHorizon - 1}, containing each the constraints on the transmission network at time $t$. The \code{NetworkBlocks} are optional, but if any of them are missing, then
 \begin{itemize}
  \item = \cstr{ActivePowerDemand} (see above) is mandatory in \code{UCBlock}.
  \item = also the \code{NetworkData} (see above) is mandatory in \code{UCBlock}, unless the transmission network is a bus (that is, \cstr{NumberNodes} is not provided or it is \code{== 1}).
 \end{itemize}
 In particular, when a \code{NetworkBlock} is not defined for a given time instant t then one of these happen:
 \begin{itemize}
  \item = If \code{"NumberNodes" == 1} (or it is not provided) then a \code{BusNetworkBlock} is automatically constructed for that time instant, and the entry \code{ActivePowerDemand[ 0 , t ]} contains the active demand for $t$.
  \item = If \code{"NumberNodes" > 1}, then a \code{DCNetworkBlock} is automatically constructed for that time instant, it is provided with the \code{NetworkData} object (which must be present in \code{UCBlock}) and the row \code{ActivePowerDemand[ ... , t ]} contains the active demand of each node at time instant $t$.
 \end{itemize}
 %
 \item the \variable \cstr{GeneratorNode}, of type int and indexed over the set {\{0, ... , \code{NumberElectricalGenerators} - 1\}}; \code{GeneratorNode[ g ]} tells to which node of the transmission network, the specified electrical generator $g$ belongs. Note that this means that different electrical generators in the same \code{UnitBlock} can belong to different nodes of the transmission network. This is justified e.g. by hydro cascade units where different turbines can be rather far apart geographically, but still linked by (long) stretches of rivers. If \code{NumberElectricalGenerators == NumberUnits } (all \code{UnitBlock} have exactly one electrical generator), then this variable is indexed over \code{NumberUnits}. If \code{NumberNodes == 1} (say, it is not provided at all), then this variable need not be defined, since it is not loaded.
 %
 \item the \variable \cstr{HeatNode}, of type int and indexed over the \dimension \cstr{NumberHeatBlocks}; the entry \code{HeatNode[ h ]} tells to which node of the transmission network *all* the heat generators that are also electrical generators in the \code{HeatBlock} $h$ belong. Note that this implies that, unlike electrical generators in a \code{UnitBlock}, heat generators in a \code{HeatBlock} are always "geographically near to each other" so that they are necessarily attached to the same node of the transmission network (which is a reasonable assumption since heat, unlike say water, usually cannot travel much far). If \code{NumberHeatBlocks == 0} (say, it is not provided at all), then this variable need not be defined, since it is not loaded. This information is actually only used to determine in which Pollutant Zone a \code{HeatBlock} is located, in order to add the corresponding heat generators (that are not also electricity generators) to the pollution constraints. This means that also if \code{NumberPollutants == } (say, it is not provided at all) this variable is useless and therefore need not be defined, since it is not loaded. Finally, notice that for heat generators into a \code{HeatBlock} that also are electrical generators, this variable provides again an information that is already known, i.e., to which node they belong to (cf. \cstr{GeneratorNode} above). Of course *the two information must agree*, otherwise the input file is ill-defined and exception is thrown.
 %
 \item the \variable \cstr{HeatSet}, of type int and indexed over the set {\{0, ..., \code{NumberHeatGenerators} - 1\}}. If \code{HeatSet[ h ] = k < NumberElectricalGenerators}, then $k$ is the unique name of the electrical generator corresponding to the heat generator $h$; otherwise the heat generator $h$ is not also an electrical generator. If \code{NumberHeatBlocks == 0} (there is no \code{HeatBlock}) then this variable need not be defined, since it is not loaded. It is possible that different heat generators correspond to the same electrical generator (that is, \code{HeatSet[ h1 ] == HeatSet[ h2 ]} for some \code{h1 != h2}), but not vice-versa: a heat generator either corresponds to a specific electrical generator, or to no electrical generator (it is an heat-only generator);
 %
 \item the \variable \cstr{PowerHeatRho}, of type double and indexed over the \dimension \cstr{NumberUnits}: entry \code{PowerHeatRho[ i ]} is assumed to contain the electrical-power-to-heat ratio for *all generators* within unit $i$ (most likely, a single generator). This is only used in the constraints linking electrical units to heat units, hence if \code{NumberHeatBlocks == 0} (there are no \code{HeatBlock}) then this variable need not be defined, since it is not loaded;
 %
 \item the \dimension \cstr{NumberPrimaryZones} tells how many \cstr{primary spinning reserve zones} are there in the problem. The \dimension is optional, if it is not provided then it is taken to be $0$, which means that no primary reserve constraints are present in the problem;
 %
 \item the \variable \cstr{PrimaryZones}, of type int and indexed over the \dimension \cstr{NumberNodes}. The entry \code{PrimaryZones[ i ]} tells to which primary zone the node $i$ belongs: if \code{PrimaryZones[ i ] >= NumberPrimaryZones}, this means that node $i$ does not belong to any primary zone, and hence the corresponding electrical generators are not involved into the primary reserve constraints. If \code{NumberPrimaryZones == 0} (say, it is not provided at all) then this variable need not be defined, since it is not loaded. If \code{NumberPrimaryZones == 1} and this variable is not defined, then there is only one primary zone and all the nodes belong to it;
 %
 \item the \variable \cstr{PrimaryDemand}, of type double and indexed both over the \dimensions \cstr{NumberPrimaryZones} and \cstr{TimeHorizon}: entry \code{PrimaryDemand[ i , t ]} is assumed to contain the primary reserves requirement which are specified on the primary reserve zone $i$ in the time t. If \code{NumberPrimaryZones == 0} (say, it is not provided at all), then this variable need not be defined, since it is not loaded;
 %
 \item the \dimension \cstr{NumberSecondaryZones} tells how many \cstr{secondary spinning reserve zones} are there in the problem. The \dimension is optional, if it is not provided then it is taken to be $0$, which means that no secondary reserve constraints are present in the problem;
 %
 \item the \variable \cstr{SecondaryZones}, of type int and indexed over the \dimension \cstr{NumberNodes}. The entry \code{SecondaryZones[ i ]} tells to which secondary zone the node $i$ belongs: if \code{SecondaryZones[ i ] >= NumberSecondaryZones}, this means that node $i$ does not belong to any secondary zone, and hence the corresponding electrical generators are not involved into the secondary reserve constraints. If \code{NumberSecondaryZones == 0} (say, it is not provided at all) then this variable need not be defined, since it is not loaded. If \code{NumberSecondaryZones == 1} and this variable is not defined, then there is only one secondary zone and all the nodes belong to it;
 %
 \item the \variable \cstr{SecondaryDemand}, of type double and indexed both over the \dimensions \cstr{NumberSecondaryZones} and \cstr{TimeHorizon}: entry \code{SecondaryDemand[ i , t ]} is assumed to contain the secondary reserves requirement which are specified on the secondary reserve zone $i$ in the time t. If \code{NumberSecondaryZones == 0} (say, it is not provided at all), then this variable need not be defined, since it is not loaded;
 %
 \ \item the \dimension \cstr{NumberInertiaZones} tells how many \cstr{inertia constraints zones} are there in the problem. The \dimension is optional, if it is not provided then it is taken to be $0$, which means that no inertia constraints are present in the problem;
 %
 \item the \variable \cstr{InertiaZones}, of type int and indexed over the \dimension \cstr{NumberNodes}. The entry \code{InertiaZones[ n ]} tells to which inertia zone the node $n$ belongs: if \code{InertiaZones[ n ] >= NumberInertiaZones}, this means that node $n$ does not belong to any inertia zone, and hence the corresponding units are not involved into the inertia reserve constraints. If \code{NumberInertiaZones == 0} (say, it is not provided at all) then this variable need not be defined, since it is not loaded. If \code{NumberInertiaZones == 1} and this variable is not defined, then there is only one inertia zone and all the nodes belong to it;
%
 \item the \variable \cstr{InertiaDemand}, of type double and indexed both over the \dimensions \cstr{NumberInertiaZones} and \cstr{TimeHorizon}: entry \code{InertiaDemand[ i , t ]} is assumed to contain the inertia reserves requirement which are specified on the inertia reserve zone $i$ in the time t. If \code{NumberInertiaZones == 0} (say, it is not provided at all), then this variable need not be defined, since it is not loaded;
%
 \item the \dimension \cstr{NumberPollutants} containing the number of pollutants in the problem. The \dimension is optional, if it is not provided then it is taken to be $0$, which means that no pollutants constraints are present in the problem;
 %
 \item the \variable \cstr{NumberPollutantZones} of type int and indexed over the \dimension \cstr{NumberPollutants}: the entry \code{NumberPollutantZones[ p ]} is assumed to contain the number of pollutant zones associated with pollutant $p$. If \code{NumberPollutants == 0} (say, it is not provided) then this variable need not be defined, since it is not loaded. Then, all number of pollutant zones associated with each pollutant $p$ is computed as: \code{TotalNumberPollutantZones == NumberPollutantZone[ 0 ] + \dots + NumberPollutantZone[ NumberPollutants - 1 ]};
%
 \item the \variable \cstr{PollutantZones}, of type int and indexed over the \dimensions \cstr{NumberPollutants} and \cstr{NumberNodes}: the entry \code{PollutantZones[ p , n ]} tells to which pollutant zone associated with pollutant $p$ the node $n$ belongs. If \code{PollutantZones[ p , n ] >= NumberPollutantZones[ p ]}, this means that node $n$ does not belong to any pollutant zone, and hence the corresponding units are not involved into the pollutant budget constraints associated with pollutant $p$. If \code{NumberPollutants == 0} (say, it is not provided) then this variable need not be defined, since it is not loaded;
 %
 \item the \variable \cstr{PollutantBudget}, of type double and indexed over the set \{ 0 , ..., \code{TotalNumberPollutantZones} - 1 \}: the entry \code{PollutantBudget[ n ]} for \code{n == 0 , ..., TotalNumberPollutantZones - 1} is assumed to contain the pollutant budget (across all the time horizon) for the pair (zone of the pollutant , pollutant) corresponding to $n$. In another word, since the number of pollutant zones of each pollutant may not be equal with each otherit is useful (to avoid having to store PollutantBudget as an irregular matrix) to be able to assign a unique index \code{n = 0, 1, ..., TotalNumberPollutantZones - 1} to each pollutant budget of each pollutant zone. A mapping must be defined between each entry $n$ and the pair (zone of the pollutant , pollutant). The mapping is the obvious one: \code{UCBlock} has a set of pollutants \code{p = 0, 1, ..., NumberPollutants - 1}, and each pollutant $p$ may have several pollutant zones (see comments of variable \cstr{NumberPollutantZones} above). Thus, in general the mapping is:
 \begin{itemize}
  \item \code{n = 0} corresponds to the zone $0$ of pollutant $0$
  \item \code{n = 1} corresponds to the zone $1$ of pollutant $0$
  \item \code{\dots}
  \item \code{n = NumberPollutantZone[ 0 ] - 1} corresponds to the zone \code{NumberPollutantZone[ 0 ] - 1} of pollutant $0$
  \item \code{n = NumberPollutantZone[ 0 ] } corresponds to the zone $0$ of pollutant $1$
  \item \code{n = NumberPollutantZone[ 0 ] + 1} corresponds to the zone $1$ of pollutant $1$
  \item \code{\dots}
 \end{itemize}
 \smallskip
 \noindent
 If \code{NumberPollutants == 0} (say, it is not provided) then this variable need not be defined, since it is not loaded;
 %
 \item the \variable \cstr{PollutantRho}, of type double and indexed over three \dimensions which are \cstr{TimeHorizon} and \cstr{NumberPollutants} and the set \{0,..., \code{NumberElectricalGenerators} - 1\} (see comments above). The first \dimension can have size either $1$ or \cstr{TimeHorizon}. In the former case the entry \code{PollutantRho[ 0 , p , g ]} is assumed to contain the conversion factor of pollutant $p$ due to the electrical generator $g$ which is equal for all time instants $t$. Otherwise, the first \dimension has full size \code{TimeHorizon} and the entry \code{PollutantRho[ t , p , g ]} gives the conversion factor of pollutant $p$ due to the electrical generator $g$ for time t. If \code{NumberPollutants == 0} (it is not provided) then this variable need not be defined, since it's not loaded.
 %
 \item the \variable \cstr{PollutantHeatRho}, of type double and indexed over three \dimensions. The first \dimension can have size $1$ or \cstr{TimeHorizon}. The second and third \dimensions have sizes \cstr{NumberPollutants} and \cstr{NumberHeatBlocks}, respectively. If the first \dimension has size $1$, then the entry \code{PollutantRho[ 0 , p , h ]} is assumed to contain the conversion factor of pollutant $p$ due to the generation of *all* heat generators in \code{HeatBlock} $h$, which is equal for all time instants $t$. If, instead, the first \dimension has full size \cstr{TimeHorizon}, then the entry \code{PollutantRho[ t , p , h ]} gives the conversion factor of pollutant $p$ due to the generation of *all* heat generators in \code{HeatBlock} $h$ for time instant $t$. If \code{NumberPollutants == 0} (say, it is not provided) then this variable does not need be defined, since it is not loaded. If \code{NumberHeatBlocks == 0} (there is no \code{HeatBlock}) then this variable need not be defined, since it is not loaded.
\end{itemize}

\subsection {\code{UnitBlock}}

The \code{UnitBlock} class, which derives from the \Block, defines a base class for any possible \cstr{unit} that can be attached to a \code{UCBlock}. A unit is in general a set of electrical generators tied together by some technical constraints, although many units actually correspond to only one generator. The base \code{UnitBlock} class only has very basic information that can characterize almost any different kind of unit:
%
\begin{itemize}
 \item The time horizon of the problem;
 %
 \item The number of generators in the unit ($1$ by default, see \code{get\_number\_generators()});
 %
 \item Four \code{boost::multi\_array< ColVariable, 2 >} objects, that are used to store the information regarding:
 %
     \begin{itemize}
      \item the commitment of the generators in the unit;
      %
      \item the primary spinning reserve of the generators in the unit;
      %
      \item the secondary spinning reserve of the generators in the unit;
      %
      \item the active power produced by the generators in the unit;

     \end{itemize}

\end{itemize}
%
Each of the \code{boost::multi\_array< ColVariable, 2 >} has as first \dimension the time horizon and as second \dimension the number of generators (as returned \code{get\_number\_generators()}). There are two possible cases:
\begin{itemize}
 \item if some \code{boost::multi\_array< ColVariable, 2 >} is empty(), then the corresponding variable does not exist (for instance, the generator in the unit may not have reserve);
 %
 \item otherwise, the \code{boost::multi\_array< ColVariable, 2 >}, say $M$, must have \code{f\_time\_horizon} rows and \code{get\_number\_generators()} columns: each element $M[ t , g ]$ gives the variable for time step $t$ of generator $g$.
\end{itemize}
%
The class also outputs some general information regarding how the active power and/or commitment status of each generator of the unit at a given time instant impact the unit's capability of satisfying inertia constraints, and the fixed consumption (if any) of each generator in the  unit when it is off.
\smallskip
\noindent
Besides the mandatory \cstr{type} attribute of any \dBlock, the \group representing the \code{UnitBlock} should contain the following:
%
\begin{itemize}
 \item the \dimension \cstr{TimeHorizon} containing the time horizon. The \dimension is optional because the same information may be passed via the method \code{set\_time\_horizon()}, or directly retrieved from the father if it is a \code{UCBlock}; see the comments to \code{set\_time\_horizon()} for details;
 %
 \item the \dimension \cstr{NumberIntervals} that is provided to allow that all time-dependent data in the \code{UnitBlock} can only change at a subset of the time instants of the time interval, being therefore piecewise-constant (possibly, constant). \cstr{NumberIntervals} should therefore be \code{<=} \cstr{TimeHorizon}, with three distinct cases:
 %
 \begin{itemize}
  \item  \cstr{NumberIntervals} \code{<= 1}, which is taken to mean \cstr{NumberIntervals} \code{== 1}; this is what is assumed if the \dimension, that is optional, is not there. This means that the value of each relevant data in the \code{UCBlock} is the same for each time instant \code{0, \dots,} \cstr{TimeHorizon} \code{ - 1} in the time horizon. In this case, the variable \cstr{ChangeIntervals} (see below) is ignored;
  %
  \item \code{1 < }\cstr{NumberIntervals} \code{<} \cstr{TimeHorizon}, which means that in some time instants, *but not all of them*, the values of some of the relevant data are changing; the intervals are then described in variable \cstr{NumberIntervals};
  %
  \item \cstr{NumberIntervals} \code{==} \cstr{TimeHorizon},  which means that values of the relevant data changes at every time interval (in principle; of course there is nothing preventing the same value to be repeated in the \code{netCDF} input). Also in this case the variable \cstr{NumberIntervals} is ignored, since it is useless;
  %
 \end{itemize}
 %
 Note that this (together with \cstr{NumberIntervals}, if defined) obviously sets the \cstr{maximum frequency} at which data can change; if some data changes less frequently (say, it is constant), then the same value will have to be repeated. Individual data can also have specific provisions for the case where the data is all equal despite \cstr{NumberIntervals} saying differently.
 %
 \item the \variable \cstr{ChangeIntervals}, of type integer and indexed over the \dimension \cstr{NumberIntervals}. The time horizon is subdivided into \code{NumberIntervals = k} of the form $[ 0 , i_1 ]$,$[ i_1 + 1 , i_2 ]$, \dots $[ i_{k-1} + 1, TimeHorizon - 1 ]$; \cstr{ChangeIntervals} then has to contain $[ i_1 , i_2 , \dots i_{k-1} ]$ . Note that, therefore, \cstr{ChangeIntervals} has one significant value less than \cstr{NumberIntervals}, which means that \code{ChangeIntervals[ NumberIntervals - 1 ]} is ignored. Anyway, the whole variable is ignored if either \cstr{NumberIntervals} \code{<= 1} (such as if it is not defined), or \cstr{NumberIntervals} \code{>=} \cstr{TimeHorizon}.
\end{itemize}

\subsubsection {\code{ThermalUnitBlock}}

The \code{ThermalUnitBlock} class derives from \code{UnitBlock} and implements a \cstr{reasonably standard} thermal unit of a Unit Commitment Problem. That is, the class is designed in order to give mathematical formulation to describe the operation of large set of conventional power plants (such as nuclear, hard coal, gas turbine, gas, combined cycle, oil, ...) which are directly connected to the transmission grid.
\smallskip
\noindent
Besides the mandatory \cstr{type} attribute of any \dBlock, the group must contain all the data required by the base \code{UnitBlock}, as described in the comments to \code{UnitBlock::deserialize}( \code{netCDF::NcGroup} ). In particular, we refer to that description for the crucial \dimensions \cstr{TimeHorizon}, \cstr{NumberIntervals} and \cstr{ChangeIntervals}. The \code{netCDF::NcGroup} must then also contain:
%
\begin{itemize}
 \item  the \variable \cstr{MinPower}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{MnP[ t ]} that, for each time instant $t$, contains the minimum active power output value of the unit for the corresponding time step. If \cstr{MinPower} has length $1$ then \code{MnP[ t ]} contains the same value for all $t$. Otherwise, \code{MinPower[ i ]} is the fixed value of \code{MnP[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. Note that it must be \code{MnP[ t ] >= 0} for all $t$. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{changeIntervals}, which in fact is not loaded;
 %
 \item  the \variable \cstr{MaxPower}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{MxP[ t ]} that, for each time instant $t$, contains the maximum active power output value of the unit for the corresponding time step. If \cstr{MaxPower} has length $1$ then \code{MxP[ t ]} contains the same value for all $t$. Otherwise, \code{MaxPower[ i ]} is the fixed value of \code{MxP[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. Note that it must be \code{MxP[ t ] >= 0} for all $t$. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{changeIntervals}, which in fact is not loaded;
%
 \item  the \variable \cstr{DeltaRampUp}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{DP[ t ]} that, for each time instant $t$, contains the ramp-up value of the unit for the corresponding time step, i.e., the maximum possible increase of active power production w.r.t. the power that had been produced in time instant \code{t - 1}, if any. This variable is optional; if it is not provided then it is assumed that \code{DP[ t ] == MxP[ t ]}, i.e., the unit can ramp up by an arbitrary amount, i.e., there are no ramp-up constraints. If \cstr{DeltaRampUp} has length $1$ then \code{DP[ t ]} contains the same value for all $t$. Otherwise, \code{DeltaRampUp[ i ]} is the fixed value of \code{DP[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
%
 \item  the \variable \cstr{DeltaRampDown}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{DM[ t ]} that, for each time instant $t$, contains the ramp-down value of the unit for the corresponding time step, i.e., the maximum possible decrease of active power production w.r.t. the power that had been produced in time instant \code{t - 1}, if any. This variable is optional; if it is not provided then it is assumed that \code{DM[ t ] == MxP[ t ]}, i.e., the unit can ramp down by an arbitrary amount, i.e., there are no ramp-down constraints. If \cstr{DeltaRampDown} has length $1$ then \code{DM[ t ]} contains the same value for all $t$. Otherwise, \code{DeltaRampDown[ i ]} is the fixed value of \code{DM[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
%
 \item the \variable \cstr{PrimaryRho}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{PR[ t ]} that, for each time instant $t$, contains the maximum possible fraction of active power that can be used as primary reserve value of the unit for the corresponding time step. This variable is optional; if it is not provided then it is assumed that this unit may not be capable of producing any primary reserve, which correspond to \code{PR[ t ] == 0} for all $t$. If \cstr{PrimaryRho} has length $1$ then \code{PR[ t ]} contains the same value for all $t$. Otherwise, \code{PrimaryRho[ i ]} is the fixed value of \code{PR[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
 %
 \ \item the \variable \cstr{SecondaryRho}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{SR[ t ]} that, for each time instant $t$, contains the maximum possible fraction of active power that can be used as secondary reserve value of the unit for the corresponding time step. This variable is optional; if it is not provided then it is assumed that this unit may not be capable of producing any secondary reserve, which correspond to \code{SR[ t ] == 0} for all $t$. If \cstr{SecondaryRho} has length $1$ then \code{SR[ t ]} contains the same value for all $t$. Otherwise, \code{SecondaryRho[ i ]} is the fixed value of \code{SR[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
 %
 \item the \variable \cstr{QuadTerm}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{A[ t ]} that, for each time instant $t$, contains the quadratic term of power cost function of the unit for the corresponding time step. This variable is optional; if it is not provided then it is assumed that \code{A[ t ] == 0}, i.e., the cost of the unit is linear in the produced power. If \cstr{QuadTerm} has length $1$ then \code{A[ t ]} contains the same value for all $t$. Otherwise, \code{QuadTerm[ i ]} is the fixed value of \code{A[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
%
 \item the \variable \cstr{StartUpCost}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{SC[ t ]} that, for each time instant $t$, contains the start up cost value of the unit for the corresponding time step. This variable is optional; if it is not provided then it is assumed that \code{SC[ t ] == 0}, i.e., this unit may not have any start up cost. If \cstr{StartUpCost} has length $1$ then \code{SC[ t ]} contains the same value for all $t$. Otherwise, \code{StartUpCost[ i ]} is the fixed value of \code{SC[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
 %
 \item the \variable \cstr{LinearTerm}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{B[ t ]} that, for each time instant $t$, contains the linear term of power cost function of the unit for the corresponding time step. This variable is optional; if it is not provided then it is assumed that \code{B[ t ] == 0}, i.e., the cost of the unit has no linear dependence on the produced power (say, only the quadratic one). If \cstr{LinearTerm} has length $1$ then \code{B[ t ]} contains the same value for all $t$. Otherwise, \code{LinearTerm[ i ]} is the fixed value of \code{B[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
 %
 \item the \variable \cstr{ConstTerm}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{C[ t ]} that, for each time instant $t$, contains the const term of power cost function of the unit for the corresponding time step. This variable is optional; if it is not provided then it is assumed that \code{C[ t ] == 0}, i.e.,  the cost of the unit has no fixed term, only those depending (linearly or quadratically) on the produced power. If \cstr{ConstTerm} has length $1$ then \code{C[ t ]} contains the same value for all $t$. Otherwise, \code{ConstTerm[ i ]} is the fixed value of \code{C[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
 %
 \item the scalar \variable \cstr{InitialPower}, of type double and not indexed over any \dimension. This variable indicates the amount of the power that the unit was producing at time instant $-1$, i.e., before the start of the time horizon; this is necessary to compute the ramp-up and ramp-down constraints. Clearly, it must be that \code{MaxPower >= InitialPower >= MinPower} if the unit was "on" at time instant $-1$, and it must be that \code{InitialPower == 0} if the unit was "off" at time instant $-1$. The on/off status of the unit is also encoded by the scalar variable \code{InitUpDownTime}: in particular, \code{InitUpDownTime > 0} then the unit was on at time instant $-1$, and therefore \code{InitialPower >= MinPower} must hold, while if \code{InitUpDownTime <= 0} then the unit was off at time instant $-1$, and therefore \code{InitialPower == 0} by definition. In fact, if \code{InitUpDownTime <= 0} then this variable need not be defined since it is not loaded.
 %
 \item the scalar \variable \cstr{InitUpDownTime}, of type Int64 and not indexed over any \dimension and indicates the initial time to generating the unit. If \code{InitUpDownTime > 0}, this means that the unit has been on for \code{InitUpDownTime} time stamps prior to time stamp $0$ (the beginning of the horizon). If, instead, \code{InitUpDownTime <= 0}, this means that the unit has been off for \code{- InitUpDownTime} time stamps prior to time stamp $0$; note that \code{InitUpDownTime == 0} means that the unit has been just shut down at the end of time instant $-1$, i.e., the beginning of time instant $0$;
 %
 \item the positive scalar \variable \cstr{MinUpTime}, of type UInt64 and not indexed over any \dimension, which indicates the minimum allowed up time in this unit. This variable is optional, if it is not provided it is taken to be \code{MinUpTime == 0}, which mean that the unit can shut down in the very same time stamp in which it starts up.
 %
 \item the positive scalar \variable \cstr{MinDownTime}, of type UInt64 and not indexed over any \dimension, which indicates the minimum allowed down time in this unit. This variable is optional, if it is not provided it is taken to be \code{MinDownTime == 0}, which mean that the unit can start up in the very same time stamp in which it starts up.
 %
 \item  the \variable \cstr{FixedConsumption}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{FC[ t ]} that, for each time instant $t$, contains the fixed consumption of the power plant if it is OFF at time $t$. The variable is optional; if it is not defined, \code{FC[ t ] == 0} for all time instants. If it has size $1$, then \code{FC[ t ] == FixedConsumption[ 0 ]} for all $t$, regardless to what \cstr{NumberIntervals} says. Otherwise, \code{FixedConsumption[ i ]} is the fixed value of \code{FC[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ], ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}.
%
\item  the \variable \cstr{InertiaCommitment}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{IC[ t ]} that, for each time instant $t$, contains the contribution that the unit can give to the inertia constraint for the sole fact that is is on (basically, the constant to be multiplied to the commitment variable) at time $t$. The variable is optional; if it is not defined, \code{IC[ t ] == 0} for all time instants. If it has size $1$, then \code{IC[ t ] == InertiaCommitment[ 0 ]} for all $t$, regardless to what \cstr{NumberIntervals} says. Otherwise, \code{InertiaCommitment[ i ]} is the fixed value of \code{IC[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ], ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}.

\end{itemize}

\subsubsection {\code{HydroUnitBlock}}
The \code{HydroUnitBlock} class derives from \code{UnitBlock} and implements a \cstr{reasonably standard} hydro unit of a Unit Commitment Problem. That is, the class is designed in order to give mathematical formulation to describe the operation of large set of hydro storage. To model complex reservoir systems several technical parameters have to be considered. These are divided into reservoir-specific parameters, the hydro links connecting the reservoirs and finally the turbine/pump parameters. The values are collected within a reservoir database, a hydro-link database and a turbine/pump-database.
\smallskip
\noindent
Besides the mandatory \cstr{type} attribute of any \dBlock, the group must contain all the data required by the base \code{UnitBlock}, as described in the comments to \code{UnitBlock::deserialize}( \code{netCDF::NcGroup} ). In particular, we refer to that description for the crucial \dimensions \cstr{TimeHorizon}, \cstr{NumberIntervals} and \cstr{ChangeIntervals}. The \code{netCDF::NcGroup} must then also contain:
%
\begin{itemize}
 \item The \dimension \cstr{NumberReservoirs} containing the number of all reservoirs (or nodes) in the \code{HydroUnitBlock}. The \dimension is optional, if it is not provided then it is taken to be \code{== 1}, which means that the (in principle) cascading hydro system is actually single hydro reservoir. Note, however, that a single reservoir can still have multiple hydro generating units (see \cstr{NumberArcs} below).
 %
 \item The \dimension \cstr{NumberArcs} containing the set of arcs (or units) connecting the reservoirs in cascading system. Each arc represents either a turbine generating electricity by converting potential energy of water going downhill, or a pump consuming electricity for moving water uphill.
 %
 \item The \variable \cstr{StartArc}, of type int and indexed over the \dimension \cstr{NumberArcs}; the r-th entry of the variable is the starting point of the arc (a number in \code{0, \dots, NumberReservoirs - 1}). Note that arcs are oriented; that is, a positive flow along arc $r$ (turbine) means that water is being taken away from \code{StartArc[ r ]} and delivered to \code{EndArc[ r ]} (see next), a negative flow (pump) means vice-versa. Note that reservoir names here go from $0$ to \code{NumberReservoirs - 1}.
 %
 \item The \variable \cstr{EndArc}, of type int and indexed over the \dimension \cstr{NumberArcs}; the r-th entry of the variable is the ending point of the arc; this is a number in \code{0, \dots, NumberReservoirs}. Note: this is \code{NumberReservoirs} and *not* \code{NumberReservoirs - 1}, because arcs can end in the "fake" reservoir \code{NumberReservoirs}. This indicates that water that flows along that arc "goes away from the system" and it is no longer counted, because it can no longer be used to produce electricity further down the river, or pumped back into one of its reservoirs. Indeed, there will be something like "the most downstream turbines": after water has been used there, it just goes away down some river and does not go to any other reservoir. Arcs are oriented (see above); \code{StartArc[ r ] == EndArc[ r ]} (a self-loop) is not allowed, but multiple arcs between the same pair of reservoirs are. Indeed, often the same physical equipment can be used both as a turbine and as a pump; in our model these are represented as two parallel arcs (but with different upper and lower flow capacity, see \cstr{MinFlow} and \cstr{MaxFlow} below).
 %
 \item The \variable \cstr{MinFlow}, of type double and indexed over both \dimensions \cstr{NumberIntervals} and \cstr{NumberArcs}. The first \dimension may have either size $1$ or size \code{NumberIntervals} whereas the second one always has size \cstr{NumberArcs} (if the variable is provided at all). This is meant to represent the matrix \code{MinF[ t , l ]} which, for each time instant $t$ and each arc $l$, contains the minimum flow value of the unit. This variable is optional; if it is not provided then it is assumed that \code{MinF[ t , l ]== 0}, i.e., the minimum flow of the unit is zero. If the first \dimension has size $1$ then the entry \code{MinF[ 0 , l ]} gives the fixed minimum flow value of the unit for all time steps and each arc $l$. Otherwise, \code{MinFlow[ i , l ]} is the fixed value of \code{MinF[ t , l ]} for all time $t$ and arc $l$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ]= 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
 %
 \item The \variable \cstr{MaxFlow}, of type double and indexed over both \dimensions \cstr{NumberIntervals} and \cstr{NumberArcs}. The first \dimension may have either size $1$ or size \code{NumberIntervals} whereas the second one always has size \cstr{NumberArcs} (if the variable is provided at all). This is meant to represent the matrix \code{MaxF[ t , l ]} which, for each time instant $t$ and each arc $l$, contains the maximum flow value of the unit. This variable is optional; if it is not provided then it is assumed that \code{MaxF[ t , l ]== 0}, i.e., the maximum flow of the unit is zero. If the first \dimension has size 1 then the entry \code{MaxF[ 0 , l ]} gives the fixed maximum flow value of the unit for all time steps and each arc $l$. Otherwise, \code{MaxFlow[ i , l ]} is the fixed value of \code{MaxF[ t , l ]} for all time $t$ and arc $l$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ]= 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
\end{itemize}
\smallskip
\noindent
Note: \cstr{MinFlow} and \cstr{MaxFlow} values can be either positive or negative (or zero); whenever \code{MinF[ t , l ] < MaxF[ t , l ] <= 0} for each $t$ and $l$, the unit is considered a pump and whenever \code{0 <= MinF[ t , l ] < MaxF[ t , l ]}, the unit is considered a turbine. Note that an arc must *always* be the same kind for *all* instants, i.e., it is not allowed that a unit suddenly changes between a turbine and a pump, or vice-versa. This is because the flow-to-active-power function of turbines is a convex piecewise function with possibly many pieces (see \cstr{NumberPieces}, \cstr{LinearTerm}, \cstr{ConstantTerm} below) , whereas the flow-to-active-power function of a pump is a simple linear function. In other words, the "number of pieces" of a turbine is \code{>= 1}, whereas the "number of pieces" of a pump is necessarily equal to $1$. In reality, the same equipment can sometimes be used both as a pump and as a turbine. In our model this is be accounted for by artificially splitting the unit into \cstr{two units}, a pump one and a turbine one, which must be done at the data processing stage. This causes the possible problem that at some time instant both the pump and the turbine be active, which is not possible in practice. This is unlikely to happen (because pumps consume more than turbines produce for the same amount of water, so this would be uneconomical), but should it ever happen, this occurrence is not handled in our model (which lets it happen).

\begin{itemize}
 \item The \variable \cstr{MinVolumetric}, of type double and indexed over both \dimensions \cstr{NumberReservoirs} and \cstr{NumberIntervals}. The first \dimension always has size \cstr{NumberReservoirs} (if it is provided at all), whereas the second one may have size one or size \cstr{NumberIntervals}. This is meant to represent the matrix \code{MinV[ r , t ]} which, for each reservoir $r$ at each time instant $t$ contains the minimum volumetric value of the unit for each reservoir and corresponding time step. It must be that \code{0 <= MinV[ r , t ] < MaxV[ r , t ]} for all $r$ and $t$ and . This variable is optional; if it's not provided then it is assumed that \code{MinV[ r , t ] == 0}, i.e., the minimum volumetric of the unit is zero. If the second \dimension has size 1 then the entry \code{MinV[ r , 0 ]} gives the fixed minimum volumetric value of the unit for each reservoir $r$ along all the time horizon. Otherwise, \code{MinVolumetric[ r , i ]} is the fixed value of \code{MinV[ r , t ]} for reservoir $r$ and all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
 %
 \item The \variable \cstr{MaxVolumetric}, of type double and indexed over both \dimensions \cstr{NumberReservoirs} and \cstr{NumberIntervals}. The first \dimension always has size \cstr{NumberReservoirs} (if it is provided at all), whereas the second one may have size one or size \cstr{NumberIntervals}. This is meant to represent the matrix \code{MaxV[ r , t ]} which, for each reservoir $r$ at each time instant $t$ contains the maximum volumetric value of the unit for each reservoir and corresponding time step. It must be that \code{0 <= MinV[ r , t ] < MaxV[ r , t ]} for all $r$ and $t$ and . This variable is optional; if it's not provided then it is assumed that \code{MaxV[ r , t ] == 0}, i.e., the maximum volumetric of the unit is zero. If the second \dimension has size 1 then the entry \code{MaxV[ r , 0 ]} gives the fixed maximum volumetric value of the unit for each reservoir $r$ along all the time horizon. Otherwise, \code{MaxVolumetric[ r , i ]} is the fixed value of \code{MaxV[ r , t ]} for reservoir $r$ and all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
\end{itemize}
Note: It may happen that \code{MinV[ r , t ] == MaxV[ r , t ]}, but only *in a subset of the time instants*. For instance, the user may want to fix the final value of the reservoir, for whatever reason. So, if \code{MinV} and \code{MaxV} are independent of t, then \code{MinV[ r ] < MaxV[ r ]} must surely happen. If, instead, they depend on $t$, then equality can be accepted at some instants (but not all of them).
\smallskip
\noindent
Besides the mandatory \cstr{type} attribute of any \dBlock, the group must contain all the data required by the base \code{UnitBlock}, as described in the comments to \code{UnitBlock::deserialize}( \code{netCDF::NcGroup} ). In particular, we refer to that description for the crucial \dimensions \cstr{TimeHorizon}, \cstr{NumberIntervals} and \cstr{ChangeIntervals}. The \code{netCDF::NcGroup} must then also contain:
\begin{itemize}

 \item The \variable \cstr{Inflows}, of type double and indexed over both \dimensions \cstr{NumberReservoirs} and \cstr{TimeHorizon}. This is meant to represent the matrix \code{InF[ r , t ]} which, for each reservoir $r$, contains the amount of water that "naturally" enters into reservoir $r$ (because of rain, ice melting, non-controlled rivers flowing, and of course net of water leaving by evaporation, human consumption etc.) during time al the time interval $t$, and therefore that is available in the reservoir at the end of time step $t$ (hence, the beginning of time step $t + 1$, if any). This variable is optional; if it isn't defined, it is taken to be zero. \cstr{Inflows} can be either positive or negative.
 %
 \item The \variable \cstr{MinPower}, of type double and indexed over both \dimensions \cstr{NumberIntervals} and \cstr{NumberArcs}. The first \dimension may have either size $1$ or size \cstr{NumberIntervals}, whereas the second one always has size \cstr{NumberArcs} (if it is provided at all). This is meant to represent the matrix \code{MinP[ t , l ]} which, for each time instant $t$ at each arc $l$ contains the minimum power value of the unit; it must be that \code{MinP[ t , l ] < MaxP[ t , l ]} for each time instant $t$ and each arc $l$. This variable is optional; if it is not provided then it is assumed that \code{MinP[ t , l ] == 0}, i.e., the minimum power of all units is zero(which means, each unit is a turbine). If the first \dimension has size $1$ then the entry \code{MinP[ 0 , l ]} is assumed to contain the minimum power of arc $l$ for all time instants. Otherwise, \code{MinPower[ i , l ]} is the fixed value of \code{MinP[ t , l ]} for arc $l$ and all time $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{NumberIntervals}, which in fact is not loaded.
 %
 \item The \variable \cstr{MaxPower}, of type double and indexed over both \dimensions \cstr{NumberIntervals} and \cstr{NumberArcs}. The first \dimension may have either size $1$ or size \cstr{NumberIntervals}, whereas the second one always has size \cstr{NumberArcs} (if it is provided at all). This is meant to represent the matrix \code{MaxP[ t , l ]} which, for each time instant $t$ at each arc $l$ contains the maximum power value of the unit; it must be that \code{MinP[ t , l ] < MaxP[ t , l ]} for each time instant $t$ and each arc $l$. This variable is optional; if it is not provided then it is assumed that \code{MaxP[ t , l ] == 0}, i.e., the maximum power of all units is zero(which means, each unit is a turbine). If the first \dimension has size $1$ then the entry \code{MaxP[ 0 , l ]} is assumed to contain the maximum power of arc $l$ for all time instants. Otherwise, \code{MaxPower[ i , l ]} is the fixed value of \code{MaxP[ t , l ]} for arc $l$ and all time $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{NumberIntervals}, which in fact is not loaded.
%
 \item The \variable \cstr{DeltaRampUp}, of type double and indexed over both \dimensions \cstr{NumberIntervals} and \cstr{NumberArcs}. The first \dimension may have either size $1$ or size \cstr{NumberIntervals}, whereas the second one always has size \cstr{NumberArcs}  (if it is provided at all). This is meant to represent the matrix \code{DP[ t , l ]} which contains the maximum possible increase of the flow rate at time instant $t$ for arc $l$. This variable is optional; if it is not provided then it is assumed that \code{DP[ t , l ] == MaxP[ t , l ] - MinP[ t , l ]}, i.e., all units can ramp up by an arbitrary amount, i.e., there are no ramp-up constraints. If the first \dimension has size 1 then the entry \code{DP[ 0 , l ]} is assumed to contain the maximum possible increase of the flow rate of arc $l$ for all time instants. Otherwise, \code{DeltaRampUp[ i , l ]} is the fixed value of \code{DP[ t , l ]} for arc $l$ and all time $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{NumberIntervals}, which in fact is not loaded.
 %
 \item The \variable \cstr{DeltaRampDown}, of type double and indexed over both \dimensions \cstr{NumberIntervals} and \cstr{NumberArcs}. The first \dimension may have either size $1$ or size \cstr{NumberIntervals}, whereas the second one always has size \cstr{NumberArcs} (if it is provided at all). This is meant to represent the matrix \code{DM[ t , l ]} which contains the maximum possible decrease of the flow rate at each time instant $t$ of each arc $l$. This variable is optional; if it is not provided then it is assumed that \code{DM[ t , l ] == MaxP[ t , l ] - MinP[ t , l ]}, i.e., the unit can ramp down by an arbitrary amount, i.e., there are no ramp-down constraints. If first \dimension has size $1$ then the entry \code{DM[ 0 , l ]} is assumed to contain the maximum possible decrease of the flow rate of arc $l$ for all time instants. Otherwise, \code{DeltaRampDown[ i , l ]} is the fixed value of \code{DM[ t , l ]} for arc $l$ and all time $t$  in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{NumberIntervals}, which in fact is not loaded.
 %
 \item The \variable \cstr{PrimaryRho}, of type double and indexed both over the \dimensions \cstr{NumberIntervals} and \cstr{NumberArcs}. The first \dimension may have either size $1$ or size \cstr{NumberIntervals}, whereas the second one always has size \cstr{NumberArcs} (if it is provided at all). This is meant to represent the matrix \code{PR[ t , l ]} which, for each time instant $t$ and arc $l$, contains the maximum possible fraction of active power that can be used as primary reserve. This variable is optional, when it's not present then \code{PR[ t , l ] == 0} for all $t$ and $l$, i.e., the unit is not capable of producing any primary reserve. Note that only turbines can produce primary reserve, i.e., \code{PR[ t , l ] > 0 ==> MaxP[ t , l ] > 0}. If the first \dimension has size $1$ then the entry \code{PR[ 0 , l ]} is assumed to contain the maximum possible fraction of active power that can be used as primary reserve by arc $l$ for all time instants. Otherwise, \code{PrimaryRho[ i , l ]} is the fixed value of \code{PR[ t , l ]} for arc $l$ and all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{NumberIntervals}, which in fact is not loaded.
 %
 \item The \variable \cstr{SecondaryRho}, of type double and indexed both over the \dimensions \cstr{NumberIntervals} and \cstr{NumberArcs}. The first \dimension may have either size $1$ or size \cstr{NumberIntervals}, whereas the second one always has size \cstr{NumberArcs} (if it is provided at all). This is meant to represent the matrix \code{SR[ t , l ]} which, for each time instant $t$ and arc $l$, contains the maximum possible fraction of active power that can be used as secondary reserve. This variable is optional, when it's not present then \code{SR[ t , l ] == 0} for all $t$ and $l$, i.e., the unit is not capable of producing any secondary reserve. Note that only turbines can produce secondary reserve, i.e., \code{SR[ t , l ] > 0 ==> MaxP[ t , l ] > 0}. If the first \dimension has size $1$ then the entry \code{SR[ 0 , l ]} is assumed to contain the maximum possible fraction of active power that can be used as secondary reserve by arc $l$ for all time instants. Otherwise, \code{SecondaryRho[ i , l ]} is the fixed value of \code{SR[ t , l ]} for arc $l$ and all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{NumberIntervals}, which in fact is not loaded.
 %
 \item The \variable \cstr{NumberPieces}, indexed over the \dimension \cstr{NumberArcs}. \code{NumberPieces[ l ]} tells how many pieces the concave flow-to-active-power function has for unit (arc) $l$. Note that pumps must necessarily have exactly one piece. The sum over all i of \code{NumberPieces[ i ]} is the total number of pieces (say, \cstr{TotalNumberPieces}). Clearly, \code{TotalNumberPieces >= NumberArcs}; if the flow-to-active-power function for all turbines only have one piece (those of pumps necessarily are so), then \code{TotalNumberPieces == NumberArcs} and there is no need to define this variable. If, instead, if it is defined, then should always be such that \code{TotalNumberPieces >= NumberArcs}.
 %
 \item The \variable \cstr{LinearTerm}, of type double and indexed over the set \code{\{0 , \dots, TotalNumberPieces - 1\}} (see \cstr{NumberPieces}). \code{LinearTerm[ h ]} gives the linear term $a_h$ of the linear function $a_h * f + b_h$ that defines the concave flow-to-active-power function for some unit; the total function if $F2AP( t ) = min \{ a_h * f + b_h , h \in H \}$ for some finite set $H$ that depends on the individual unit. It is then necessary to be able to assign a unique index \code{h = 0, 1, \dots, TotalNumberPieces - 1} to each pair ( unit , linear function $a_h * f + b_h$ ). When \code{TotalNumberPieces == NumberArcs}, the index is the same as \code{i = 0, 1, \dots, NumberArcs - 1} (there is a one-to-one correspondence between each (unit) arc and each piece). When, instead, \code{TotalNumberPieces > NumberArcs}, a mapping must be defined. The mapping is the obvious one: each index of \code{i = 0, 1, \dots, NumberArcs - 1}, corresponds with a unit (arc), and the linear functions for each unit (arc) also have some natural ordering. Thus, in general the mapping is:
 \begin{itemize}
  \item piece $0$ = first piece of unit (arc) $0$
  \item piece $1$ = second piece of unit (arc) $0$
  \item \code{\dots}
  \item piece \code{NumberPieces[ 0 ] - 1 =} last piece of unit (arc) $0$
  \item piece \code{NumberPieces[ 0 ] =} first piece of unit (arc) $1$
  \item piece \code{NumberPieces[ 0 ] + 1 =} second piece of unit (arc) $1$
  \item \code{\dots}
 \end{itemize}
 which of course boils down to \cstr{h = i} when each arc has exactly one piece.
 \item The \variable \cstr{ConstantTerm}, of type double and indexed over the set \code{\{0 , \dots, TotalNumberPieces - 1\}}. \code{ConstantTerm[ h ]} gives the constant term $b_h$ of the linear function $a_h * f + b_h$ that defines the concave flow-to-active-power function for some unit; see the comments to \cstr{LinearTerm} for details.
 %
 \item The \variable \cstr{InertiaPower}, of type double and indexed both over the \dimensions \cstr{NumberIntervals} and \cstr{NumberArcs}. The first \dimension may have either size $1$ or size \cstr{NumberIntervals} whereas the second one always has size \cstr{NumberArcs} (if it is provided at all). This is meant to represent the matrix \code{IP[ t , l ]} which, for each time instant $t$ and arc $l$, contains the contribution that the unit can give to the inertia constraint which depends on the active power that it is currently generating (basically, the constant to be multiplied to the active power variable) at time $t$ for arc $l$. The variable is optional; if it is not defined, \code{IP[ t , l ] == 0} for each time instants $t$ and arc $l$. If the first \dimension has size $1$ then the entry \code{IP[ 0 , l ]} is assumed to contain the the inertia power value for arc $l$ and all time instants $t$. Otherwise, \code{InertiaPower[ i , l ]} is the fixed value of \code{IP[ t , l ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ]= 0} and all $l$. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon} then the mapping clearly does not require \code{ChangeIntervals}, which in fact is not loaded.
 %
 \item The \variable \cstr{InitialFlowRate}, of type double and indexed over the \dimension \cstr{NumberArcs}. Each entry \code{InFR[ i ]} indicates the amount of the flow that was going along arc $i$ at time instant $-1$. This is necessary to compute ramp-up and ramp-down limits (cf. \cstr{DeltaRampUp} and \cstr{DeltaRampDown}), and therefore it is useless if there are no ramp constraints on *any* unit (arc), in which case it is not loaded.
 %
 \item The \variable \cstr{InitialVolumetric}, of type double and indexed over the \dimension \cstr{NumberReservoirs}. Each entry \code{InV[ r ]} indicates the volumes of water in reservoir $r$ at time instant $-1$.
 %
 \item The negative or positive scalar \variable \cstr{UphillFlow}, of type \code{Int64} and indexed over the \dimension \cstr{NumberArcs}. Each entry \code{UpF[ l ]} indicates the uphill flow delay for each unit (arc) $l$; the nontrivial concept is detailed below. This variable is optional, if it is not provided it is taken to be \code{UpF[ l ] == 0}.
 %
 \item The positive scalar \variable \cstr{DownhillFlow}, of type UInt64 and indexed over the \dimension \cstr{NumberArcs}. Each entry \code{DnF[ l ]} indicates the downhill flow delay for each arc (unit) $l$. This variable is optional, if it is not provided it is taken to be \code{DnF[ l ] == 0}.
\end{itemize}

The last two quantities require some comment. Let us assume that we have any arc $l$, with \code{( StartArc[ l ] = n , EndArc[ l ] = n' )}, which corresponds to (say) a turbine. This means that a positive flow along $l$ implies that water is being taken away from $n$ and delivered to $n'$, passing through the turbine to produce flow, as graphically depicted below:
\\
\\

$  \backslash n / >==============> [ TURBINE ] >================>  \backslash n' / $
\\

\hspace{25mm}  $ UpF[ l ]$    \hspace{53mm}     $ DnF[ l ]$
\\

The issue here is that the turbine can be geographically far enough from both $n$ and $n'$ that the water can take a long time (one or more time instant, especially if these are \cstr{short} such as $15$ or $5$ minutes) to reach the turbine from $n$ and $n'$ from the turbine.
\\
A particular note of caution has to be mentioned regarding the fact that \code{UpF[ l ]} can be *negative*: this means that the water is used in the turbine *before* it goes out of reservoir $n$. This is counter-intuitive, but can be explained by the fact that the pipe between $n$ and the turbine can be full, and therefore works as a \cstr{mini reservoir} in itself. When the turbine is started, a \cstr{bubble} (depression) is created uphill the turbine; this \cstr{bubbles up} the $n ==> TURBINE$ pipe until it reaches $n$, and it is only at that point that the water in $n$ starts flowing away. Hence, there is a negative temporal delay between the water starting flowing in the turbine and it starting flowing away from n. Note that if the $n ==> TURBINE$ pipe is rather empty, the delay is positive in that one have to start sending the water, which may take some time before filling the pipe and therefore starting the turbine. Of course these are all somewhat crude approximations of the true physical behavior, but they are accurate enough for this setting. Yet, the case \code{UpF[ l ] < 0} cannot be disregarded.

\subsubsection {\code{BatteryUnitBlock}}
The \code{BatteryUnitBlock} class derives from \code{UnitBlock} and implements a \cstr{reasonably standard} Battery storage, E-mobility, Centralized demand response, Distributed load management, Distributed storage, and Power to gas units in a single class at Unit commitment problem. This can be the case of actual physical batteries, either \cstr{large} (battery storage) or \cstr{small} (e-mobility, distributed storage), of methods that use some intermediate energy vector with limited local storage/production (power-to-gas units), as well as of \cstr{logical} mechanisms that allow to temporally shift production/consumption in a limited way, thereby acting like an energy storage (centralized demand response, distributed load management). \code{BatteryUnitBlock} provides a quite general concept of \cstr{battery} that covers different units which mostly fit the same mathematical equations pattern. For instance, a \code{BatteryUnitBlock} may or may not have a fixed demand (e-mobility has, other units have not) and it may or may not provide primary and secondary reserve (battery storage may do, but other units don't). Battery storage provide an additional flexibility to the system by shifting a surplus of electric energy (e.g. due to high renewable feeding) to times with high demand or lower renewable generation. The distributed battery storage can be aggregated in the energy cells or directly placed in a single node of the network. We will therefore not stress this dependency in the subsequent equations. We emphasize that potential contribution of batteries to inertia is still a subject of active research and should be considered as optional. Besides, since the transport sector is moving towards electrification, electric mobility will have a rising impact on the electricity system. First, electricity demand is growing due to a higher amount of electric vehicles that need to be charged. On the other hand, vehicles are used only a small amount of time while being charged over a much longer timespan (e.g. at night). This allows to shift the charging process in time and provide this flexibility to the overall energy system by means of an additional generator (vehicle-to-grid) or an additional load (power-to-vehicle). Two main differences between battery storages unit and other existing units in this class are:
\begin{itemize}
 \item battery storages unit can do primary and secondary reserve, while other units cannot;
 \item some of the units may have a fixed demand that battery storages unit has not.
\end{itemize}
Moreover, as the considered storage cycle is small w.r.t. the EUC time horizon, distributed storage is not considered as seasonal storage. Hence, the associated mathematical description follows the same equations as the one provided for battery storages unit. The specificity of distributed storage only relies on the fact that it is connected to a distribution grid node.

\noindent
\begin{itemize}

If \cstr{MinStorage} has length $1$ then \code{MinS[ t ]} contains the same value for all $t$. Note that it must always be \code{0 <= MinS[ t ] < MaxS[ t ]} for all $t$. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
%
\item The \variable \cstr{MaxStorage}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{MaxS[ t ]} that, for each time instant $t$, contains the maximum storage level of the unit for the corresponding time step. If \cstr{MaxStorage} has length $1$ then \code{MaxS[ t ]} contains the same value for all $t$. Otherwise, \code{MaxStorage[ i ]} is the fixed value of \code{MaxS[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \cstr{MinPower} has length $1$ then \code{MinP[ t ]} contains the same value for all $t$. Otherwise, \code{MinPower[ i ]} is the fixed value of \code{MinP[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.

This is meant to represent the vector \code{MaxP[ t ]} that, for each time instant $t$, contains the maximum active power output value of the unit for the corresponding time step. If \cstr{MaxPower} has length $1$ then \code{MaxP[ t ]} contains the same value for all $t$. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
%

This variable indicates the amount of the power that the unit was producing at time instant $-1$, i.e., before the start of the time horizon; this is necessary to compute the ramp-up and ramp-down constraints. This variable is optional; if \cstr{DeltaRampUp} and \cstr{DeltaRampDown} are not present, \cstr{InitialPower} should not be read, since there are no ramping constraints. If \cstr{DeltaRampUp} and \cstr{DeltaRampDown} are present but \cstr{InitialPower} is not provided, its value is taken to be $0$.

Otherwise, \code{DeltaRampUp[ i ]} is the fixed value of \code{DP[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. \subsubsection {\code{IntermittentUnitBlock}}
The \code{IntermittentUnitBlock} class derives from \code{UnitBlock} and implements a Intermittent Generation for a unit representing generation (be ir centralized or distributed) by intermittent (= unreliable) sources in the unit commitment problem, such as wind farms, solar parks and run-of-the-river hydroelectricity. Each unit is supposed to be connected to a specific node of the clustered network (which means that the \cstr{distributed} case refers to \cstr{distributed in a small region}, where of course \cstr{small} depends on the granularity of the network description. The model relies mainly on historical data of local generation of wind and solar at each node of the grid; these data are used to develop normalized generation profiles associated with wind and solar generators. Intermittent generators are supposed to be able to contribute to primary and secondary reserves. Contribution to the system inertia concerns more specifically run of river generators. The potential contribution of solar or wind generation to inertia is still the subject of active research. Reserve requirements are specified in order to be symmetrically available to increase or decrease power injected into the grid.
\smallskip
\noindent
Besides the mandatory \cstr{type} attribute of any \dBlock, the group must contain all the data required by the base \code{UnitBlock}, as described in the comments to \code{UnitBlock::deserialize}( \code{netCDF::NcGroup} ). In particular, we refer to that description for the crucial \dimensions \cstr{TimeHorizon}, \cstr{NumberIntervals} and \cstr{ChangeIntervals}. The \code{netCDF::NcGroup} must then also contain:
\begin{itemize}
 \item The \variable \cstr{MinPower}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{MinP[ t ]} that, for each time instant $t$, contains the minimum potential production value of the unit for the corresponding time step. If \cstr{MinPower} has length $1$ then \code{MinP[ t ]} contains the same value for all $t$. Otherwise, \code{MinPower[ i ]} is the fixed value of \code{MinP[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon}, then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded. Note that it must be \code{MnP[ t ] >= 0} for all $t$.
 %
 \item The \variable \cstr{MaxPower}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{MaxP[ t ]} that, for each time instant $t$, contains the maximum potential production value of the unit for the corresponding time step. If \cstr{MaxPower} has length $1$ then \code{MaxP[ t ]} contains the same value for all $t$. Otherwise, \code{MaxPower[ i ]} is the fixed value of \code{MaxP[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. Note that it must be \code{MxP[ t ] >= MnP[ t ] [>= 0]} for all t. Yet, \code{MxP[ t ] == MnP[ t ]} is possible: it means that (at time instant $t$) the unit cannot be curtailed and cannot provide any reserve.
 %
 \item The \variable \cstr{InertiaPower}, of type double and either indexed over the \dimension \cstr{NumberIntervals} or has size $1$. This is meant to represent the vector \code{IP[ t ]} which, for each time instant $t$, contains the contribution that the unit can give to the inertia constraint which depends on the active power that it is currently generating (basically, the constant to be multiplied to the active power variable) at time t for this unit. The variable is optional; if it is not defined, \code{IP[ t ] == 0} for each time instants $t$. If it has size $1$ then the entry \code{IP[ 0 ]} is assumed to contain the the inertia power value for this unit and all time instants $t$. Otherwise, \code{InertiaPower[ i ]} is the fixed value of \code{IP[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon} then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
%
 \item The scalar \variable \cstr{Gamma}, of type double and not indexed over any \dimension. This variable is used to take into account an uncertainty on the maximal potential production. Note that it must be \code{0 <= Gamma <= 1}; when \code{Gamma == 0}, the unit does not provide any reserve.
\end{itemize}

\subsubsection {\code{SlackUnitBlock}}
The \code{SlackUnitBlock} class derives from \code{UnitBlock} and implements implements a \cstr{slack} unit; a (typically, fictitious) unit capable of producing (typically, a large amount of) active power and/or primary/secondary reserve and/or inertia at any time period completely independently from each other and from all other time periods, albeit at a (typically, huge) cost. Such a unit is typically added to a Unit Commitment problem to ensure that it has a (fictitious) feasible solution, which may help solution methods. At the very least such a modified UC would produce a "least unfeasible" solution which can be used to identify the parts of the system that lack capacity/resources.
\smallskip
\noindent
Besides the mandatory \cstr{type} attribute of any \dBlock, the group must contain all the data required by the base \code{UnitBlock}, as described in the comments to \code{UnitBlock::deserialize}( \code{netCDF::NcGroup} ). In particular, we refer to that description for the crucial \dimensions \cstr{TimeHorizon}, \cstr{NumberIntervals} and \cstr{ChangeIntervals}. The \code{netCDF::NcGroup} must then also contain:
\begin{itemize}
 \item The \variable \cstr{MaxPower}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{MxP[ t ]} that, for each time instant $t$, contains the maximum active power output value of the unit for the corresponding time step. If \cstr{MaxPower} has length $1$ then \code{MxP[ t ]} contains the same value for all $t$. Otherwise, \code{MaxPower[ i ]} is the fixed value of \code{MxP[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. This \variable is optional, if is not provided then \code{MxP[ t ] == 0} for all $t$. Note that it must be \code{MxP[ t ] >= 0} for all $t$. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon} then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
 %
 \item The \variable \cstr{MaxPrimaryPower}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{MaxPP[ t ]} that, for each time instant $t$, contains the maximum amount of primary reserve that the unit can produce in the corresponding time step. If \cstr{MaxPrimaryPower} has length $1$ then \code{MaxPP[ t ]} contains the same value for all $t$. Otherwise, \code{MaxPrimaryPower[ i ]} is the fixed value of \code{MaxPP[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}.  \item The \variable \cstr{MaxSecondaryPower}, of type double and either of size $1$ or indexed over the \dimension \cstr{NumberIntervals}. This is meant to represent the vector \code{MaxSP[ t ]} that, for each time instant $t$, contains the maximum amount of secondary reserve that the unit can produce in the corresponding time step. If \cstr{MaxSecondaryPower} has length $1$ then \code{MaxSP[ t ]} contains the same value for all $t$. Otherwise, \code{MaxSecondaryPower[ i ]} is the fixed value of \code{MaxSP[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. This \variable is optional, if is not provided then \code{MaxSP[ t ] == 0} for all $t$. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon} then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
 %
 \item The \variable \cstr{MaxInertia}, of type double and either indexed over the \dimension \cstr{NumberIntervals} or has size $1$. This is meant to represent the vector \code{MaxI[ t ]} which, for each time instant $t$, contains the maximum "amount of inertia" (contribution that the SlackUnit can give to the inertia constraint) at time $t$. This \variable is optional; if it is not defined, \code{MaxI[ t ] == 0} for all time instants. If it has size $1$, then \code{MaxI[ t ] == MaxInertia[ 0 ]} for all $t$, regardless to what \cstr{NumberIntervals} says. Otherwise, \code{MaxInertia[ i ]} is the fixed value of \code{MaxI[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon} then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
 %
 \item The \variable \cstr{ActivePowerCost}, of type double and either indexed over the \dimension \cstr{NumberIntervals} or has size $1$. This is meant to represent the vector \code{APC[ t ]} that, for each time instant $t$, contains the cost of producing one unit of active power at the corresponding time step. This \variable is optional, if it is not provided then it's taken to be zero(although this is a very strange setting, as it would typically imply that all the demand, or at least as much as possible of it, is satisfied by the fictitious SlackUnit rather than from "real" ones). Otherwise, \code{ActivePowerCost[ i ]} is the fixed value of \code{APC[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}.  \item The \variable \cstr{PrimaryCost}, of type double and either indexed over the \dimension \cstr{NumberIntervals} or has size $1$. This is meant to represent the vector \code{PC[ t ]} that, for each time instant $t$, contains the cost of producing one unit of primary reserve at the corresponding time step. This \variable is optional; if it is not provided then it's taken to be zero (but this is a very strange setting, cf. the discussion in \code{ActivePowerCost}). If \cstr{PrimaryCost} has length $1$ then \code{PC[ t ]} contains the same value for $t$. Otherwise, \code{PrimaryCost[ i ]} is the fixed value of \code{PC[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}.  %
 \item The \variable \cstr{SecondaryCost}, of type double and either indexed over the \dimension \cstr{NumberIntervals} or has size $1$. This is meant to represent the vector \code{SC[ t ]} that, for each time instant $t$, contains the cost of producing one unit of secondary reserve at the corresponding time step. This \variable is optional; if it is not provided then it's taken to be zero (but this is a very strange setting, cf. the discussion in \code{ActivePowerCost}). If \cstr{SecondaryCost} has length $1$ then \code{SC[ t ]} contains the same value for $t$. Otherwise, \code{SecondaryCost[ i ]} is the fixed value of \code{SC[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon} then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.

 \item The \variable \cstr{InertiaCost}, of type double and either indexed over the \dimension \cstr{NumberIntervals} or has size $1$. Otherwise, \code{InertiaCost[ i ]} is the fixed value of \code{IC[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ i - 1 ] , ChangeIntervals[ i ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0}. If \code{NumberIntervals <= 1} or \code{NumberIntervals >= TimeHorizon} then the mapping clearly does not require \cstr{ChangeIntervals}, which in fact is not loaded.
\end{itemize}

\subsection {\code{NetworkBlock}}
The class \code{NetworkBlock}, which derives from the \Block, defines the basic interface for the constraints/optimization problems which describe the behaviour of the transmission network in a specific time instant in the Unit Commitment (UC) problem, as represented in \code{UCBlock}. The base class handles only basic information: it allows to read/set the topology (and capacity/susceptances) of the network, and the active power demand at the different nodes in the given time instant. This information is actually bunched together in a small \cstr{passive} \code{NetworkData} object (no methods, just a data repository) that can be either de-serialized or passed ready-made (typically, by the \code{UCBlock}). Details of the kind of network that is implemented (\cstr{bus}, DC equations, AC equations, OPF, ...) are entirely demanded to derived objects. The interface between a \code{NetworkBlock} and the rest of the UC is just the vector of node injection variables, which will have to satisfy the technical constraints of the transmission network. Besides the mandatory \cstr{type} attribute of any \dBlock, the group should contain the following:
\begin{itemize}
 \item Optionally, the \dimensions and variables necessary to a \code{NetworkData} object, that describe the transmission network; see \ref{NetworkData} for details. All that is optional, because the \code{NetworkData} object can alternatively be passed to the \code{NetworkBlock} via a call to \code{set\_NetworkData()}. Note that if \code{set\_NetworkData()} is called, but the representation of a \code{NetworkData} object is found in the NcGroup, then the \code{NetworkData} passed by \code{set\_NetworkData()} is ignored, and a new \code{NetworkData} object is read from the \code{NcGroup} and used instead.
 %
 \item The \cstr{ActiveDemand}, of type double, and of size \cstr{number of nodes}. If the \code{NetworkData} object description is present in the \code{NcGroup} this is the \dimension \cstr{NumberNodes}, but the \code{NetworkData} object is optional and it may not be there. Thus if \cstr{NumberNodes} is not there and \cstr{ActiveDemand} is, then the \code{NetworkData} object must have been passed by \code{set\_NetworkData()}, and the number of nodes can be read via \code{NetworkData::get\_number\_nodes()}. However, \cstr{ActiveDemand} itself is optional. If it is not found in the \code{NcGroup}, then it *must* be passed (either before or after the call to \code{deserialize()}) by calling \code{set\_ActiveDemand()}. Since both groups of data are optional, the \code{NcGroup}  can actually be empty which implies that all the data will be (or have been) passed by the in-memory interface. In this case, it would clearly be preferable to *entirely avoid the \code{NcGroup} to be there*, and in fact \code{UCBlock} has provisions for the \code{NcGroup} describing the \code{NetworkBlock} to be optional (see the comments to  \code{UCBlock::deserialize()}).
\end{itemize}

\subsubsection  {\code{NetworkData}} \label{NetworkData}
The \code{NetworkData} class is a nested sub-class which only serves to have a quick way to load all the basic data (topology and electrical characteristics) that describe the transmission network. The rationale is that while often the network does not change during the (short) time horizon of UC, it makes sense to allow for this to happen. This means that individual \code{NetworkBlock} objects may in principle have different \code{NetworkData}, but most often they can share the same. By bunching all the information together we make it easy for this sharing to happen.
\smallskip
\noindent
Deserialize a \code{NetworkData} out of a \code{netCDF::NcGroup}, which should contain the following:
\begin{itemize}
 \item the \dimension \cstr{NumberNodes} containing the number of nodes in the problem; this \dimension is optional, if it is not provided then it is taken to be \code{== 1};
 %
 \smallskip
 \noindent
 If \code{NumberNodes == 1} (equivalently, it is not provided), the network is a \cstr{bus} formed of only one node, and therefore all the subsequent information need not to be present since it is not loaded. If \code{NumberNodes > 1}, then all the subsequent information is mandatory:
 %
 \item the \dimension \cstr{NumberLines} containing the number of lines in the transmission network;
 %
 \item the \variable \cstr{StartLine}, of type int and indexed over the \dimension \cstr{NumberLines}; the $i-th$ entry of the variable is the starting point of the line (a number in \code{0, \dots, NumberLines - 1}). Note that lines are not oriented, but the flow of energy is; that is, a positive flow along line $i$ means that energy is being taken away from \code{StartLine[ i ]} and delivered to \code{EndLine[ i ]} (see next), a negative flow means vice-versa. Note that lines names here go from $0$ to \code{NLines.getSize() - 1};
 %
 \item the \variable \cstr{EndLine}, of type int and indexed over the \dimension \cstr{NumberLines}; the $i-th$ entry of the variable is the ending point of the line (a number in \code{0, \dots, NumberLines - 1}. Note that lines are not oriented, but see above). \code{StartLine[ i ] == EndLine[ i ]} (a self-loop) is not allowed, but multiple lines between the same pair of nodes are. Note that lines names here go from $0$ to \code{NLines.getSize() - 1};
 %
 \item the \variable \cstr{MinPowerFlow}, of type double and indexed over the \dimension \cstr{NumberLines}; the $i-th$ entry of the variable is assumed to contain the minimum power flow on line $i$ (note that this is typically a negative number as lines are bi-directional, see above);
%
 \item the \variable \cstr{MaxPowerFlow}, of type double and indexed over the \dimension \cstr{NumberLines}; the $i-th$ entry of the variable is assumed to contain the maximum power flow at line $i$ (a non-negative number);
 %
 \item the \variable \cstr{Susceptance}, of type double and indexed over the \dimension \cstr{NumberLines}; the $i-th$ entry of this variable is assumed to contain the susceptance of line $i$. Note that this is strictly a positive value.
\end{itemize}

\subsection {\code{HeatBlock}}

The \code{HeatBlock} class implements the \Block concept [see Block.h] for a set of \cstr{heat units} as required in the plan4res project. The constraints regarding heat management in the plan4res project can be described separately for each \code{HeatBlock}. In the parlance of plan4res, a HB is the intersection of an Energy Cell and a heat-ID: a set of heat-producing units that are geographically close enough to exchange heat of the same type, together with possibly a (single) storage for this type of heat, in order to satisfy a given heat demand. HBs are only connected to each other because some heat-producing units are also electricity-producing ones, where heat is a by-product or a co-product of electricity. However, this linking \cstr{happens at the level of the main UC model}, and therefore it is not required for the description of the internal constraints of a HB. All this on a given time horizon, as in the UC problem. The operations of the heat generating unit are described on a discrete time horizon where there may exist some heat-producing units, possibly of a single heat storage, and of the demand that has to be satisfied.
\smallskip
\noindent
Besides the mandatory \cstr{type} attribute of any \dBlock, the group should contain all the following:
%
\begin{itemize}
 \item the \dimension \cstr{NumberHeatUnits} containing the number heat-producing units. This is not optional, and has to be \code{>= 1};
 %
 \item the \dimension \cstr{TimeHorizon} containing the time horizon. The \dimension is optional because the same information may be passed via the method \code{set\_time\_horizon()}, or directly retrieved from the father if it is a \code{UCBlock}; see the comments to \code{set\_time\_horizon()} for details;
 %
 \item the \dimension \cstr{NumberIntervals} that is provided to allow that all time-dependent data in the \code{HeatBlock} can only change at a subset of the time instants of the time interval, being therefore piecewise-constant (possibly, constant). \cstr{NumberIntervals} should therefore be \code{<=} \cstr{TimeHorizon}, with three distinct cases:
 %
 \begin{itemize}
  \item  \cstr{NumberIntervals} \code{<= 1}, which is taken to mean \cstr{NumberIntervals} \code{== 1}; this is what is assumed if the \dimension, that is optional, is not there. This means that the value of each relevant data in the \code{UCBlock} (see e.g. \cstr{CostHeatUnit}, \cstr{MinHeatProduction} and \cstr{MaxHeatProduction} below)is the same for each time instant \code{0, \dots,} \cstr{TimeHorizon} \code{ - 1} in the time horizon. In this case, the variable \cstr{ChangeIntervals} (see below) is ignored;
  %
  \item \code{1 < }\cstr{NumberIntervals} \code{<} \cstr{TimeHorizon}, which means that in some time instants, *but not all of them*, the values of some of the relevant data are changing; the intervals are then described in variable \cstr{NumberIntervals};
  %
  \item \cstr{NumberIntervals} \code{==} \cstr{TimeHorizon},  which means that values of the relevant data changes at every time interval (in principle; of course there is nothing preventing the same value to be repeated in the \code{netCDF} input). Also in this case the variable \cstr{NumberIntervals} is ignored, since it is useless;
  %
 \end{itemize}
 %
 Note that this (together with \cstr{NumberIntervals}, if defined) obviously sets the \cstr{maximum frequency} at which data can change; if some data changes less frequently (say, it is constant), then the same value will have to be repeated. Individual data can also have specific provisions for the case where the data is all equal despite \cstr{NumberIntervals} saying differently.
 %
 \item the \variable \cstr{ChangeIntervals}, of type integer and indexed over the \dimension \cstr{NumberIntervals}. The time horizon is subdivided into \code{NumberIntervals = k} of the form $[ 0 , i_1 ]$,$[ i_1 + 1 , i_2 ]$, \dots $[ i_{k-1} + 1, TimeHorizon - 1 ]$; \cstr{ChangeIntervals} then has to contain $[ i_1 , i_2 , \dots i_{k-1} ]$ . Note that, therefore, \cstr{ChangeIntervals} has one significant value less than \cstr{NumberIntervals}, which means that \code{ChangeIntervals[ NumberIntervals - 1 ]} is ignored. Anyway, the whole variable is ignored if either \cstr{NumberIntervals} \code{<= 1} (such as if it is not defined), or \cstr{NumberIntervals} \code{>=} \cstr{TimeHorizon};
 %
 \item the \variable \cstr{TotalHeatDemand}, of type double and indexed over the \dimension \cstr{TimeHorizon}: entry \code{TotalHeatDemand[ t ]} is assumed to contain the total heat demand of this heat block to be satisfied for the corresponding time instant $t$. Note that this variable does *not* use the \cstr{NumberIntervals} / \cstr{ChangeIntervals} system, as demand is usually changing from one time instant to the next;
 %
 \item the variable \cstr{CostHeatUnit}, of type double and indexed over two \dimensions. The first \dimension can have size $1$ or \cstr{NumberIntervals}. The second \dimension has size \cstr{NumberHeatUnits}. This is meant to represent the matrix \code{CHU[ t , i ]} which is assumed to contain the unitary cost of heat production of heat-producing unit $i$ for time instant $t$. If the first \dimension has size $1$, then the cost is the same for all time instants (for the same unit). Otherwise, \code{CostHeatUnit[ h , i ]} is the fixed value of \code{CHU[ t , i ]} for all $t$ in the interval \code{[ ChangeIntervals[ h - 1 ], ChangeIntervals[ h ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0};
 %
 \item the \variable \cstr{MinHeatProduction}, of type double and indexed over two \dimensions. The first \dimension can have size $1$ or \cstr{NumberIntervals}. The second \dimension has size \cstr{NumberHeatUnits}. This is meant to represent the matrix \cstr{MinHP[ t , i ]} which is assumed to contain the minimum heat production of heat-producing unit $i$ for time instant $t$. The variable is optional; if it is not provided at all, it is intended \cstr{MnHP[ t , i ] == 0} for all $i$ and $t$. If the first \dimension has size $1$, then the minimum heat production is the same for all time instants (for the same unit). Otherwise, \code{MinHeatProduction[ h , i ]} is the fixed value of \code{MinHP[ t , i ]} for all $t$ in the interval \code{[ ChangeIntervals[ h - 1 ], ChangeIntervals[ h ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0};
 %
 \item the \variable \cstr{MaxHeatProduction}, of type double and indexed over two \dimensions. The first \dimension can have size $1$ or \cstr{NumberIntervals}. The second \dimension has size \cstr{NumberHeatUnits}. This is meant to represent the matrix \cstr{MaxHP[ t , i ]} which is assumed to contain the maximum heat production of heat-producing unit $i$ for time instant $t$. It is assumed \code{MaxHP[ t , i ] >= MinHP[ t , i ] >= 0} for all $i$ and $t$, with strict inequality holding for at least some $t$ for each unit $i$ (otherwise the production of unit $i$ is fixed and there is nothing to decide). The variable is optional; if it is not provided at all, it is intended \cstr{MaxHP[ t , i ] == 0} for all $i$ and $t$. If the first \dimension has size $1$, then the maximum heat production is the same for all time instants (for the same unit). Otherwise, \code{MaxHeatProduction[ h , i ]} is the fixed value of \code{MaxHP[ t , i ]} for all $t$ in the interval \code{[ ChangeIntervals[ h - 1 ], ChangeIntervals[ h ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0};
 %
 \item the \variable \cstr{MinHeatStorage}, of type double and either indexed over the \dimension \cstr{NumberIntervals} or has size $1$. This is meant to represent the vector \code{MinHS[ t ]} which, for each time instant $t$, contains the minimum heat storage of this HB. The variable is optional, if it is not provided at all it is intended that \code{MinHS[ t ] == 0} for all $t$. If the variable has size $1$, then the minimum heat storage is the same for all time instants. Otherwise, \code{MinHeatStorage[ h ]} is the fixed value of \code{MinHS[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ h - 1 ], ChangeIntervals[ h ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0};
 %
 \item the \variable \cstr{MaxHeatStorage}, of type double and either indexed over the \dimension \cstr{NumberIntervals} or has size $1$. This is meant to represent the vector \code{MaxHS[ t ]} which, for each time instant $t$, contains the maximum heat storage of this HB. The variable is optional, if it is not provided at all it is intended that \code{MaxHS[ t ] == 0} for all $t$  and since it's assumed that \code{MaxHS[ t ] >= MinHS[ t ] >= 0} for all $t$, this means that there is no heat storage in this HB.. If the variable has size $1$, then the maximum heat storage is the same for all time instants. Otherwise, \code{MaxHeatStorage[ h ]} is the fixed value of \code{MaxHS[ t ]} for all $t$ in the interval \code{[ ChangeIntervals[ h - 1 ], ChangeIntervals[ h ] ]}, with the assumption that \code{ChangeIntervals[ - 1 ] = 0};
 %
 \item the scalar \variable \cstr{InitialHeatAvailable}, of type double and not indexed over any \dimension, which indicates the the amount of heat in the storage at the beginning of the first time instant in this HB. It is assumed that \cstr{MaxHS[ 0 ] >= InitialHeatAvailable >= MinHS[ 0 ]}. This variable is optional, if it is not provided it is taken to be \code{InitialHeatAvailable == MinHS[ 0 ]}. If there is no heat storage (say, \code{MaxHeatStorage} is not defined) then this variable is not read, because it is not used;
 %
 \item the scalar \variable \cstr{StoringHeatRho}, of type double and not indexed over any \dimension, which indicates the inefficiency of storing heat in the heat storage (if any) in this HB. This variable is optional and it must always be \code{StoringHeatRho <= 1}, if it is not provided it is taken to be \code{StoringHeatRho == 1}. If there is no heat storage (say, MaxHeatStorage is not defined) then this variable is not read, because it is not used;
 %
 \item the scalar \variable \cstr{ExtractingHeatRho}, of type double and not indexed over any \dimension, and which indicates the inefficiency of extracting heat from the heat storage (if any) in this HB. This variable is optional and it must always be \code{ExtractingHeatRho >= 1}, if it is not provided it is taken to be \code{ExtractingHeatRho == 1}. If there is no heat storage (say, \code{MaxHeatStorage} is not defined) then this variable is not read, because it is not used;
 %
 \item the scalar \variable \cstr{KeepingHeatRho}, of type double and not indexed over any \dimension, which indicates the double of keeping heat in the heat storage (if any) in this HB. This variable is optional and it must always be \code{KeepingHeatRho <= 1}, if it is not provided it is taken to be \code{KeepingHeatRho == 1}. If there is no heat storage (say, \code{MaxHeatStorage} is not defined) then this variable is not read, because it is not used;
\end{itemize}

\section{\BlockConfig for existing \dBlock}

As described in \S \ref{ssec:BlockConfig}, each \Block can have several \Configuration parameters, which can be dealt with by a \BlockConfig object. It makes therefore sense to collect here all possible \Configuration parameters for existing \dBlock, since these may end up in a \SMSpp \netCDF file.

%- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
\subsection{Parameters of \code{MCFBlock}}

The \code{MCFBlock} class defines the following \Configuration parameters:
%
\begin{itemize}
 \item \code{f\_static\_constraints\_Configuration}. The static constraint of a MCF are the flow conservation equations and the bound constraints. The latter are typically implemented via a \code{std::vector<LB0Constraint>} with exactly $m$ entries. However, If \emph{all} the upper bound are $+\infty$, it is possible to skip the \code{std::vector<LB0Constraint>} entirely and just use the fact that the \code{ColVariable can be defined to be non-negative}. If \code{f\_static\_constraints\_Configuration} is set, it is a \code{SimpleConfiguration<int>} whose \code{f\_value} is not $0$, the bound constraints are not implemented if it is possible to do so; otherwise they are always implemented. Note that this makes it impossible to change any upper bound.
 %
 \item \code{f\_is\_feasible\_Configuration}. If \code{f\_is\_feasible\_Configuration} is a \code{SimpleConfiguration<double>}, its \code{f\_value} is taken as the parameter for deciding what ``approximately feasible'' exactly means while checking satisfaction of both flow conservation constraint and flow upper/lower bounds; the value is taken as the \emph{relative} tolerance for those checks.
 %
 \item \code{f\_is\_optimal\_Configuration}. Checking optimality of a primal-dual solution of the MCF problems means checking that both are approximately feasible, and that they approximately satisfy the Complementary Slackness Conditions. This requires two parameters for deciding what ``approximately feasible'' means, one for the primal ($\epsilon_f$) and one for the dual ($\epsilon_c$). If \code{f\_is\_optimal\_Configuration} is a \code{SimpleConfiguration< std::pair<double,double> >}, then $\epsilon_c =$ \code{f\_value.first} and $\epsilon_f =$ \code{f\_value.second}.
 %
 \item \code{f\_solution\_Configuration}. For all the methods dealing with solutions, i.e., \code{get\_Solution()} and \code{map\_[back/forwatd]\_solution()}, if \code{f\_solution\_Configuration} is a \code{SimpleConfiguration<int>}, then its \code{f\_value} decides what is mapped, with the following encoding: $1$ means ``only map the primal solution'', $2$ means ``only map the dual solution'', everything else (e.g., $0$) means "
 ``map everything''.
\end{itemize}

\section{\ComputeConfig for existing \dSolver}

As described in \S \ref{ssec:ComputeConfig}, each \Block can have several \ComputeConfig parameters, which can be dealt with by a \BlockSolverConfig object. It makes therefore sense to collect here all possible \ComputeConfig parameters for the existing objects that define actual values for their algorithmic parameters, since these may end up in a \SMSpp \netCDF file.

%- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
\subsection{Standard parameters in \Solver}

The base \Solver class defines a set of ``general'' algorithmic parameters, described in the following Table.

\begin{longtable}{|c|c|p{14cm}|}
 \hline
 name & title & description \\
 %
 \hline
 \code{intMaxIter} & \code{int} & The algorithmic parameter for setting the maximum number of iterations that the next call to \code{solve()} is allowed to execute for trying to solve the \Block. The concept of ``what exactly an iteration is'' is clearly \Solver-dependent, and the user of the \Solver need supposedly be aware of which concrete \dSolver it is actually using to be able to sensibly set this parameter; however, because most \Solver will actually be iterative processes, it makes sense to offer  support for this notion in the base class. \\
 %
 \hline
 \code{intMaxSol} & \code{int} & The algorithmic parameter for setting the maximum  number of different solutions to the \Block that the \Solver should attempt to obtain and store. Mathematical models can have (very) many solutions: an objective function precisely helps in selecting among them, but even that may not be enough to narrow the choice down to a single solution (multiple optima may exist, or quasi-optimal solutions may also be sought for for any number of reasons). On the other hand, a solution can be a ``big'' object, and storing it may be costly. It may be therefore helpful for a Solver to know beforehand how many different solutions the user would like to get. Among the reasonable values for this parameter, $1$ says ``I don't care of multiple solutions, give me only the best one'', and $0$ says ``I don't care of solutions at all, just tell me if there is any, and what its value is''. The default is $1$. \\
 %
 \hline
 \code{intLogVerb} & \code{int} & An integer parameter dictating how "verbose" the log of the \Solver has to be. The specific meaning of each value is \Solver-dependent, but it is intended that $0$ means ``no log at all'', and increasing values correspond to increasing verbosity. The default value is $0$ (no log). \\
 %
 \hline
 \code{dblMaxTime} & \code{dbl} & The algorithmic parameter for setting the maximum time limit that the next call to \code{solve()} can expend in trying to solve the \Block. The value is assumed to be in seconds, and it's a double (so both very quick and very slow solvers are supported). The base \Solver class does not explicitly distinguish between ``wall-clock time'' and ``CPU time'', which may be rather different especially in a parallel environment, but this concept can be easily added by derived classes.\\
 %
 \hline
 \code{dblRelAcc} & \code{dbl} & The algorithmic parameter for setting the \emph{relative} accuracy required to the solution of the Block. This is geared towards single-objective optimization problems, and it is defined as follows: a solution for a \emph{minimization} problem has a relative accuracy of $\varepsilon$ if a feasible (to within the required tolerance for each \Block) solution has been obtained, an upper bound $ub$ on its objective function value has been found, a lower bound $lb$ on the optimal value of the problem has been found, and $ub - lb \leq \varepsilon \max( |lb| , 1 )$. The roles of $ub$ and $lb$ are suitably reversed for a maximization problem. The default is \code{1e-6}.\\
 %
 \hline
 \code{dblAbsAcc} & \code{dbl} & The algorithmic parameter for setting the \emph{absolute} accuracy required to the solution of the model. This is geared towards single-objective optimization problems, and it is defined as follows: a solution for a \emph{minimization} problem has a absolute accuracy of $\varepsilon$ if a feasible  (to within the required tolerance for each \Block) solution has been obtained, an upper bound $ub$ on its objective function value has been found, a lower bound $lb$ on the optimal value of the problem has been found, and $ub - lb \leq \varepsilon$. The roles of $ub$ and $lb$ are suitably reversed for a maximization problem. The default is $+\infty$, which is intended to mean that the only working accuracy is the relative one.\\
 %
 \hline
 \code{dblUpCutOff} & \code{dbl} & The algorithmic parameter for setting the \emph{upper cut off} of the solution process. This is a value basically telling the \Solver ``when enough is enough''. In particular, if the Solver obtains a certified lower bound $lb$ on the optimal value such that $lb \geq \varepsilon$ with the provided parameter $\varepsilon$, then it can stop. This is a certificate that the optimal value is at least $\varepsilon$. For a maximization problem the condition says: I actually needed a solution with objective function value at least as good as (i.e., larger than) $\varepsilon$, now that I have found one the problem is as good as solved to me. Hence this parameter is analogous to the maximum absolute accuracy \code{dblAbsAcc}, but ``weaker'' in that it does not not require any upper bound to work. For a minimization problem, instead, the condition says: I actually needed a solution with objective function value at least as good as (i.e., smaller than) $\varepsilon$, now that I have know for sure that this is never going to happen the problem is as good as unfeasible to me. The default is $+\infty$.\\
 %
 \hline
 \code{dblLwCutOff} & \code{dbl} & The algorithmic parameter for setting the \emph{lower cut off} of the solution process. This is a value basically telling the \Solver ``when enough is enough''. In particular, if the \Solver obtains a certified upper bound $ub$ on the optimal value such that $ub \leq \varepsilon$ with the provided parameter $\varepsilon$, then it can stop. This is a certificate that the optimal value is at most $\varepsilon$. For a minimization problem the condition says: I actually needed a solution with objective function value at least as good as (i.e., smaller than) $\varepsilon$, now that I have found one the problem is as good as solved to me. Hence this parameter is analogous to the maximum absolute accuracy \code{dblAbsAcc}, but ``weaker'' in that it does not not require any lower bound to work. For a maximization problem, instead, the condition says: I actually needed a solution with objective function value at least as good as (i.e., larger than) $\varepsilon$, now that I have know for sure that this is never going to happen the problem is as good as unfeasible to me. The default is $-\infty$.\\
 %
 \hline
 \code{dblRAccSol} & \code{dbl} & The algorithmic parameter for setting the relative accuracy of the accepted solutions. It instructs the \Solver not to even consider a solution among the ones to be reported \code{intMaxSol} if its objective function value is ``too'' bad. For a minimization problem, the objective function value of a feasible solution provides an upper bound $ub$ on the optimal value. Assuming a lower bound $lb$ on the optimal value of the problem has been found, a solution is deemed acceptable with the provided parameter $\varepsilon$ if $ub - lb \leq \varepsilon \max( |ub| , |lb| , 1 )$. Note that if no $lb$ is available, the above formula can be replaced with $ub - f_{best} \leq \varepsilon \max( |ub| , |f_{best}| , 1 )$, where $f_{best}$ is the value of the best (with smallest objective value) solution found so far. The roles of $ub$ and $lb$ are suitably reversed for a maximization problem. The default is $+\infty$.\\
 %
 \hline
 \code{dblAAccSol} & \code{dbl} & Similar to \code{dblRAccSol} but for an \emph{absolute} accuracy; that is, a solution is deemed acceptable with the provided parameter $\varepsilon$ if $ub - lb \leq \varepsilon$ or $ub - f_{best} \leq \varepsilon$ with the same notation as in \code{dblRAccSol} and the same provisions about the case of a maximization problem. The default is $+\infty$.\\
 %
 \hline
 \code{dblFAccSol} & \code{dbl} & The algorithmic parameter for setting the maximum relative allowed violation of constraints. Whenever the \Solver is incapable of finding feasible solutions (maybe because there is none), it may still be useful that it returns the ``least unfeasible'' ones. This parameter instructs the \Solver not to even consider a solution among the ones to be reported (see \code{intMaxSol}) if its violation is ``too'' bad. The actual meaning of this parameter may be \Solver-dependent, but it can be thought to work as the ``relative constraint violation''. A setting of $0$ may be taken as a way to tell the Solver not to bother to produce unfeasible solutions at all, which is why this is the default value of the parameter.\\
  \hline
\end{longtable}

\begin{longtable}{|c|c|p{14cm}|}
 \hline
 name & title & description \\
 %
 \hline
 \code{intMaxDSol} & \code{int} & The algorithmic parameter for setting the maximum number of different \emph{dual} solutions that the \Solver should attempt to obtain and store. Since dual solutions can be a ``big'' objects (in some cases, much bigger than primal sones), storing them may be costly. It may be therefore helpful for a \code{CDASolver} to know beforehand how many different dual solutions the user would like to get. Among the reasonable values for this parameter, $1$ says ``I don't care of multuple dual solutions, give me only the best one'', and $0$ says ``I don't care of dual solutions at all, just tell me if there is any, and what its value is''. If the original problem is a minimization one, its dual is a maximization one. Hence, the objective function value of a dual solution provides a lower bound $lb$ on the optimal dual value (which may, or may not, be equal to that of the primal problem). Assuming an upper bound $ub$ on the optimal value of the \emph{dual} problem has been found (note that this can be obtained by means of the objective value of a feasible \emph{primal} solution), a solution is deemed acceptable with the provided parameter $\varepsilon$ if $ub - lb \leq \varepsilon \max( |ub| , |lb| , 1 )$. Note that if no $ub$ is available, the above formula can be replaced with $f_{best} - lb \leq \varepsilon \max( |f_{best}| , |lb| , 1 )$ where $f_{best}$ is the value of the best (with largest objective value) solution found so far. The roles of $ub$ and $lb$ are suitably reversed if the primal is a maximization problem, so that the dual is a minimization one. The default is $+\infty$. \\
 %
 \hline
 \code{dblAAccDSol} & \code{dbl} & Similar to \code{dblRAccDSol} but for an \emph{absolute} accuracy; that is, a dual solution is deemed acceptable with the provided parameter $\varepsilon$ if $ub - lb \leq \varepsilon$ or $f_{best} - lb \leq \varepsilon$ with the same notation as in \code{dblRAccDSol} and the same provisions about the case of a maximization problem. The default is $+\infty$. \\
 %
 \hline
 \code{dblFAccDSol} & \code{dbl} & The algorithmic parameter for setting the maximum relative allowed violation of \emph{dual} constraints, assuming of course something like that exists in the specific dual that is being dealt with. Whenever the \code{CDASolver} is incapable of finding feasible dual solutions (maybe because there is none), it may still be useful that it returns the ``least unfeasible'' ones. This parameter instructs the \code{CDASolver} not to even consider a solution among the ones to be reported (see \code{intMaxDSol}) if its violation is ``too'' bad. The actual meaning of this parameter is necessarily be \code{CDASolver}-dependent; intuitively, it may be thought to work as the ``relative constraint violation'' \code{feas\_epsilon} of \Block if the concept of ``dual constraint'' is applicable. A setting of $0$ may be taken as a way to tell the \code{CDASolver} not to bother to produce unfeasible solutions at all, which is why this is the default value of the parameter. \\
 %
 \hline
\end{longtable}

\subsection{Standard parameters in \code{Function}}

The base \code{Function} class defines a set of ``general'' algorithmic parameters, described in the following Table.

\begin{longtable}{|c|c|p{14cm}|}
 \hline
 name & title & description \\
 %
 \hline
 \code{intMaxIter} & \code{int} & The algorithmic parameter for setting the maximum number of iterations in the next call to \code{compute()}. The concept of ``what exactly an iteration is'' is clearly dependent on the \code{Function}, and it may not even make sense for all \code{Function}. However, some \code{Function} will actually be iterative processes, and therefore it makes sense to offer support for this notion in the base class. The default is $+\infty =$ no limits.\\
 %
 \hline
 \code{dblMaxTime} & \code{dbl} & The parameter for setting the maximum time limit for the next call to \code{compute()}. The value is assumed to be in seconds, and it's a double (so both very fast and very slow computations are supported). The \code{Function} class (so far) does not explicitly distinguish between ``wall-clock time'' and ``CPU time'', which may be rather different especially in a parallel environment. The default is $+\infty$.\\
 %
 \hline
 \code{dblRelAcc} & \code{dbl} & The parameter for setting the \emph{relative} accuracy required to the function value. That is, if both an upper bound $ub$ and a lower bound $lb$ on the value have been found, then \code{compute()} can stop as soon as $ub - lb \leq \code{dblRelAcc} \max( |lb| , 1 )$. The default is \code{1e-6}.\\
 %
 \hline
 \code{dblAbsAcc} & \code{dbl} & The parameter for setting the \emph{absolute} accuracy required to the function value. That is, if both an upper bound $ub$ and a lower bound $lb$ on the value have been found, then \code{compute()} can stop as soon as $ub - lb \leq \code{dblRelAcc}$. The default is $+\infty$, which is intended to mean that the only working accuracy is the relative one.\\
 %
 \hline
 \code{dblUpCutOff} & \code{dbl} & The parameter for setting the ``upper cut off'' of the computation; that is, if a lower bound $lb$ on the value has been found, then \code{compute()} can stop as soon as $lb \geq \code{dblUpCutOff}$. This is a certificate that the value is at least \code{dblUpCutOff}. The default is $+\infty$, i.e., no upper cut off.\\
 %
 \hline
 \code{dblLwCutOff} & \code{dbl} & The parameter for setting the ``lower cut off'' of the computation; that is, if an upper bound $ub$ on the value has been found, then \code{compute()} can stop as soon as $ub \leq \code{dblLwCutOff}$. This is a certificate that the value is at most \code{dblLwCutOff}. The default is $-\infty$, i.e., no lower cut off.\\
 \hline
\end{longtable}

\subsection{Standard parameters in \code{C05Function}}

The \code{C05Function} class extends the parameters of \code{Function} with the ones described in the following Table.

\begin{longtable}{|c|c|p{14cm}|}
 \hline
 name & title & description \\
 %
 \hline
 \code{intLPMaxSz} & \code{int} & The algorithmic parameter for setting the size of the ``local pool'', that is, the maximum number of linearizations that should be stored in the local pool. The default is $1$, which corresponds to the fact that the \code{Function} can only produce a single linearization at a time (for it is, say, smooth).\\
 %
 \hline
 \code{intGPMaxSz} & \code{int} & The algorithmic parameter for setting the size of the ``global pool'', that is, the maximum number of linearizations that should be stored in the local pool. The default is $0$, which corresponds to the fact that the \code{Function} cannot store any linearization (for it is, say, smooth and therefore there is no need to).\\
 %
 \hline
 \code{dblRAccLin} & \code{dbl} & A linearization $( g , \alpha )$ computed at the point $x$ is ``accurate'' if the value of the linearization coincides with the value of the function at $x$, i.e., $\alpha = f(x)$. In general linearizations that are not ``completely accurate'' can still be useful: for instance, in the Lagrangian case an $\varepsilon$-optimal solution to the Lagrangian problem gives rise to a valid linearization $( g , \alpha )$ with $\varepsilon \geq f(x) - \alpha$. This can be deemed interesting if $\varepsilon$ is ``small'', but not if $\varepsilon$ is ``large''. This parameter instructs the \code{C05Function} not to bother reporting (and therefore storing in the ``local pool'') any linearization having a relative error with $f(x)$ larger than \code{dblRAccLin}. This would generally mean $| f(x) - \alpha | \leq \code{dblRAccLin}  \max( | f(x) | , | \alpha | , 1 )$, except that the value $f(x)$ may not be known exactly, with only lower and/or upper bounds on it available. The actual formula therefore depends on what information is actually available: for instance, in the Lagrangian case one knows that $f(x) \geq \alpha$, and therefore typically an upper estimate $ub \geq f(x)$ is used in the formula instead of $f(x)$. The default is $0$, i.e., ``only perfect linearizations are allowed''.\\
 %
 \hline
 \code{dblAAccLin} & \code{dbl} &  Similar to \code{dblRAccLin} but for an \emph{absolute} accuracy; that is, a linearization is deemed acceptable if $| f(x) - \alpha | \leq \code{dblAAccLin}$, except that the value $f(x)$ may not be known exactly, with only lower and/or upper bounds on it available. The actual formula therefore depends on what information is actually available: for instance, in the Lagrangian case one knows that $f(x) \geq \alpha$, and therefore typically an upper estimate $ub \geq f(x)$ is used in the formula instead of $f(x)$. The default is $0$, i.e., ``only perfect linearizations are allowed''. \\
 \hline
\end{longtable}

\section{Conclusion}

This document is intended as a quick reference manual for anybody who is required to construct \SMSpp \netCDF input files. It should be remarked that basically all the \dBlock and \dConfiguration objects are supposed to have an in-memory interface to initialize the data. Thus, a workable way to produce \netCDF input files for those is to use the in-memory interface, and then the \code{serialize()} method to save it into a file. Yet, \netCDF has interfaces for all primary programming languages, hence files with the required format can be written independently by any \SMSpp object.
